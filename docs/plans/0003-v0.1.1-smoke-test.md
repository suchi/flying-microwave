# 0003: v0.1.1 スモークテストと実機での確認

- ステータス: 合意済み(2026-11-02)
- 日付: 2026-11-02
- 関連: [計画0001](0001-initial-implementation-plan.md)のPhase 1の作業14、8.1、D-24、D-30、D-31、[懸念事項の確認](../reviews/0003-roadmap-concerns-to-v1.md)のK-07

## 目的

v0.1.1は、v0.1.0で先送りした確認を済ませる版である(D-30)。製品の機能は増やさない(製品の変更は、確認で見つかった問題の修正だけにする。D-6)。

1. スモークテスト(作業14)を作り、CIとリリースのワークフローで、起動と終了を自動で確かめる。
2. メンテナーが、v0.1.1の候補の成果物で実機での確認を行う(D-30の完了条件)。
3. 商標の確認を済ませる(メンテナー)。
4. リリースのワークフローの所要時間を、v0.1.1のタグの実行で記録する(D-31)。

## 要件

| ID | 要件 |
| --- | --- |
| F-01 | `/s`で起動し、すべてのウィンドウの最初のフレームが表示されたあと、キー入力を送ると終了する。入力から画面が消える(そのプロセスの表示中のトップレベルのウィンドウがなくなる)までの時間を記録し、0.2秒(N-02)を超えたら失敗にする。プロセスは2秒以内に終わり、ログの終了の理由がキーの押下であること(D-5) |
| F-02 | テスト用の親ウィンドウを作って`/p <HWND>`で起動し、最初のフレームが表示されたあと、親ウィンドウを破棄すると、2秒以内に終了する。ログの終了の理由が、ウィンドウの破棄か親の消失であること |
| F-03 | 認識できない引数(`/x`)で起動すると、全画面のウィンドウを作らず、設定のメッセージボックスを表示する。メッセージボックスを閉じると終了する |
| F-04 | どのテストのあとにも、テスト対象のプロセスが残っていない |
| F-05 | 起動から最初のフレームまでの時間(N-01の目安)と、使われたアダプタの名前を、ログから読んでテストの出力に記録する。N-01は実機で判定するため、ここでは失敗の条件にしない |
| N-01 | 新しい依存を加えない(`windows-sys`は既存の版を使う) |
| N-02 | テストは1回あたり2分以内に終わる。どの待ち時間にも上限を設け、止まったまま残らない |

## 設計(案)

- テストの道具: ワークスペースに、Windows専用の小さなcrate(`crates/smoke`、`publish = false`)を加える。ビルドした実行ファイルのパスを引数に受け取り、F-01〜F-05を順に実行する。CIとリリースでは、名前を変える前の`flying-microwave.exe`を渡す(引数があるときの動作は`.scr`と同じ。拡張子が効くのは引数がないときだけ)。
  - テストする実行ファイルには、専用の一時フォルダを環境変数`TMP`と`TEMP`で渡す。利用者の`%TEMP%\flying-microwave.log`を消したり、ほかのプロセスのログと混ざったりしないためである。
  - ケースが失敗したときは、そのプロセスのログの行をすべて出力する。成功したときも、アダプタの名前、前景にできたか(`SetForegroundWindow`)、終了の理由を出力する。
  - 最初のフレームの検出は、製品のログ(`%TEMP%\flying-microwave.log`)の`first frame presented`の行で行う。v0.x系の間はログをいつも書く(D-25)。v1.0.0でログを既定で書かなくする(Phase 6)ときに、テストでだけログを有効にする方法を決める(Phase 6の作業に登録する)。
  - 入力は`SendInput`で送る。プロセスの終了は、標準ライブラリの`Child::try_wait`を短い間隔で呼んで待つ。
  - 「画面が消えた」は、そのプロセスの全画面を覆うウィンドウが表示されていなくなったことで判定する。winitは、自分のメッセージのために、大きさが0の表示中のウィンドウをプロセスの終了まで持つため、それは数えない。
  - 描画は、ランナーで使えるアダプタ(GPUがなければWARP)で行う。製品のコードは、D-6の修正のほかは変えない。
  - 親ウィンドウの破棄(`DestroyWindow`)は、別のプロセスの子ウィンドウへの同期の送信を伴いうるため、プレビューのプロセスが止まっていると戻らないおそれがある(推測)。この場合は、ワークフローの手順の時間の上限(5分)で止める。
- 実行する場所:
  - CIのWindowsのジョブ(x64、PRごと)。製品のビルドのあとに実行する。
  - リリースのワークフローのビルドのジョブ(x64とarm64)。arm64は、これが初めての起動の自動の確認になる(ADR-0016)。リリースノートの「arm64版について」の節(`scripts/prepare_release.py`)も合わせて直す。
- 未確認の前提: GitHubがホストするWindowsのランナーで、`SendInput`が全画面のウィンドウに届くかは確かめていない(スパイクの自己テストは、ウィンドウとサーフェスを作れることだけを確かめた)。最初のPRのCIで確かめ、届かない場合は代わりの方法(ウィンドウへのメッセージの送信など)を、メンテナーに確認してから採る。

## 作業

1. スモークテストのcrateとテスト(TDD。ログの読み取りなど、Windowsに依存しない部分は単体テストにする)。
2. CIのWindowsのジョブへの組み込み(ワークフローの変更。要承認)。
3. リリースのワークフローへの組み込み(x64とarm64。要承認)と、`prepare_release.py`のarm64の節。
4. v0.1.1の準備: まず、版を`0.1.1-alpha.1`にし、CHANGELOGに`## v0.1.1-alpha.1 (日付)`の節を加えるPRを作る(リリースのワークフローの検査が求めるため)。マージしたら、プレリリース`v0.1.1-alpha.1`のタグ(メンテナーが付ける)でリリースのワークフローを通し、arm64のスモークテストと、D-31のジョブ構成を確かめる(D-4)。その成果物を候補として、メンテナーに実機での確認を依頼する(確認の項目はD-30の完了条件のとおり)。結果を計画・スパイクの結果・説明書に反映し、版を上げ、CHANGELOGを書く。
5. タグとリリース(タグはメンテナーが付ける)。所要時間を記録する。

## 決定

| ID | 内容 |
| --- | --- |
| D-1 | テストの道具は、ワークスペースのRustのcrate(`crates/smoke`)で書く(メンテナーの判断)。PowerShellのスクリプトより、ログの読み取りなどを単体テストにしやすく、製品と同じ依存で書けるため |
| D-2 | PRごとのCIのWindowsのジョブ(x64)と、リリースのワークフローのビルドのジョブ(x64とarm64)の両方で実行する(メンテナーの判断)。ワークフローへの組み込みは、計画の合意をもって承認とした |
| D-3 | F-01の終了の速さは、N-02の0.2秒で判定する(メンテナーの判断)。ランナーで不安定なら見直す |
| D-4 | arm64のスモークテストは、PRのCIでは動かない(CIのWindowsのジョブはx64だけ)。正式なタグで初めて動かすと、失敗したときに新しい版のタグが要るため、先にプレリリース`v0.1.1-alpha.1`のタグでリリースのワークフローを通す(メンテナーの判断) |
| D-5 | N-02は「入力から画面が消えるまで」なので、F-01では、入力からそのプロセスの表示中のトップレベルのウィンドウがなくなるまでを0.2秒で判定する。プロセスの終了(GPUの資源の解放などを含む)は、2秒の上限で別に確かめて記録する(メンテナーの判断) |
| D-6 | 製品の全画面のウィンドウは、終了を決めたあとも、GPUの解放が済んでwinitのイベントループが終わるまで破棄されず、画面に残っていた(winit 0.30.13のソースで確かめた。`Window`のDropは破棄のメッセージを送るだけで、ループを抜けたあとは処理されない)。終了を決めたときに、すべての全画面のウィンドウをすぐ非表示にするよう、製品を直す(メンテナーの判断。v0.1.1の修正) |
