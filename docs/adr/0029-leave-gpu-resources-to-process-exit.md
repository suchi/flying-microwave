# ADR-0029: 終了するときは、描画先とGPUを破棄せずにプロセスの終わりに任せる

- ステータス: 採用
- 日付: 2026-11-22

## 背景

スモークテストの終了の時間が、上限(2秒)の近くにあり、ときどき上限を超えて失敗していた([incident 0033](../incidents/0033-exit-time-near-limit-unnoticed.md)、[0035](../incidents/0035-key-to-screen-gone-failed-after-adr-0028.md))。終了の後始末の各段の時間をログに書いたところ(計画0005のD-24の(6)、D-33)、終了までの時間のほとんどが、描画先(wgpuの`Surface`)の破棄にかかっていた。値はincident 0033の「その後の再発」の表のとおりで、プレビュー(F-02)で1574.0msと2008.9ms、スクリーンセーバー(F-01)で616.9〜1060.1msだった。2008.9msの回は、F-02が上限を超えて失敗した(2026-11-22のmainのCI、実行44948887108)。

描画先の破棄では、wgpu-coreの`Surface`の`Drop`(`wgpu-core-30.0.1/src/instance.rs`の720〜729行)が、wgpu-halの`unconfigure`を呼ぶ。DX12の`unconfigure`(`wgpu-hal-30.0.1/src/dx12/mod.rs`の1710〜1724行)は、表示のキュー(present queue)の仕事がすべて終わるまで、上限なしで待つ(`device.rs`の262〜277行の`wait_for_present_queue_idle`)。表示のキューの仕事が、なぜ1〜2秒終わらないかは、確かめていない(推測と根拠はincident 0033の「その後の再発」)。

画面は、終了を決めた直後に消えている(スクリーンセーバーは窓を隠し、プレビューの窓は親の窓と一緒に消える)。後始末の待ちは、利用者には見えず、プロセスが残る時間だけを延ばしている。

## 決定

スクリーンセーバー(`/s`)とプレビュー(`/p`)は、終了するとき(winitの`exiting`)、窓ごとの要約の行と後始末の行を書いたら、描画先、GPU(デバイスとキュー)、wgpuのインスタンス、winitの窓を破棄せずに残し、プロセスの終わりにOSが回収するのに任せる(2026-11-22のメンテナーの判断。計画0005のD-34)。

待ちの深い原因(表示のキューの仕事が終わらない理由)は分からないままの回避策である。AGENTS.mdの「進め方」のとおり、調べた経緯と理由をこのADRとincident 0033に記録する。

検討した選択肢と採用しなかった理由:

- 先に実験で原因を確かめてから直す: 原因に合った直し方を選べるが、そのあいだmainのCIが失敗したままになり、ほかの変更をマージできない。原因は、このADRのあとでも調べられる(下の「将来の見直し条件」)。
- スモークテストの上限を延ばす: 製品は変わらず、プロセスは終了のあとも数秒GPUを持ち続ける。上限は計画0003のD-5の要件で、待ちが延びればまた上限の近くに来る。

## 結果

- メリット: 終了の時間から、描画先の破棄の待ち(1〜2秒)がなくなる見込みである。見た目は変わらない。
- デメリット・受け入れたトレードオフ:
  - wgpuとドライバーの、順序立てた後始末を飛ばす。資源の解放は、プロセスの終わりにOSが行う。
  - プロセスの終わり(DLLの切り離しなど)で、別の待ちが起きるかは確かめていない。このADRを入れたPRのCIで、スモークテストの終了の時間(`timing:`の行)を、それまでの実行と並べて確かめる。
  - 後始末の各段の時間(描画先、GPU、インスタンス)は、測るものがなくなる。後始末の行は、要約の行を書くまでの時間と、破棄を残したことを書く。
- 将来の見直し条件: 終了のあとに資源の解放が必要になったとき(同じプロセスで描画をやり直す機能など)。プロセスの終わりで待ちが起きると分かったとき。表示のキューの仕事が終わらない原因が分かり、wgpuかDXGIの使い方で直せると分かったとき。
