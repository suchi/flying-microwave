# ADR-0015: CIでビルドをキャッシュし、PRでのスパイクのビルドをx64に限る

- ステータス: 採用
- 日付: 2026-10-31

## 背景

Phase 0のPR(#4)では、スパイクのビルド(`.github/workflows/spikes.yml`)がプッシュのたびに最初から行われ、待ち時間の大部分を占めた。最後の実行では、x64のジョブが約9分、arm64のジョブが約11分かかった(どちらも同じ`windows-2025`のランナーで、依存crateのwinit・wgpu・eframeなどのコンパイルが大半を占める)。ワークスペースのCI(`ci.yml`)は、依存crateがまだないため1分以内に終わる。ただし、Phase 1でGUI関連のcrateを加えると、同じ程度の時間がかかる見込みである。

レビュー指摘の修正を何回かに分けてプッシュしたため、この待ち時間が回数分たまった。メンテナーが2026-10-31に、次の3点で短縮する方針を決定した。

## 決定

1. ビルドのキャッシュ: `ci.yml`と`spikes.yml`のRustのビルドに、[Swatinem/rust-cache](https://github.com/Swatinem/rust-cache)を使う。
   - 他のActionsと同じく、コミットのSHAで固定する(v2.9.3、`d1527c8f67ef9af357290475d4af4b0fab8f12e0`)。更新はDependabotで行い、`cooldown`を適用する。
   - ツールチェーンの導入のあとに置く(rustcのバージョンがキャッシュのキーに含まれるため)。
   - 既定のキーには、ジョブのID、rustcのバージョン、`Cargo.lock`・`Cargo.toml`・`rust-toolchain.toml`・`.cargo/config.toml`のハッシュが含まれる。マトリクスのターゲットは含まれないため、`key`にターゲットを加えて、x64とarm64のキャッシュを分ける。
   - スパイクはワークスペースの外にあるため、`workspaces`で各スパイクのディレクトリと`target`を指定する。
2. スパイクのビルドの対象: PRではx64だけをビルドする。arm64は、ワークフローを手動で実行(`workflow_dispatch`)したときに、x64とあわせてビルドする。arm64のビルドが必要になるのは、arm64の端末で確かめるときだけだからである。
3. プッシュの単位: レビュー指摘の修正は論理変更ごとにコミットし、検証を終えてからまとめて1回でプッシュする(AGENTS.mdとレビュー手順に記す)。

### キャッシュの安全性

GitHubの公式ドキュメント(Dependency caching reference。調査環境から`docs.github.com`には接続できなかったため、同じ内容のソースである`github/docs`リポジトリの原文で確認した)によると、次のとおりである。

- PRの実行で作られたキャッシュは、そのPRのマージ用の参照(`refs/pull/.../merge`)に属し、ベースブランチや他のPRからは復元できない。
- デフォルトブランチのキャッシュを作成・上書きできるのは、`push`・`workflow_dispatch`・`schedule`などの信頼できるトリガーの実行だけである。`pull_request_target`などの外部から起動できるトリガーの実行は、読み取りしかできない。

本リポジトリのワークフローは`pull_request`・`push`(`main`)・`workflow_dispatch`だけで起動するため、フォークのPRなど外部の実行が、`main`のキャッシュを汚染する経路はない。そのうえで、将来のリリースのワークフローではキャッシュを復元せず、毎回最初からビルドする(配布物に、検証していないキャッシュの内容が入らないようにするため)。

### 検討した選択肢と採用しなかった理由

- GitHub公式の`actions/cache`を直接使う: 第三者のActionを増やさずに済む。ただし、キャッシュのキーの組み立てと、使われなくなった依存crateやワークスペースのcrateの成果物の掃除を自前で書く必要がある。掃除しないと、キャッシュが肥大化する。
- sccache: コンパイラの単位でキャッシュでき効果は大きいが、導入と保守の手間が増える。現在の規模には過剰である。
- スパイクを手動実行だけにする: 最も速いが、スパイクを直したPRで、Windowsでのビルドが通るかを自動で確かめられなくなる。
- キャッシュを使わない: 依存crateのコンパイルに毎回約9〜11分かかり、Phase 1以降はワークスペースのCIも同じになる。

## 結果

- メリット: 同じPRの2回目以降のプッシュでは、依存crateのコンパイルが省ける。`main`へのプッシュで作られたワークスペースのキャッシュは、新しいPRでも使える。PRのスパイクのビルドでは、arm64のランナーの時間がかからない。
- デメリット・受け入れたトレードオフ: 第三者のActionが1つ増える(SHAでの固定とDependabotの`cooldown`で対処する)。キャッシュの保存と復元に時間がかかる(数十秒程度と見込む)。スパイクのワークフローは`main`で自動実行されないため、スパイクを変更する新しいPRの最初の実行では、キャッシュが効かない。PRではarm64向けのビルドが通るかを確かめないため、arm64でだけ失敗する変更は、手動実行するまで見つからない(製品のコードは、`ci.yml`で両方のターゲットを確かめ続ける)。
- 将来の見直し条件: キャッシュの合計が上限(既定でリポジトリごとに10GB)に近づいたとき。キャッシュが効かない、または壊れたキャッシュでビルドが失敗する事象が起きたとき。リリースのワークフローを作るとき(キャッシュを使わない設定を、公式ドキュメントで確かめて組み込む)。
