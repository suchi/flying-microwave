# ADR-0015: CIでビルドをキャッシュし、PRでのスパイクのビルドをx64に限る

- ステータス: 採用
- 日付: 2026-10-31

## 背景

Phase 0のPR(#4)では、スパイクのビルド(`.github/workflows/spikes.yml`)がプッシュのたびに最初から行われ、待ち時間の大部分を占めた。

- 所要時間: 最後の実行では、x64のジョブが約9分、arm64のジョブが約11分かかった。どちらも同じ`windows-2025`のランナーで、依存crateのwinit・wgpu・eframeなどのコンパイルが大半を占める。
- 起動の条件: PRでのパスの絞り込みは、そのプッシュの差分ではなく、PR全体の差分(ベースブランチとの分岐点からの差分)で判定される(GitHubの公式ドキュメントの原文で確認)。そのため、`spikes/`を含むPRでは、文書だけを直したプッシュでもスパイクのビルドが走る。
- ワークスペースのCI(`ci.yml`): 依存crateがまだないため、1分以内に終わる。ただし、Phase 1でGUI関連のcrateを加えると、同じ程度の時間がかかる見込みである。

レビュー指摘の修正を何回かに分けてプッシュしたため、この待ち時間が回数分たまった。メンテナーが2026-10-31に、次の3点で短縮する方針を決定した。

## 決定

1. ビルドのキャッシュ: `ci.yml`のすべてのジョブと、`spikes.yml`のPRでの実行に、[Swatinem/rust-cache](https://github.com/Swatinem/rust-cache)を使う。
   - 他のActionsと同じく、コミットのSHAで固定する(v2.9.3、`d1527c8f67ef9af357290475d4af4b0fab8f12e0`)。更新はDependabotで行い、`cooldown`を適用する。
   - ツールチェーンの導入のあとに置く(rustcのバージョンがキャッシュのキーに含まれるため)。
   - 既定のキーに含まれるもの: ジョブのID、rustcのバージョン、ルートの`rust-toolchain.toml`と`.cargo/config.toml`のハッシュ、`Cargo.lock`、メンバーのcrateの`Cargo.toml`(`package.version`とpath依存を正規化したうえで全体。`[profile]`も含む)。rust-cacheのソース(`src/config.ts`)で確認した。
   - 既定のキーに含まれないもの: マトリクスのターゲットと、メンバーではないワークスペースのルートの仮想マニフェスト(本リポジトリのルートの`Cargo.toml`。`[profile]`や`[workspace.dependencies]`はここに書く)。これらが変わってもキーが変わらないと、キャッシュが更新されないまま効かなくなる。そこで、`key`にターゲットを加え、`ci.yml`ではルートの`Cargo.toml`のハッシュも加える。各スパイクの`Cargo.toml`は、そのスパイク自身がワークスペースのルートで唯一のメンバーのため、既定のキーに含まれる。
   - `key`に加えた値は、`Cargo.lock`を含まない復元用のキーにも入る。そのため、`ci.yml`でルートの`Cargo.toml`を変えると、その次の実行では古いキャッシュからの部分的な復元もされず、最初からビルドする。
   - スパイクはワークスペースの外にあるため、`workspaces`で各スパイクのディレクトリと`target`を指定する。
   - `ci.yml`には、依存crateがまだないいまの時点で入れる。キャッシュの導入はメンテナーの承認を得ている。セキュリティ設定の変更をこのPRにまとめれば、依存crateを加えるPhase 1のPRのレビューを、製品のコードに集中させられるからである。
2. スパイクのビルドの対象と成果物:
   - PR: x64だけを、キャッシュを使ってビルドし、ビルドが通るかと自己テストだけを確かめる。成果物は公開しない。
   - 手動実行(`workflow_dispatch`): x64とarm64の両方を、キャッシュを使わずに最初からビルドし、成果物を公開する。メンテナーが実機で実行するのは、この成果物だけとする。
   - arm64のビルドが必要になるのは、arm64の端末で確かめるときだけである。成果物を実機で実行する頻度は低く、そのたびに手動で実行する手間は小さい。
3. プッシュの単位: レビュー指摘の修正は論理変更ごとにコミットし、検証を終えてからまとめて1回でプッシュする(AGENTS.md、レビュー手順、`/babysit-pr`に記す)。

### キャッシュの安全性

GitHubの公式ドキュメント(Dependency caching reference)で確かめた。調査環境から`docs.github.com`には接続できなかったため、同じ内容のソースである`github/docs`リポジトリの原文を読んだ。

- PRの実行で作られたキャッシュは、そのPRのマージ用の参照(`refs/pull/.../merge`)に属し、ベースブランチや他のPRからは復元できない。
- デフォルトブランチのキャッシュを作成・上書きできるのは、`push`・`workflow_dispatch`・`schedule`などの信頼できるトリガーの実行だけである。`pull_request_target`などの外部から起動できるトリガーの実行は、読み取りしかできない。
- 本リポジトリのワークフローは`pull_request`・`push`(`main`)・`workflow_dispatch`だけで起動する。そのため、フォークのPRなど外部の実行が、`main`のキャッシュを汚染する経路はない。

残るリスク:

- キャッシュの内容は署名も検証もされない(同じ文書の「Best practices」)。
- あるスコープ(PRのマージ用の参照や`main`)で一度でも実行されたコードの成果物は、キャッシュに残りうる。たとえば、悪意のある依存crateのビルドスクリプトが一度動いた場合である。
- その変更をあとで取り消しても、rust-cacheは`Cargo.lock`を含まない復元用のキーで、同じスコープの古いキャッシュを復元する。そのため、取り消したあとのビルドにも、その成果物が入りうる。

これに対して、次のようにする。

- 人が実行する成果物は、キャッシュを使わずに最初からビルドする。スパイクの手動実行の成果物と、将来のリリースのワークフローの配布物がこれにあたる(計画の9章)。
- PRと`main`のCIのキャッシュは、ビルドとテストの結果を早く得るためだけに使う。
- 汚染を疑ったとき(悪意のある依存crateを取り込んだと分かったときなど)は、GitHubのActionsの「Caches」の画面でキャッシュをすべて削除するか、`prefix-key`を変えて、既存のキャッシュを使わないようにする。

### 検討した選択肢と採用しなかった理由

- GitHub公式の`actions/cache`を直接使う: 第三者のActionを増やさずに済む。ただし、キャッシュのキーの組み立てと、使われなくなった依存crateやワークスペースのcrateの成果物の掃除を自前で書く必要がある。掃除しないと、キャッシュが肥大化する。
- sccache: コンパイラの単位でキャッシュでき効果は大きいが、導入と保守の手間が増える。現在の規模には過剰である。
- スパイクを手動実行だけにする: 最も速いが、スパイクを直したPRで、Windowsでのビルドが通るかを自動で確かめられなくなる。
- PRの成果物も公開する(キャッシュを使ってビルドしたもの): メンテナーが手動で実行する手間は省けるが、上記の残るリスクがある成果物を実機で実行することになる。
- キャッシュを使わない: 依存crateのコンパイルに毎回約9〜11分かかり、Phase 1以降はワークスペースのCIも同じになる。

## 結果

- メリット:
  - 同じPRの2回目以降のプッシュでは、依存crateのコンパイルが省ける。
  - `main`へのプッシュで作られたワークスペースのキャッシュは、新しいPRでも使える。
  - PRのスパイクのビルドでは、arm64のランナーの時間がかからない。
- デメリット・受け入れたトレードオフ:
  - 第三者のActionが1つ増える。SHAでの固定とDependabotの`cooldown`で対処する。
  - キャッシュの保存と復元に時間がかかる。数十秒程度と見込む。
  - スパイクのワークフローは`main`で自動では実行されない。そのため、スパイクを変更する新しいPRの最初の実行では、キャッシュが効かない。
  - スパイクの成果物を得るには手動で実行する必要があり、最初からビルドするため約10分かかる。
  - PRではarm64向けのビルドが通るかを確かめない。そのため、arm64でだけ失敗する変更は、手動で実行するまで見つからない。製品のコードは、`ci.yml`で両方のターゲットを確かめ続ける。
  - `ci.yml`のキーにルートの`Cargo.toml`のハッシュを加えたため、それを変えると、その次の実行ではキャッシュが効かない。
- 将来の見直し条件:
  - キャッシュの合計が上限(既定でリポジトリごとに10GB)に近づいたとき。
  - キャッシュが効かない、または壊れたキャッシュでビルドが失敗する事象が起きたとき。
  - リリースのワークフローを作るとき。キャッシュを使わない設定を、公式ドキュメントで確かめて組み込む。
