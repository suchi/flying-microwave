# ADR-0022: 当面はx64版だけを配布し、arm64には対応しない

- ステータス: 採用
- 日付: 2026-11-03
- 置き換え: [ADR-0016: arm64-without-guarantee](0016-arm64-without-guarantee.md) を非推奨とし、本ADRが最新の決定となる

## 背景

[ADR-0016](0016-arm64-without-guarantee.md)では、arm64版を動作を保証せずに配布し、リリースのワークフローで、GitHubがホストするarm64のWindowsランナー(`windows-11-arm`)で自動の確認を行うことにした。v0.1.0は、この決定のとおりarm64版も配布した。

v0.1.1の準備で、次のことが起きた([計画0003](../plans/0003-v0.1.1-smoke-test.md)のD-7・D-9、[incidents 0013](../incidents/0013-arm64-smoke-test-only-at-release.md))。

- プレリリース`v0.1.1-alpha.1`と`v0.1.1-alpha.2`のリリースのワークフローで、arm64のスモークテストのF-01(全画面をキーやクリックで終わらせる確認)が2回続けて失敗し、下書きが作られなかった。x64では成功した。
- `windows-11-arm`のランナーでは、製品の前面化(`SetForegroundWindow`)が拒まれ、前面には別のプロセスの`Windows.UI.Core.CoreWindow`のウィンドウがあった。キーもクリックも製品に届かない状態で、原因は確かめていない。
- arm64のランナーでGUIを伴う処理を試せるのは、リリースのワークフロー(タグ)だけで、修正をタグを付けずに試す手段がない。
- メンテナーはarm64の実機を持っておらず、実機で確かめる手段もない。

これはADR-0016の見直しの条件(リリースのときのarm64のビルドや確認がたびたび失敗する、`windows-11-arm`でスモークテストが動かない)に当たる。メンテナーが2026-11-03に、arm64には当面対応しないと決めた。

## 決定

対象環境は、Windows 11のx64だけとする。arm64には当面対応せず、arm64版を配布しない。

- 配布物: x64のzip(`FlyingMicrowave-<version>-windows-x64.zip`)と`SHA256SUMS.txt`だけとする。v0.1.1(プレリリースの`v0.1.1-alpha.3`)から適用する。v0.1.0で配布したarm64版のzipは、そのまま残す(公開済みのリリースは変えない)。
- リリースのワークフロー(`release.yml`): ビルドのジョブは、x64(`windows-2025`)だけとする。ライセンスの表示(`about.toml`)とSBOMも、x64のターゲットだけを対象にする。リリースノートの、arm64版についての決まった節(`scripts/prepare_release.py`)はなくす。
- CI(`ci.yml`): Windowsのジョブはこれまでどおりx64だけとする。Linuxのジョブの、`aarch64-pc-windows-msvc`向けの型検査(`cargo check`)は続ける。数十秒で終わり、arm64でだけコンパイルが通らない変更を早く見つけられ、対応を再開するときの手間を小さくできるためである。ただし、これはarm64に対応していることを意味しない。
- 今後の扱い: arm64への対応は、Issue #44で扱う。v1.0.0のあと、ほかの改善や修正と並べて優先度を決め、対応するかを判断する。メンテナーがarm64の実機を持っていないため、先延ばしになる可能性がある。v1.0.0の完了条件にはしない。
- 利用者向けの文書: `packaging/windows/README.md`の動作環境に、arm64版は提供していないことを書く。CHANGELOGには、v0.1.1からarm64版の配布をやめたことを書く。arm64のWindowsでは、x64版がエミュレーションで動く可能性があるが、確かめていないため、動くとは書かない。
- そのほかの項目はADR-0016のまま変えない: Windows 10は動作を保証しない、32ビットはサポートしない、追加のランタイムは必要としない(VC++ランタイムを静的リンクする。[ADR-0001](0001-use-rust.md))。スパイクのビルドはx64だけ([ADR-0017](0017-ci-build-cache-and-x64-spike-builds.md))。
- 当てはまらなくなる記述: 採用中のADRのうち、[ADR-0017](0017-ci-build-cache-and-x64-spike-builds.md)の結果の「arm64のビルドはリリースのときに行う」と、[ADR-0021](0021-spdx-sbom-with-own-script.md)の背景の「リリースはx64とarm64のzipに分かれる」は、本ADRにより当てはまらなくなる。SBOMは、x64のzipの分だけを作る。

### 検討した選択肢と採用しなかった理由

- arm64版の配布を続け、arm64ではF-01の入力から先を飛ばす(一度決めてから改めた案。[incidents 0013](../incidents/0013-arm64-smoke-test-only-at-release.md)の対策1): 配布は続けられる。しかし、確かめられない範囲がさらに広がり、arm64の確認がタグでしか試せない状態も変わらない。arm64の利用者がいるかも分からないため、配布と確認の手間に見合わない。
- CIにarm64の手動実行のジョブを加え、原因を調べてから配布を続ける: 確認を元の範囲に戻せる可能性がある。しかし、原因の調査と、実機のない環境での確認の手間がかかり、v0.1.1以降の作業(設定画面など)が遅れる。v1.0.0のあとに対応を決めるときに、改めて検討する(Issue #44)。

## 結果

- メリット:
  - リリースのワークフローが、arm64のランナーの環境の問題で止まらなくなる。
  - リリースのワークフローの所要時間とランナーの使用量が減る。
  - 確かめられない配布物を出さずに済む。
- デメリット・受け入れたトレードオフ:
  - arm64のWindowsの利用者は、x64版をエミュレーションで動かすしかない。動くかは確かめていない。
  - v0.1.0にはarm64版があり、v0.1.1からはない。利用者向けのCHANGELOGに書く。
  - arm64でだけ起きる問題のうち、型検査で見つからないもの(リンクの失敗、実行時の不具合)は、対応を再開するまで分からない。
- 将来の見直し条件:
  - v1.0.0のあとで、Issue #44の優先度を決めるとき。
  - arm64の実機での確認の手段が得られたとき。
  - arm64のWindowsでの利用の要望があったとき。
