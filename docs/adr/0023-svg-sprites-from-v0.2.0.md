# ADR-0023: 素材をSVGで作り、v0.2.0の試作版からresvgでラスタライズして描く

- ステータス: ~~採用~~ 非推奨 → [ADR-0026: render-microwaves-as-3d-meshes](0026-render-microwaves-as-3d-meshes.md) に置き換え
- 日付: 2026-11-03
- 置き換え: [ADR-0008: svg-assets-with-resvg](0008-svg-assets-with-resvg.md) を非推奨とし、本ADRが最新の決定となる

> 非推奨理由: 電子レンジが3Dの任意の方向に回転しながら飛ぶ表現(計画0005のD-2)を描くため、2Dのスプライトと平行四辺形の変形をやめ、箱のメッシュと透視投影で描くことにした(2026-11-11)。SVGで自作してresvgでラスタライズする点は、ADR-0026に引き継いだ。製品の描画は、計画0005の作業5・6で実装するまで、本ADRの方式のままである。

## 背景

[ADR-0008](0008-svg-assets-with-resvg.md)では、素材をSVGで作り、resvgでラスタライズすることにし、導入はPhase 3から、Phase 1・2は仮素材(単純な図形)と決めた。

2026-11-03に、メンテナーが、立体的な電子レンジの絵を早く見たいと望み、本番の絵をv0.2.0の試作版に前倒しした([計画0004](../plans/0004-v0.2.0-settings.md)のD-6)。resvgの追加は、同じ日にメンテナーが承認した(計画0004のD-7)。実装で、ADR-0008に書いたアニメーションの方法(横方向の拡大縮小)と、依存の使い方の詳細も決まった。

## 決定

素材をSVGで作り、起動時にresvgでラスタライズして描画に使う(ADR-0008と同じ)。次の点を改める。

- 導入時期: `v0.2.0-alpha.1`から。仮素材(四角の組み合わせ)は使わなくなる。
- 依存: `resvg` `=0.49.0`を、既定の機能を切って使う(文字の描画と、埋め込みの画像の読み込みを使わない)。素材には`<text>`、`<image>`、外部ファイルへの参照を使わない。LEDの時計は、四角で描いた7セグメント風の表示にする。resvgが使う`tiny-skia`のライセンス(BSD-3-Clause)は、ライセンスの表示に加える(計画0004のD-7)。
- 描画: wgpuのレンダーパイプラインで、テクスチャを貼った四角形をインスタンスごとの変換で描く(乗算済みのアルファで合成する)。シェーダーはWGSLで書き、wgpuの`wgsl`の機能を有効にする。この機能は、wgpu-coreがWindows向けにもともと組み込むWGSLの読み込み(nagaの`wgsl-in`)を、アプリから使えるようにするだけで、新しいcrateは増えない(`Cargo.lock`は変わらない)。
- アトラス: 素材は、サーフェスの設定時と、スプライトの画素の大きさが変わったときに、画面の大きさに合った解像度でラスタライズし、1枚のテクスチャアトラスにまとめる。毎フレームのラスタライズはしない。
- アニメーション: ドアは本体と別の素材にし、左の縦の辺(ヒンジ)を固定した平行四辺形に変形して開閉させる(斜め上から見た平行投影では、回るドアは平行四辺形になり、アフィン変換で表せる)。開く角度は0°〜70°にする(この投影では約76°でドアの外側の面が見る人から背を向けるため、裏側は描かない)。本体の色は4種類(silver、graphite、white、mint)にし、飛ぶときは-8°傾ける。
- 記録: 素材ごとの作者・ライセンス・出典を`assets/sprites/README.md`に記録する(ADR-0008と同じ)。

### 検討した選択肢と採用しなかった理由

- PNGのスプライトシート(ADR-0008で検討した): 解像度ごとに素材が要り、差分をテキストで確かめられない。
- 開発環境でSVGを画像にして実行ファイルに埋め込む(2026-11-03にメンテナーに示した): 実行時の依存は増えないが、絵を直すたびに画像も作り直す必要があり、解像度ごとの鮮明さも失う。
- ドアを横方向の拡大縮小だけで動かす(ADR-0008の案): 実装は単純だが、開いたドアが前に張り出す立体感が出ない。平行四辺形への変形は、同じアフィン変換で表せるため、手間はほとんど変わらない。

## 結果

- メリット:
  - 解像度に依存せず、どのモニタ・DPIでも鮮明に描ける。
  - 絵の直しは、SVGを書き換えるだけで済む。
  - 毎フレームの処理は、インスタンスのデータの書き込みと1回の描画だけである。
- デメリット・受け入れたトレードオフ:
  - 依存が26個のcrateだけ増え、ライセンスの表示とSBOMの対象も増える。`tiny-skia`の既定の機能(PNGの出力)は、resvgから切れないため、`png`などもリンクの対象になる。
  - アトラスはウィンドウごとに作るので、複数のモニタではモニタの数だけラスタライズする(4Kで約8ミリ秒。Linuxのリリースビルドで測った。Windowsでは測っていない)。
  - ミップマップを使わないため、ドアを強く縮めたときに、わずかにちらつく可能性がある(推測)。
  - Windowsの実機での描画と、DX12でのシェーダーのコンパイルは、試作版の実機での確認とCIで確かめる。
- 将来の見直し条件:
  - 必要な表現がresvgで描けないとき。
  - resvgの保守状況やライセンスに問題が生じたとき。
  - 起動時のラスタライズが、起動の速さ(計画0001のN-01)を満たせないとき。
