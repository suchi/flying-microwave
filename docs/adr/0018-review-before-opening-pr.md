# ADR-0018: 敵対的レビューをPRを作る前に行う

- ステータス: 採用
- 日付: 2026-11-01

## 背景

これまでの手順は、PRを作ってから、敵対的レビューを依頼する順だった(AGENTS.md、レビュー手順)。[ADR-0017](0017-ci-build-cache-and-x64-spike-builds.md)の決定3で、レビューの指摘の修正はまとめて1回でプッシュすることにしていた。それでも、PRを作ったときと、レビューの指摘を直したあとの2回、CIが走る構造は残っていた。

CIのワークフローの起動の条件は、次のとおりである(2026-11-01に`.github/workflows/`の原文で確かめた)。

- `ci.yml`: `pull_request`と、`main`への`push`。
- `spikes.yml`: `pull_request`(`spikes/`などのパスの条件付き)と、手動実行(`workflow_dispatch`)。

つまり、PRのないフィーチャーブランチにプッシュしても、CIは走らない。CIの回数を決めるのは、PRを作ったあとのプッシュの回数である。

2026-11-01、PR #16で、手順書の1文だけの修正をプッシュし、Windowsのランナーでスパイクのビルドがもう一度走った。なぜなぜ分析で、PRを作ってからレビューする順番が真因だと分かった([異常の記録0002](../incidents/0002-extra-ci-run-after-review.md))。メンテナーの方針は、GitHub Actionsは必要な実行は惜しまず、不要な実行は最小限にする、である。

## 決定

敵対的レビューを、PRを作る前に行う。プッシュは、作業を残すためにいつ行ってもよい(PRがなければCIは走らない)。

1. フィーチャーブランチで変更をコミットする。作業を失わないよう、プッシュしてよい。
2. PRを作る前に、レビュー用のエージェントを別のworktreeで起動し、ブランチと`main`との差分を渡す。
3. 指摘を検証して、修正をコミットする。再レビューが要る場合(medium以上を修正したとき。1つの変更で最大1回)も、PRを作る前に行う。
4. レビューを終えてから、PRを作る。レビューの結果をPRのまとめコメントに記録する。
5. PRを作ったあとで修正が要る場合(CIの失敗、人間のレビュー、ユーザーの指示)は、修正をまとめて1回でプッシュし(ADR-0017の決定3)、その修正のコミットをまとめコメントに追記する。設計や動作を変える修正は、プッシュの前に、その修正の差分だけを敵対的レビューにかける。これは新しい差分に対する1回のレビューとして数え、再レビューの上限とは別にする。この回でmedium以上を直しても、さらにレビューはせず、修正をまとめコメントに記録する。

[ADR-0014](0014-risk-based-review-depth.md)の「再レビューは1つのPRで最大1回」は、PRを作る前のレビューを含む1つの変更(ブランチ)で最大1回、と読む。PRを作ったあとの修正のレビュー(上の5)は、この再レビューに当たらない。

あわせて、GitHub Actionsの使い方を定める。必要な実行(PRのCI、成果物を作る手動実行)は惜しまない。不要な実行は避ける。手動実行は、成果物が必要なときだけ行う。

### 検討した選択肢と採用しなかった理由

- PRを作ってからレビューする順のまま、文書だけの修正を次の変更まで持ち越す: CIの回数は減る。しかし、レビューで指摘された修正をPRに入れないまま、マージの判断をすることになる。
- レビューが終わるまでプッシュしない: CIは走らないが、プッシュしても走らないので、CIの回数は変わらない。レビューの間に作業環境が失われると、コミットも失われる。
- スパイクのワークフローのパスの条件から、文書(`spikes/**/*.md`)を外す: 文書だけの変更では、スパイクのビルドが走らなくなる。しかし、真因(レビューの順番)は残り、ほかのワークフローでは同じことが起きる。また、ワークフローの変更(セキュリティ設定)になる。
- PRをドラフトで作り、ドラフトの間はCIを走らせない: ワークフローの条件の変更が要る。また、ドラフトの間に、CIで見つかる問題に気づけない。

## 結果

- メリット:
  - レビューで指摘があっても、CIの実行は原則として1回(PRを作ったとき)で済む。
  - PRを作った時点で、レビューの結果をまとめコメントに記録できる。
- デメリット・受け入れたトレードオフ:
  - CIでしか見つからない問題(Windowsでのビルドなど)は、レビューの後に見つかる。その修正のプッシュは避けられない。
  - レビューの間は、PRがないため、GitHubの上でレビューの経過を見られない。
- 将来の見直し条件:
  - PRのないブランチへのプッシュでCIが走るよう、ワークフローの起動の条件を変えるとき。
  - 人間のレビュアーが加わり、PRの上でレビューする必要が生じたとき。
