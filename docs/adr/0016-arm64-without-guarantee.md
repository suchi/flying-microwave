# ADR-0016: arm64版は動作を保証せずに配布し、CIではx64だけをビルドする

- ステータス: ~~採用~~ 非推奨 → [ADR-0022: ship-x64-only-until-v1](0022-ship-x64-only-until-v1.md) に置き換え
- 日付: 2026-11-01
- 置き換え: [ADR-0006: target-windows-11-x64-arm64](0006-target-windows-11-x64-arm64.md) を非推奨とし、本ADRが最新の決定となる

> 非推奨理由: v0.1.1の準備で、`windows-11-arm`のランナーでのarm64のスモークテストが2回続けて失敗し、arm64の実機で確かめる手段もないため、arm64には当面対応せず、arm64版を配布しないことにした(2026-11-03)。

## 背景

[ADR-0006](0006-target-windows-11-x64-arm64.md)では、Windows 11のx64とarm64を対象環境とした。これに沿って、CIはPRと`main`へのプッシュのたびに、Windowsのランナーでx64とarm64の両方をビルドしていた。スパイクの手動実行でも、両方をビルドしていた。

その結果、次の負担が生じた。

- 所要時間: スパイクの手動実行(2026-11-01)では、x64とarm64のジョブがそれぞれ約11分かかった。Phase 1でGUI関連のcrateを加えると、ワークスペースのCIも同じ程度になる見込みである([ADR-0015](0015-ci-build-cache-and-spike-targets.md))。
- ランナーの使用量: 非公開のリポジトリでは、Windowsのランナーが無料枠を多く消費する。
- 確かめられる範囲: メンテナーはarm64の実機を持っていない。CIでarm64をビルドしても、実機で動くかは確かめられない。

メンテナーが2026-11-01に、次の方針を決めた。

- CIでWindows向けにビルドするのはx64だけとする(Linuxのジョブはそのまま)。
- arm64版は、リリースのときにだけビルドし、自動のスモークテストだけを行って、動作を保証せずに配布する。
- リリースのたびに行う(v0.1.0から)。
- スモークテストを`windows-11-arm`で実行できない場合や、スモークテストがまだない場合も、ビルドと依存DLLの確認だけで配布する(レビューで扱いが決まっていないと指摘を受け、同じ日に決めた)。

## 決定

対象環境は、Windows 11のx64とする。arm64版は、動作を保証せずに配布する。

- ビルドターゲット: `x86_64-pc-windows-msvc`と`aarch64-pc-windows-msvc`は、どちらも維持する([ADR-0001](0001-use-rust.md))。配布物はアーキテクチャごとのzipとする(案: `FlyingMicrowave-<version>-windows-x64.zip`、`FlyingMicrowave-<version>-windows-arm64.zip`)。
- x64: 動作を保証する対象である。CIでビルド・テストし、リリースの前にメンテナーが実機で手動テストを行う。
- arm64: 動作を保証しない。
  - リリースのワークフローで、リリースのたびに、キャッシュを使わずにビルドする。
  - GitHubがホストするarm64のWindowsランナー(`windows-11-arm`)で、自動の確認を行う。このランナーは、非公開のリポジトリでも標準のランナーとして使える(GitHubの公式ドキュメント「GitHub-hosted runners reference」で2026-11-01に確かめた)。
  - 自動の確認の内容: 最低限、ビルドが通ることと、依存DLLの確認(CIのx64と同じく、VC++ランタイムに依存しないこと)を行う。Phase 1でx64のスモークテスト(計画のPhase 1の作業14)を作ったら、同じものを`windows-11-arm`でも実行する。ただし、`windows-11-arm`でウィンドウの作成や描画ができるかは確かめていない(未確認)。スモークテストがこのランナーで動かない場合や、スモークテストがまだない場合(x64のスモークテストをPhase 1で作らなかった場合を含む)は、ビルドと依存DLLの確認だけで配布し、そのことをリリースノートに書く。スモークテストが動くようになったら、確認に加える。
  - arm64のビルドか自動の確認が失敗したら、リリースのワークフローを失敗にする。arm64版を黙って省いてリリースすることはしない。
  - 実機での手動テストは行わない。リリースノートと利用者向けのREADMEに、arm64版は動作を保証しないこと、自動の確認だけを行っていることを書く。リリースノートには、そのリリースで行った確認(スモークテストを含むか)も書く。
- CI(`ci.yml`):
  - Windowsのジョブは、x64だけをビルド・テストする。
  - Linuxのジョブでは、arm64向けの型チェック(`cargo check --target aarch64-pc-windows-msvc`)を続ける。キャッシュがあれば数十秒で終わり、arm64でだけコンパイルが通らない変更を、リリースの前に見つけられるためである。
- スパイク(`spikes.yml`): 手動実行でも、x64だけをビルドする([ADR-0017](0017-ci-build-cache-and-x64-spike-builds.md))。
- Windows 10: 動作を保証しない。Windows 10は2025-10-14にサポートが終了している(Microsoftのライフサイクルのページに「Windows 10 will reach end of support on October 14, 2025」とある。[Microsoft Learn][MS-5])。
- 32ビット: サポートしない。
- 追加のランタイム: 必要としない(VC++ランタイムを静的リンクする。[ADR-0001](0001-use-rust.md))。

### 検討した選択肢と採用しなかった理由

- CIで両方のターゲットをビルドし続ける(ADR-0006のまま): arm64でだけ起きるビルドの失敗を早く見つけられる。しかし、Windowsのランナーの時間と使用量が約2倍になる。また、実機で確かめられないため、得られる保証はビルドが通ることだけである。そのビルドの確認は、Linuxでの型チェックと、リリースのときのビルドでおおむね代えられる。
- arm64版を配布しない: 検証と配布の負担はなくなる。しかし、arm64のWindowsの利用者は、x64版をエミュレーションで動かすしかなくなる。ビルドと自動の確認の手間は小さいため、保証なしで配布する。
- arm64版はv1.0.0のときだけ配布する: それまでのリリースでは、arm64の利用者が試せない。また、arm64でだけ起きる問題が、v1.0.0の直前にまとめて見つかるおそれがある。

## 結果

- メリット:
  - PRと`main`のCIで、Windowsのランナーの時間と使用量が約半分になる。
  - スパイクの手動実行の使用量も約半分になる。
  - arm64版も、リリースのたびに配布し続けられる。
- デメリット・受け入れたトレードオフ:
  - arm64でだけ起きる問題のうち、型チェックでは見つからないもの(リンクの失敗、実行時の不具合)は、リリースのときまで見つからない。
  - arm64版は、実機で確かめないまま配布される。利用者には、動作を保証しないことを明記する。
  - `windows-11-arm`のランナーは、x64のランナーとは別のイメージである。リリースのワークフローを作るときに、ツールチェーンとビルドツールが使えるかを確かめる必要がある。
  - `windows-11-arm`でGUIのスモークテストが動かない場合、arm64版の自動の確認は、ビルドと依存DLLの確認だけになる。
- 将来の見直し条件:
  - arm64の実機での動作の確認が得られたとき(保証する対象に加えるかを見直す)。
  - arm64版でだけ起きる不具合の報告が続くとき。
  - リリースのときのarm64のビルドが、たびたび失敗するとき(CIにarm64のビルドを戻すかを見直す)。
  - `windows-11-arm`でスモークテストが動かないと分かったとき。その時点のリリースは、ビルドと依存DLLの確認だけで配布し、そのあとで、スモークテストを動かす方法か、arm64版の配布を続けるかを見直す。
  - Windows 10での利用の要望が多く、動作確認の手段が得られたとき。
  - 32ビット環境のサポート要望が生じたとき。
