# ADR-0013: v0.x系はコード署名せずに配布し、v1.0.0までに再判断する

- ステータス: 採用
- 日付: 2026-10-31

## 背景

署名のない実行ファイルは、WindowsのSmartScreenで警告が出る可能性が高い。さらに、Smart App Controlが強制モード(enforcement mode)の環境では、署名のない不明なコードは既定でブロックされる(「unknown, unsigned code are blocked by default」。[Microsoft Learn「Smart App Control」][MS-6])。評価モード(evaluation mode)ではブロックされない。したがって署名なしの`.scr`は、そのような環境ではまったく動かない可能性が高い([Windowsスクリーンセーバーの仕様調査](../research/windows-screensaver.md#配布に関わるwindowsの保護機能))。

一方で、署名には手段ごとに条件や費用がある。

- SignPath Foundationの無償署名: 条件は[SignPath Foundationの利用規約][SP-1]で確認した。すべての構成要素がOSIの承認ライセンスであること、独自(非OSS)コンポーネントを含まないこと、署名する形で既にリリースされていること、アンインストールの手順または仕組みを提供すること、検証可能な方法でソースからビルドすること、全メンバーの多要素認証、リリースごとの手動承認、コード署名ポリシーの公開などが求められる。加えて「a certain verifiable reputation」が求められるため、新しいプロジェクトは申請が通らない可能性がある。公開リポジトリを前提とする。証明書の発行者表示はSignPath Foundationになる。
- 有料の署名サービス: 費用がかかる。個人での利用資格は未確認である。

実装計画の確認事項D-14として提示され、メンテナーが2026-10-31に決定した。

## 決定

v0.x系のリリースはコード署名せずに配布し、これを既知の制限としてREADMEに明記する。v1.0.0の前(Phase 6)に、署名の方針を再判断する。再判断は、GitHub Issue #2「Decide code signing policy before v1.0.0」で追跡する。

- READMEの記載: SmartScreenの警告、Smart App Controlの強制モードでの動作不可、グループポリシーで固定された環境での制限を、既知の制限として記載する。
- 配布の工夫: 署名の代わりに、zipでの配布(`.scr`単体はメールやブラウザで危険なファイルとして扱われやすいため)、チェックサム、(利用できれば)アーティファクト証明を付ける。
- 手動テスト: Smart App Controlが有効な環境での挙動を記録する(環境がある場合)。

### 検討した選択肢と採用しなかった理由

- SignPath Foundationで早期に署名する: 多くの環境で動くようになる。しかし検証可能な実績が求められ、新しいプロジェクトは申請が通らない可能性がある。公開リポジトリが前提で、署名する形で既にリリースされていることも求められるため、初回のリリースより前には条件を満たせない。
- 有料の署名サービスを使う: 多くの環境で動くようになる。しかし費用がかかり、個人での利用資格は確認できていない。

## 結果

- メリット:
  - 費用と手間がかからず、早い段階からリリースを進められる。
  - SignPath Foundationの条件(公開リポジトリ、検証可能な実績など)が整う時間を確保できる。
- デメリット・受け入れたトレードオフ:
  - Smart App Controlが強制モードの環境では、署名のない`.scr`はまったく動かない可能性が高い。
  - SmartScreenの警告が出る可能性が高く、利用者に不安を与える。
  - 利用者への説明と、README・リリースノートでの注意喚起が必要になる。
- 将来の見直し条件:
  - v1.0.0の前(Phase 6)。GitHub Issue #2で追跡する。
  - リポジトリの公開後、SignPath Foundationの条件を満たせると判断できたとき(v1.0.0を待たずに申請を検討する)。
  - 署名なしによる利用上の不具合の報告が多いとき。
