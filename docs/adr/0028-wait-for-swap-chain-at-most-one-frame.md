# ADR-0028: スワップチェーンの待機オブジェクトを、製品が最大1フレームだけ待ってから描く

- ステータス: 採用
- 日付: 2026-11-14

## 背景

CIのスモークテストの F-01(キーを押してから画面が消えるまで200ms以内)が、ときどき失敗していた([incident 0028](../incidents/0028-smoke-failure-merged-on-a-guess.md))。PR #81で加えた計測で、WARPでは、描く先の画像を受け取る処理(`get_current_texture`)が約1秒止まっていたことが分かった(incident 0028の「その後の確認」の表)。

wgpu 30.0.1のソースで確かめた待ちの仕組み(Cargoが取得したクレートの中のファイル):

- wgpu-coreの`Surface::get_current_texture`は、画像の取得を上限1000msで待つ(`wgpu-core-30.0.1/src/present.rs`の32行目の`FRAME_TIMEOUT_MS`と、177〜178行目)。
- DX12では、画像を返す前に、スワップチェーンの待機オブジェクト(`GetFrameLatencyWaitableObject`)を、この上限まで待つ(`wgpu-hal-30.0.1/src/dx12/mod.rs`の`acquire_texture`。既定は`Dx12UseFrameLatencyWaitableObject::Wait`)。上限に達しても、そのまま画像を返す(同じファイルの`SwapChain::wait`は`Ok(false)`を返し、`acquire_texture`はその値を見ない)。

製品は、描画とキーの処理を同じスレッドのイベントループで行う([ADR-0025](0025-draw-every-window-from-one-place.md)。`crates/app/src/saver.rs`)。そのため、この待ちの最中にキーが届くと、キーの処理が最大で約1秒遅れる。

試しのPR #82で、3つの案をCIにかけた。どれも、結果を記録したあとで打ち消した(incident 0028の「その後の確認」)。

- 案A(表示の方式をMailboxにする): 待ちはなくならず、F-01が失敗した。
- 案B(待機オブジェクトを使わない。`None`): 待ちはなくなったが、終了の処理が止まり、2秒たってもプロセスが終わらなかった。
- 案E(wgpuには待たせず(`DontWait`)、描く前に自分で待ち時間0で確かめ、合図がまだならその回は描かない): 4つの確認がすべて通った。キーから画面が消えるまでは0msだった。ただし、CIのWARPで、最初の2フレームのあと合図が一度も来ず、画面が止まったままだった(要約の行「23 draws attempted, 2 frames, 1 paced, 0 blank, 20 skipped」)。

## 決定

判断していただいたこと(2026-11-14、メンテナーの判断。計画0005のD-20):

1. 案Eを元に直す。wgpuには待たせず、製品が自分で待機オブジェクトを確かめ、合図がまだならその回は描かない。
2. 合図を待つのは最大1フレーム分(フレームレートの上限の間隔とモニターのリフレッシュの間隔の長いほう。60Hzで約17ms)にする。合図が来たらすぐ描き、来なければその回はスキップして、すぐ試し直す。
3. 合図が来ないまま、最後に表示してから1秒(wgpuの上限と同じ)たったら、合図を待たずに描く。

2は、はじめ「待ち時間0で確かめ、1フレーム後に試し直す」としていた。PRを作る前のレビューで、その方式では、描く時刻が合図から0〜1フレーム遅れて揃わず、ときどき2枚を続けて描くため、実機でも動きが毎秒数回1フレーム止まって見える恐れがある、と指摘された(コードからの推論で、実測はしていない)。メンテナーが、最大1フレーム待つ方式に変えた。3は、案Eのままでは合図が来ない環境で画面が止まるため、メンテナーが選んだ。

実装の方式(エージェントの案):

- wgpuのインスタンスを`Dx12UseFrameLatencyWaitableObject::DontWait`で作る(`crates/app/src/render.rs`の`create_instance`)。wgpuは待機オブジェクトを作るが、待たない(`wgpu-types-30.0.1/src/backend.rs`の871〜872行目の`DontWait`の説明。原文は「This is useful if the application wants to wait for the waitable object itself.」)。
- `Target::draw`の始めで、`wgpu::Surface::as_hal::<Dx12>`でwgpu-halのサーフェスを取り出し、`waitable_handle`で得たハンドルを、`WaitForSingleObject`で最大1フレーム分待つ(`Target::swap_chain_signalled`。待ちの長さはミリ秒に切り上げる)。合図があれば、そのカウントを1つ消費する。wgpuの`Wait`の方式が待って消費するのと同じである。待ちの長さは、`FramePacer::frame_period`(`crates/core/src/pacing.rs`)を、全画面(`saver.rs`の`try_draw`)とプレビュー枠(`preview.rs`の`redraw`)が渡す。
- 描くかどうかは`core::pacing::may_draw`で決める。合図があれば描く。合図がなければ、最後に表示した描画(その描画が確かめを通った時刻)から`core::pacing::SIGNAL_WAIT_LIMIT`(1000ms)たつまで、その回を`Skip::NotReady`でスキップし、たったら合図なしで描く。最初の描画は、合図を待ったあとで、合図がなくても描く。
- `NotReady`でスキップしたときは、すぐに試し直す(`saver.rs`の`retry_delay`。プレビュー枠も同じ)。描画の中ですでに1フレーム分待っているため。試し直すまでの間に、イベントループがキーなどのイベントを処理する。ほかの理由のスキップは、これまでどおり50ms後に試し直す。
- 描く先の画像の待ち(要約の行の`longest surface wait`)には、合図の待ちと`get_current_texture`の待ちを合わせた時間を記録する。
- 終了のときの要約の行(`crates/app/src/diag.rs`の`FrameStats::summary`)に、`NotReady`の回数(括弧の中)と、合図なしで表示した回数(`N drawn without signal`)を加える。

wgpuの内部(`as_hal`)と`unsafe`を使う理由: wgpuの公開のAPIには、待機オブジェクトを、上限を決めて待つ手段がない。wgpu自身が、`DontWait`を「アプリが自分で待つ」ための設定として用意し、`waitable_handle`を公開している(`wgpu-hal-30.0.1/src/dx12/mod.rs`の654〜658行目)。`unsafe`の条件は、wgpuの`Surface::as_hal`の説明(ガードを通して資源を破棄しない)と、wgpu-halの`waitable_handle`の説明(スワップチェーンが生きている間だけ有効)である。描く先の作り直しは同じスレッドの`Target::new`、`Target::resize`、`Target::draw`の中だけで行うため、待つ間はハンドルが有効である。

### 検討した選択肢と採用しなかった理由

- 案A(Mailbox): CIで待ちがなくならず、F-01が失敗した。
- 案B(待機オブジェクトを使わない): CIで終了の処理が止まった。
- 案E(待ち時間0で確かめ、合図が来るまで描かない): CIのWARPで画面が止まったままになった。WARPは、ハードウェアのGPUがない環境で使われるため、実機でも同じになりうる。
- 待ち時間0で確かめ、1フレーム後に試し直す: 描く時刻が揃わず、動きがときどき止まって見える恐れがある(上の「決定」の2の経緯)。
- 待ち時間0で確かめ、1msごとに試し直す: 描く時刻のずれは約1msで済むが、イベントループが起きる回数が、毎秒約60回から最大で毎秒約1000回(1秒÷1ms)に増える。CPUの負荷は測っていない。
- 描画を別のスレッドに移す: キーの処理は止まらなくなるが、ウィンドウとサーフェスの扱いを大きく変える。ADR-0025の決定(イベントループの1か所から順に描く)を変えることになるため、採らない。
- wgpuの上限(`FRAME_TIMEOUT_MS`)を短くする: wgpuの定数で、変えられない。

## 結果

- メリット:
  - キーの処理が待たされるのは、最大で1フレーム分(60Hzで約17ms)×モニターの数になる(ウィンドウを順に描くため。60Hzのモニター3台で約51ms)。F-01の上限200msに収まる。
  - 実機のGPUで合図が毎フレーム来るなら、いまの方式と同じく、合図の時刻に描く。
  - 合図が来ない環境でも、いまの方式と同じく1秒に1回は描く。
- デメリット・受け入れたトレードオフ:
  - wgpuの内部のAPI(`as_hal`、`waitable_handle`)と`unsafe`に頼る。wgpuを更新するときに、この部分が変わっていないかを確かめる必要がある。
  - 合図が来ない環境では、1フレーム分の待ちとスキップを繰り返す(60Hzで毎秒約60回の`NotReady`)。待つ間はCPUを使わない。
  - この方式(最大1フレーム待つ)は、PRのCIで初めて確かめる。試しのPR #82で確かめたのは、待ち時間0の案Eである。
- 実機での判定の基準(`v0.3.0-alpha.4`の実機での確認。計画0005の作業10の2): ログの要約の行(`crates/app/src/diag.rs`の`FrameStats::summary`。ウィンドウごとに終了のときに1行)で判定する。
  - 合図が毎フレーム来ている: `drawn without signal`が0か、ごく少ない。`NotReady`は、フレームの数よりずっと少ない。フレームの数は、動いた秒数×リフレッシュレート(上限がそれより低ければ上限)に近い。
  - 合図が来ていない: `drawn without signal`が、動いた秒数とほぼ同じ。`NotReady`は、動いた秒数×リフレッシュレートに近い。
- 将来の見直し条件: wgpuの更新で、上限を決めて待つ手段が公開のAPIに加わったとき、または`as_hal`や`waitable_handle`が変わったとき。実機で合図が来ずに`drawn without signal`が多いとき。描画を別のスレッドに移すとき。
