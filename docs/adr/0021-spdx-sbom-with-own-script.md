# ADR-0021: リリースのSBOMを、SPDX 2.3の形式で、自前のスクリプトで作る

- ステータス: 採用
- 日付: 2026-11-02

## 背景

メンテナーの依頼で、v0.1.0から、リリースの成果物にSBOM(ソフトウェア部品表)を、SPDXの形式で入れることになった。配布物の利用者や、将来の公開のあとに確かめる人が、実行ファイルに組み込まれるcrateと、そのコードを生成する手続き的マクロ(名前、版、ライセンス、出所)を、機械で読める形で知るためである。

リリースはx64とarm64のzipに分かれる([ADR-0016](0016-arm64-without-guarantee.md))。依存のcrateは、ターゲットによって変わりうる。

## 決定

`scripts/make_sbom.py`(Pythonの標準ライブラリだけ)で、SPDX 2.3のJSONを作る。

- 対象: 実行ファイル(`flying-microwave`)と、そのターゲットの`cargo tree -e normal`に出るcrate。`THIRD-PARTY-LICENSES.txt`(cargo-about)と同じ範囲になる(x64とarm64の和が一致することを確かめた)。
  - 範囲をcargo-aboutと同じにする理由: ライセンスの表示とSBOMの対象が食い違わないようにするため(メンテナーの判断)。
  - 手続き的マクロ(thiserror-implなど)とその依存(synなど)は含める。それ自体は実行ファイルにリンクされないが、そのコードを生成する。
  - ビルドスクリプトの依存(embed-resourceなど)と、テストの依存は除く。Rustのツールチェーンも含めない。
  - 有効でない機能の任意の依存は除く。`cargo metadata`の`resolve`は機能の解決を反映せず、使わないcrate(serdeなど)が混ざるため、範囲は`cargo tree`で決める。ライセンスと出所は`cargo metadata --filter-platform <ターゲット>`から取る。
- 各パッケージの情報: 名前、版、宣言されたライセンス(Cargoの`license`。古い`/`の表記は`OR`の式にする。`/`がほかの演算子や括弧と混ざっていれば、意味が1つに決まらないため失敗にする)、crates.ioのダウンロードの場所、`Cargo.lock`のSHA-256、purl(`pkg:cargo/名前@版`)。ワークスペースのcrateは、ダウンロードの場所を`NOASSERTION`にする。結論のライセンスと著作権の表示は`NOASSERTION`にする(調べた結果ではないため)。
- 関係: 文書が実行ファイルを`DESCRIBES`し、依存の辺を`DEPENDS_ON`で表す。
- 作成日時: リリースのコミットの日時(UTC)。同じコミットを作り直しても、同じ文書になる。
- 名前空間: リリースのタグ、アーキテクチャ、コミットのSHAから作る一意のURI。
- 置き場所: リリースのワークフローの検査のジョブ(Ubuntu)で、両方のターゲットについて作り、ワークフローの成果物としてビルドのジョブに渡す。ビルドのジョブは、それを`FlyingMicrowave-<版>-windows-<arch>.spdx.json`としてzipに入れる。zipは`SHA256SUMS.txt`で確かめられる。
  - 検査のジョブで作る理由: スクリプトを、ほかの検査と同じくワークフローのコミットから実行できる(スクリプトのない古いタグも手動実行でリリースできる)。ランナーごとのPythonの違いにも左右されない(arm64のランナーのイメージの文書には、Python 3.13とGitHub CLIが載っている)。
  - 検査のジョブのcargoは、タグのコミットのビルドスクリプトや手続き的マクロを実行しないが、そのcargoの設定(`rustc-wrapper`など)とツールチェーンの指定は使う。タグがmainの上にあることを先に確かめており、ジョブのトークンも読み取りだけなので、受け入れる。
  - ビルドのジョブは、成果物を受け取るために`actions: read`の権限を持つ。受け取りは、依存のコード(ビルドスクリプト、手続き的マクロ)を実行する手順より前に行い、トークンはその手順にだけ渡す。依存のコードは後の手順の環境(`PATH`など)を変えられるため、その前に済ませる。受け取りには、ほかのActionを加えず、ランナーのgh CLIを使う([docs/incidents/0007](../incidents/0007-dependencies-inside-cooldown.md))。

### 検討した選択肢と採用しなかった理由

- cargo-sbom(crate、0.10.0、MIT): SPDXを出力できるが、最後の公開が2025-06で、保守が続いているかが分からない。リリースのワークフローに道具を加えると、公開から7日の検査と版の管理が増える。
- cargo-cyclonedx: CycloneDXの形式で、SPDXではない。
- GitHubの依存グラフのSBOMの書き出し: リポジトリの既定のブランチを対象にし、タグの内容やターゲットごとの依存を表せない。ワークフローのActionの依存も混ざる。

## 結果

- メリット: 新しい依存が増えない。中身(どの依存を含めるか)を自分で決めて、テストで確かめられる。ターゲットごとの依存を正確に表せる。
- デメリット・受け入れたトレードオフ: SPDXの仕様に合うかは、仕様の必須の項目をテストで確かめるだけで、リリースのたびには公式の検証の道具を通さない(作成時に、生成した文書をSPDX 2.3の公式のJSONスキーマで検証し、エラーがないことを確かめた)。ファイル単位の情報(`filesAnalyzed`)や、ライセンスの調査の結果は含まない。
- 将来の見直し条件: 利用者や配布先(wingetなど)が、公式の検証の道具に通ることや、別の形式(CycloneDX)を求めたとき。保守の続いている道具が、ターゲットごとのSBOMを作れるようになったとき。
