# ADR-0021: リリースのSBOMを、SPDX 2.3の形式で、自前のスクリプトで作る

- ステータス: 採用
- 日付: 2026-11-02

## 背景

メンテナーの依頼で、v0.1.0から、リリースの成果物にSBOM(ソフトウェア部品表)を、SPDXの形式で入れることになった。配布物の利用者や、将来の公開のあとに確かめる人が、実行ファイルに含まれるソフトウェア(crateの名前、版、ライセンス、出所)を、機械で読める形で知るためである。

リリースはx64とarm64のzipに分かれる([ADR-0016](0016-arm64-without-guarantee.md))。依存のcrateは、ターゲットによって変わりうる。

## 決定

`scripts/make_sbom.py`(Pythonの標準ライブラリだけ)で、SPDX 2.3のJSONを作る。

- 対象: 実行ファイル(`flying-microwave`)と、それがそのターゲットで通常の依存としてたどるcrate。`cargo metadata --filter-platform <ターゲット>`の解決の結果を使う。ビルド時だけの依存(embed-resourceなど)とテストの依存は、実行ファイルに入らないため除く。
- 各パッケージの情報: 名前、版、宣言されたライセンス(Cargoの`license`。古い`/`の表記は`OR`の式にする)、crates.ioのダウンロードの場所、`Cargo.lock`のSHA-256、purl(`pkg:cargo/名前@版`)。ワークスペースのcrateは、ダウンロードの場所を`NOASSERTION`にする。結論のライセンスと著作権の表示は`NOASSERTION`にする(調べた結果ではないため)。
- 関係: 文書が実行ファイルを`DESCRIBES`し、依存の辺を`DEPENDS_ON`で表す。
- 作成日時: リリースのコミットの日時(UTC)。同じコミットを作り直しても、同じ文書になる。
- 名前空間: リリースのタグ、アーキテクチャ、コミットのSHAから作る一意のURI。
- 置き場所: リリースのワークフローのビルドのジョブで作り、`FlyingMicrowave-<版>-windows-<arch>.spdx.json`としてzipに入れる。zipは`SHA256SUMS.txt`で確かめられる。

### 検討した選択肢と採用しなかった理由

- cargo-sbom(crate、0.10.0、MIT): SPDXを出力できるが、最後の公開が2025-06で、保守が続いているかが分からない。リリースのワークフローに道具を加えると、公開から7日の検査と版の管理が増える。
- cargo-cyclonedx: CycloneDXの形式で、SPDXではない。
- GitHubの依存グラフのSBOMの書き出し: リポジトリの既定のブランチを対象にし、タグの内容やターゲットごとの依存を表せない。ワークフローのActionの依存も混ざる。

## 結果

- メリット: 新しい依存が増えない。中身(どの依存を含めるか)を自分で決めて、テストで確かめられる。ターゲットごとの依存を正確に表せる。
- デメリット・受け入れたトレードオフ: SPDXの仕様に合うかは、仕様の必須の項目をテストで確かめるだけで、公式の検証の道具では確かめていない。ファイル単位の情報(`filesAnalyzed`)や、ライセンスの調査の結果は含まない。
- 将来の見直し条件: 利用者や配布先(wingetなど)が、公式の検証の道具に通ることや、別の形式(CycloneDX)を求めたとき。保守の続いている道具が、ターゲットごとのSBOMを作れるようになったとき。
