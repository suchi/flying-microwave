# ADR-0009: Cargoワークスペースをcoreとappの2つのcrateに分ける

- ステータス: 採用
- 日付: 2026-10-31

## 背景

開発環境(エージェント)はLinuxで、Windowsの画面を伴う動作は確認できない。将来のLinux版・macOS版を妨げない設計にし、シミュレーションや設定の検証などのロジックをLinux上でも単体テストできるようにしたい。

プラットフォームに依存しないロジックの分離は、アーキテクチャの原則A-1、A-2、A-7として整理している([アーキテクチャ](../design/architecture.md#設計原則))。ワークスペースを2つのcrateに分けるか、1つのcrateにするかを比較した。実装計画の確認事項D-16として提示され、メンテナーが2026-10-31に決定した。

## 決定

Cargoワークスペースを、次の2つのcrateに分ける。

- `crates/core`(`flying-microwave-core`): OSやGPUに依存しない純粋なロジック(設定モデルと検証、シミュレーション、テーマ選択、終了判定、乱数生成器など)。
- `crates/app`(`flying-microwave`): 実行ファイル(起動モード、描画、設定画面、設定ファイルの入出力、プラットフォーム固有の処理)。

付随する決定:

- Linuxでのビルド: `core`と`app`のどちらも、Linuxでビルドできる状態を保つ(アーキテクチャのA-7)。Windows固有のコードは`cfg`で分岐する。Windows固有の部分の確認は、WindowsのCIで行う。
- 技術スパイク: `spikes/`に置き、ワークスペースには含めない。製品コードから参照しない。
- 抽象化の保留: プラットフォーム固有のコードは`app`の`platform`モジュールに閉じ込めるが、2つ目のOSに着手するまでtraitなどの抽象化は作らない(A-2、YAGNI)。描画モジュールも、必要になるまで独立crateにしない。

### 検討した選択肢と採用しなかった理由

- 1つのcrate: 構成は単純になる。しかしOSに依存するコードとそうでないコードの分離が崩れやすく、`core`だけを別のOSで再利用・テストすることが難しくなるため採用しなかった。

## 結果

- メリット:
  - `core`をLinux上で単体テストでき、将来のLinux版・macOS版で再利用できる。
  - `core`にOSやGPUのcrateへの依存を持たせないことで、OS依存のコードの混入を防ぎやすい。
  - `cargo test --workspace`でロジックを一括して検証できる。
- デメリット・受け入れたトレードオフ:
  - 構成が少し複雑になる(crate間の公開APIを設計する必要がある)。
  - Windows固有のコードはLinuxではコンパイルされないため、その部分はWindowsのCIでしか検証できない。
- 将来の見直し条件:
  - `app`の中の描画やプラットフォーム固有の処理が大きくなり、独立したcrateに分ける利点が上回ったとき。
  - 2つ目のOSに着手するとき(プラットフォーム固有コードの抽象化を設計する)。
  - 2つのcrateへの分割で、境界のコストが利点を上回ると分かったとき。
