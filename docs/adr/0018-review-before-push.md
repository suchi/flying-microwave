# ADR-0018: 敵対的レビューをプッシュの前に行う

- ステータス: 採用
- 日付: 2026-11-01

## 背景

これまでの手順は、PRを作ってプッシュしてから、敵対的レビューを依頼する順だった(AGENTS.md、レビュー手順)。[ADR-0017](0017-ci-build-cache-and-x64-spike-builds.md)の決定3で、レビューの指摘の修正はまとめて1回でプッシュすることにしていた。それでも、最初のプッシュとレビュー後のプッシュの2回は、構造的に避けられなかった。

2026-11-01、PR #16で、手順書の1文だけの修正を単独でプッシュし、Windowsのランナーでスパイクのビルドがもう一度走った。なぜなぜ分析で、この順番が真因だと分かった([異常の記録0002](../incidents/0002-extra-ci-run-after-review.md))。メンテナーの方針は、GitHub Actionsは必要な実行は惜しまず、不要な実行は最小限にする、である。

## 決定

敵対的レビューを、プッシュの前に、ローカルのコミットを対象に行う。

1. フィーチャーブランチで変更をコミットする。この時点ではプッシュしない。
2. レビュー用のエージェントを別のworktreeで起動し、ローカルのブランチと`main`との差分を渡す。同じリポジトリのworktreeは参照を共有するため、プッシュしていないブランチも読める。
3. 指摘を検証して、修正をコミットする。再レビューが要る場合(medium以上を修正したとき。最大1回)も、プッシュの前に行う。
4. 最初のプッシュとPRの作成を行い、レビューの結果をPRのまとめコメントに記録する。
5. PRを作ったあとで修正が要る場合(CIの失敗、人間のレビュー、メンテナーの指示)も、修正はまとめて1回でプッシュする(ADR-0017の決定3)。

あわせて、GitHub Actionsの使い方を定める。必要な実行(PRのCI、成果物を作る手動実行)は惜しまない。不要な実行は避ける。手動実行は、成果物が必要なときだけ行う。

### 検討した選択肢と採用しなかった理由

- プッシュの後にレビューする順のまま、文書だけの修正を次の変更まで持ち越す: プッシュの回数は減る。しかし、レビューで指摘された修正をPRに入れないまま、マージの判断をすることになる。
- スパイクのワークフローのパスの条件から、文書(`spikes/**/*.md`)を外す: 文書だけの変更では、スパイクのビルドが走らなくなる。しかし、真因(レビューの順番)は残り、ほかのワークフローでは同じことが起きる。また、ワークフローの変更(セキュリティ設定)になる。
- PRをドラフトで作り、ドラフトの間はCIを走らせない: ワークフローの条件の変更が要る。また、ドラフトの間に、CIで見つかる問題に気づけない。

## 結果

- メリット:
  - レビューで指摘があっても、CIの実行は原則として1回で済む。
  - PRを作った時点で、レビューの結果をまとめコメントに記録できる。
- デメリット・受け入れたトレードオフ:
  - レビューの間は、ブランチがリモートにない。作業環境が失われると、レビュー中のコミットも失われる(Claude Code on the Webでは、コンテナが回収されたとき)。レビューが長引くときは、ユーザーに断ってからプッシュする。
  - CIでしか見つからない問題(Windowsでのビルドなど)は、レビューの後に見つかる。その修正のプッシュは避けられない。
- 将来の見直し条件:
  - レビューの間にコミットが失われることが起きたとき。
  - 人間のレビュアーが加わり、PRの上でレビューする必要が生じたとき。
