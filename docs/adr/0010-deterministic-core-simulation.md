# ADR-0010: シミュレーションを決定的にする

- ステータス: 採用
- 日付: 2026-10-31

## 背景

開発フローはTDDで進める(AGENTS.md)。電子レンジが飛ぶシミュレーションや、時刻・季節に応じたテーマ選択、確率で起こる隠し要素を自動テストするには、同じ入力から常に同じ結果が得られる必要がある。

実行環境のフレームレートや、乱数の出力列、現在時刻に結果が左右されると、テストが不安定になったり、依存の更新で壊れたりする。アーキテクチャの原則A-3として整理している([アーキテクチャ](../design/architecture.md#設計原則)、[シミュレーション](../design/architecture.md#シミュレーションcore))。メンテナーが2026-10-31に決定した。

## 決定

`core`のシミュレーションを決定的にする。次の3点を満たす。

- 固定タイムステップ: 固定の刻み(例: 1/120秒)で状態を更新する。実時間の経過分を積算し、必要な回数だけ進める。スリープ復帰などで大きな経過時間が来た場合は、上限で切り詰める。描画時は、直前と現在の状態を経過時間の端数で補間する。固定タイムステップとモニタのリフレッシュレート(144Hz、165Hzなど)が合わないときのカクつきを防ぐため。
- 自前の小さな乱数生成器: `core`に小さな乱数生成器(例: SplitMix64)を実装し、既知の出力列と一致することをテストする。テストでは固定シードを使い、実行時は起動時刻などからシードを作る。
- 時刻の注入: 現在時刻はインターフェースを通して与え、テストでは任意の日時を指定できるようにする。時計表示や季節テーマ、日付の切り替わりなどの境界条件を、日時を固定してテストするため。

### 検討した選択肢と採用しなかった理由

- 外部の乱数crate(例: fastrand): 実装を持たずに済む。しかし出力列がバージョンをまたいで安定する保証がなく、固定シードで結果を比較するテストが依存の更新で壊れうるため採用しなかった。この点は[敵対的レビュー記録](../reviews/0001-plan-adversarial-review.md)の指摘No.26で提起され、fastrandの方針自体は一次情報で未確認である。自前の生成器に既知の出力列のテストを付ければ、出力列の安定をこちらで保証できる。
- 経過時間に比例して状態を進める方式(可変のタイムステップ): 実行環境のフレームレートによって結果が変わり、再現性のあるテストを書きにくいため採用しなかった。
- 実行時に現在時刻を直接取得する方式: テストで任意の日時を与えられないため採用しなかった。

## 結果

- メリット:
  - 同じシードと同じ入力から常に同じ結果が得られ、位置や個数などを決定的に比較するテストを書ける。
  - 乱数の出力列が外部crateの更新で変わらない。
  - 日時を注入するため、日付の切り替わりや年末年始などの境界条件をテストできる。
  - 補間により、リフレッシュレートが固定ステップと合わなくても滑らかに見える。
- デメリット・受け入れたトレードオフ:
  - 乱数生成器を自前で実装し、保守する必要がある(統計的な品質は、スクリーンセーバーの用途で十分な範囲にとどめる)。
  - 固定ステップと補間の実装が必要で、可変ステップより複雑になる。
  - 経過時間の上限による切り詰めで、長い停止の後は実時間より遅れて進む。
- 将来の見直し条件:
  - 乱数の品質が演出の見た目に問題を起こしたとき(生成器を変更する。既知の出力列のテストを更新する)。
  - 固定ステップの刻みが、描画や負荷の目標に合わないと分かったとき。
  - 外部の乱数crateが出力列の安定を保証するようになり、自前実装を置き換える利点が上回ったとき。
