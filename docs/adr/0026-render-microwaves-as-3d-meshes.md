# ADR-0026: 電子レンジを箱のメッシュで3Dに描き、面の絵をSVGからテクスチャにする

- ステータス: 採用
- 日付: 2026-11-11
- 置き換え: [ADR-0023: svg-sprites-from-v0.2.0](0023-svg-sprites-from-v0.2.0.md) を非推奨とし、本ADRが最新の決定となる

## 背景

[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)のD-2で、電子レンジがそれぞれ違う向きと速さで、3Dの任意の方向に回転しながら飛ぶ表現([将来のオプションのアイデア](../ideas/future-options.md)のO-08)を、v0.3.0に含めて既定にすると決めた。いまの描画([ADR-0023](0023-svg-sprites-from-v0.2.0.md))は、斜め上から見た絵を2Dのスプライトとして並べ、ドアを平行四辺形に変形して開閉させる方式で、任意の方向の回転は描けない。

計画0005のD-3は、方式をスパイクとADRで決めるとし、進める方向を「箱の形のメッシュに、面ごとにSVGからラスタライズした絵を貼り、深度バッファを使って透視投影で描く」とした。2026-11-10に、スパイク(`spikes/render3d/`。[スパイクの説明](../../spikes/README.md))で、この方式で描いた画像を作り、メンテナーが見て、この方向で進めると判断した(2026-11-11)。スパイクは、Linuxのソフトウェアの描画(Vulkanのlavapipe)で確かめたもので、Windows(DX12、WARP)では確かめていない。

## 決定

電子レンジを、箱の形のメッシュで3Dに描く。面の絵は、これまでどおりSVGで自作し、resvgでラスタライズする。

- 形: 本体は直方体(幅1.5、高さ1.0、奥行き1.3125。いまのSVGの絵の比率)。正面は、ドアの開口部の周りの帯と、その奥の灯りのついた庫内の箱にする。ドアは窓付きの薄い箱で、正面の左の縦の辺(ヒンジ)の軸の回りに0°〜70°回って開閉する(ADR-0023の平行四辺形の変形は使わない)。ターンテーブルは庫内の円盤、LEDの表示は正面の別の板にする。頂点のデータは、コードの中に手で書く。
- 絵: 面ごとの絵(正面、側面、背面、ドアの外側と内側、庫内、ターンテーブル、LED)をSVGで自作し、resvgでラスタライズして、1枚のテクスチャアトラスにまとめる。`<text>`、`<image>`、外部ファイルへの参照は使わない(ADR-0023と同じ)。3Dでは、奥行きと回転で画面上の大きさが変わるため、アトラスは画面の大きさではなく決まった大きさでラスタライズし、ミップマップを付ける。本体の色(silver、graphite、white、mint)は、ADR-0023と同じ4種類にする。
- 描画: wgpuで、深度バッファ(Depth32Float)と透視投影を使う。不透明な面を先に描き(深度を書く)、ドアの窓のガラスはあとで、奥のものから順に重ねて描く(深度は書かない)。光は、平行光源とアンビエントの簡単な陰影にする。明るさは、どの向きでも0.55〜1.00の範囲に収め、回転による明るさの変化が明滅に見えないようにする(ガイドラインG-3)。庫内、ターンテーブル、LEDは、光の影響を受けない自発光にする。DX12とFxcの指定(SEC-2)は変えない。メンテナーが判断したスパイクの画像は、MSAA 4倍と異方性フィルタ8で描いたもので、製品でMSAAを使うか(サンプル数)と異方性フィルタは、メモリと負荷を見て、計画0005の作業6の前に決める(E-8)。
- 数学: 向き(四元数)、行列、透視投影の計算は、`core`に必要な分だけ自前で書く。スパイクでは約230行(テストを含む)で足りた。数学のcrateは加えない(計画0005のE-5)。
- 同じ向きで飛ぶ表現(計画0005のD-4の`Level`): 全機を同じ向きにしたうえで、機体ごとに、カメラから機体への向きに合わせて補正する。透視投影では、同じ向きでも画面の位置によって見える面が変わるため、どの位置でもv0.2.0に近い同じ面が見えるようにする(2026-11-11にメンテナーが選んだ。計画0005のD-10)。
- 見た目の値(計画0005のE-1。スパイクで置いた出発点の値で、メンテナーはまだ判断していない。`v0.3.0-alpha.2`で動きを見て、メンテナーが決める): `flight.speed`と`flight.scale`が1.0のときの値である。視野角は縦40°。クリップ面は手前1.0・奥100(本体の高さを1とする単位)。電子レンジの奥行き(視線の方向)は10〜26。回転の速さは毎秒0.35〜0.9ラジアン。ドアの羽ばたきは毎秒1.2〜1.8回(v0.2.0と同じ)。ターンテーブルは毎秒0.1回転。飛ぶ速さは、本体の高さを1とする単位で毎秒2.4で、奥行きによらず同じ(遠いものほど遅く見える。計画0005のF-08)。v0.2.0の`flight.scale`が1.0のときの大きさ(本体の幅が画面の高さの0.09)は、奥行き23に、v0.2.0の飛ぶ速さ(毎秒、画面の高さの0.15)は、奥行き22に当たる(スパイクの`scene.rs`の値からの計算)。機体ごとの速さの倍率と、設定の倍率の当てはめ方は、計画0005の作業5で決める。

### 検討した選択肢と採用しなかった理由

- 回転した姿を前もって描いておく(角度ごとの絵): 任意の軸の回転では、絵の数が多くなりすぎる。
- 2Dのスプライトのまま(ADR-0023): 任意の方向の回転(O-08)を描けない。
- 数学のcrate(glamなど)を使う: 必要な計算が少なく、自前で足りた。依存を増やさない。
- 同じ向きで飛ぶ表現を、補正せずに描く(スパイクの`level.png`): 画面の左右で見える面が変わり、v0.2.0の見え方と離れるため、メンテナーが補正する案を選んだ。

## 結果

- メリット:
  - 任意の方向の回転、ヒンジの回りのドアの開閉、奥行きによる大きさの違いを、同じ仕組みで描ける。
  - 絵の直しは、これまでどおりSVGを書き換えるだけで済む。新しいcrateは増えない。
- デメリット・受け入れたトレードオフ:
  - メモリ: アトラスは、スパイクの大きさ(4096x1632、ミップマップ5段)で約35MB使う。ウィンドウごとに作ると、モニターの数だけ増える。深度バッファは、4Kのウィンドウ1つで約33MB使う。MSAAを4倍で使うと、色と深度の添付が、4Kのウィンドウ1つでそれぞれ約133MBになり、それだけで計画0001のN-04(200MB以下)を超えうる(3840×2160×4バイト×4サンプルからの計算)。WARPでは、これらがプロセスのメモリに乗るかは確かめていない。アトラスの共有とMSAAの扱いは、計画0005の作業6の前に決める(E-8)。
  - 左の側面、上面、底面は無地で、その面だけが見えるときは、ただの箱に見える。描き加えるかは、素材を作るときに決める(計画0005のE-8)。
  - 同じ向きで飛ぶ表現の補正では、画面を横切る間に、見かけの向きが少しずつ変わる(補正の計算から言えること。アニメーションでは確かめていない)。
  - スパイクの画像は静止画で、回転の速さと、回転による明るさの変化が明滅に見えないか(ガイドラインG-3)は、動きでは確かめていない。明るさの変化の速さが最大で毎秒0.2(最も暗い状態から最も明るい状態まで、最短で約3.5秒)であることは、計算で確かめた。動きは`v0.3.0-alpha.2`で確かめる(計画0005の作業8)。
  - Windows(DX12、WARP)での描画、Fxcでのシェーダーのコンパイル、WARPでの負荷(計画0001のN-03)と、CIのスモークテストの時間は、確かめていない。製品に移すとき(計画0005の作業5・6)と、プレリリース`v0.3.0-alpha.2`で確かめる。
  - 製品の描画は、計画0005の作業5・6で実装するまでは、ADR-0023の方式のまま(`v0.3.0-alpha.1`まで)である。
- 将来の見直し条件:
  - WARPやGPUの弱い環境で、起動の速さ(計画0001のN-01)やCPU負荷(N-03)を満たせないとき。
  - 必要な表現が、箱のメッシュと面の絵では描けないとき。
