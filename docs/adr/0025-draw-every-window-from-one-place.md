# ADR-0025: 全画面のウィンドウを、イベントループの1か所から順に描く

- ステータス: 採用
- 日付: 2026-11-08

## 背景

`/s`は、モニタごとに全画面のウィンドウを作り、それぞれで電子レンジを描く([ADR-0019](0019-screensaver-windows-without-winit-fullscreen.md))。これまでは、ウィンドウごとにwinitの`request_redraw`を呼び、届いた`RedrawRequested`の中でそのウィンドウを描き、描き終えたら同じウィンドウの`request_redraw`を呼んでいた。

2画面の環境で、2台目のウィンドウに1回も描かれなかった(Issue #50、[incidents 0014](../incidents/0014-second-monitor-not-drawn.md))。`v0.2.0-alpha.3`の実機のログでは、約8秒のあいだに、1台目のウィンドウには`RedrawRequested`が232回届き、2台目には1回も届かなかった。

- winit 0.30.13のWindowsの実装は、`RedrawRequested`を`WM_PAINT`の処理の中で送り、1回送るたびにメッセージの処理を打ち切る(`platform_impl/windows/event_loop.rs`)。
- 1台目のウィンドウは描くたびに再描画の印を付け直すため、印の付いたウィンドウが常に2つある。Windowsがどちらの`WM_PAINT`を先に返すかは、Win32の文書に決まりがない。ログでは、1台目が選ばれ続けた。

## 決定

- 全画面(`/s`)では、描画を`ApplicationHandler::about_to_wait`の1か所にまとめる。イベントの処理が一巡するたびに、描く時期が来たすべてのウィンドウを順に描く。描く時期は、これまでと同じく、フレームレートの上限(`display.max_fps`)と、スキップしたあとの再試行の時刻で決める。
- 描画のために`request_redraw`を呼ばない。`RedrawRequested`は、描画先のないウィンドウ(黒のままのウィンドウ)を黒く塗り直すことにだけ使う。
- 描けたウィンドウが1つでもあれば、次の一巡をすぐに始める(`ControlFlow::Poll`)。描くペースは、これまでと同じく、`Fifo`の表示の切り替えと、フレームレートの上限で決まる。どのウィンドウも描けなかったときは、次の再試行や上限の時刻まで待つ(`ControlFlow::WaitUntil`)。
- プレビュー枠(`/p`)は、ウィンドウが1つなので、今のまま`RedrawRequested`で描く。

### 検討した選択肢と採用しなかった理由

- どれか1つのウィンドウに`RedrawRequested`が届いたら、すべてのウィンドウを描く: 変更は小さいが、1つのウィンドウにイベントが届き続けることに頼る点は今と同じで、意図も分かりにくい。
- ウィンドウごとに別のスレッドで描く: モニタごとのリフレッシュレートに左右されないが、GPUのデバイスの共有とスレッド間の同期が増える。いまの目的には大きすぎる(YAGNI)。

## 結果

- どのウィンドウに`WM_PAINT`が届くかの順番に左右されず、すべてのウィンドウを描く。実行中に増えたモニタのウィンドウ(計画0004のF-07)も、同じ一巡で描く。
- 1つのスレッドで、ウィンドウごとの表示の切り替えを順に待つ。リフレッシュレートの違うモニタを並べると、遅いほうに引きずられるおそれがある(推測。実機で確かめる)。
- 診断用のログのまとめの行は、`RedrawRequested`を受け取った回数ではなく、描こうとした回数を数える形に変える。
