# 0043: 実装を任せたサブエージェントが、先に失敗するテストを書かなかった

- 日付: 2026-11-21
- ステータス: 対策済み(対策の(1)(計画0005のD-32。AGENTS.mdのモデルの使い分けの段)を、2026-11-22にPR #98でマージした)
- 関連: AGENTS.mdの「開発フロー」(TDD)と「進め方」(モデルの使い分け)、計画0005の作業10の4と10の5

## 起きたこと

2026-11-21に、incident 0033の対策(1)〜(3)と0035の対策(1)(終了の各段の時間のログと、スモークテストの時間の警告。計画0005のD-24の(6)、D-25の(2))の実装を、エージェントは、安価なモデルのサブエージェントに任せた(AGENTS.mdの「進め方」のモデルの使い分け)。サブエージェントは、判定の関数とその単体テストを同時に書き、テストが先に失敗すること(TDDのRed)を確かめなかった。エージェントは、サブエージェントの報告で気づいた。

確かめた事実:

- 依頼文は、AGENTS.mdを最初に読み、TDDの規則に従うよう求め、項目5で「TDD: 先に失敗するテスト」と書いていた。報告に何を書くかの指定(変えたファイル、各項目の実装、設計から外れた点、検証の結果)には、Redの結果を含めていなかった。
- サブエージェントの報告は、「先に失敗するテスト(Red)を確かめずに、関数とテストを同時に書きました。TDD の手順は守れていません。」と書いていた。
- 取り込む前の確かめとして、エージェントは、判定を1つずつわざと壊した写しでテストを実行した。壊したのは6か所で、どれもテストが失敗した(`crates/app/src/diag.rs`の`log_slow_acquire`の2つの比較と`after_exit_decision`の文言、`crates/smoke/src/lib.rs`の`Timing::is_over_half`の比較、`Progress::read`の遅い取得の行の読み取り、`Timing::line`の形式)。壊したファイルは、そのたびに元に戻した。

## なぜなぜ分析

1. なぜ、先に失敗するテストを書かなかったか。
   - サブエージェントが、関数とテストを同時に書いた(サブエージェントの報告)。同時に書いた理由は、報告に書かれておらず分からない。
2. なぜ、依頼文に書いた手順が守られなかったか。
   - 依頼文は、TDDを手順として求めたが、Redを確かめた証拠(失敗したテストの出力)を報告に求めなかった。そのため、手順を飛ばしても、報告の形では分からない作りだった(依頼文の報告の指定を読み直して確かめた)。
3. なぜ、取り込む前の確かめで見つける作りでなかったか。
   - AGENTS.mdのモデルの使い分けは、安価なモデルの成果物を「高性能なモデルで整合性を確認してから取り込む」と定めるが、何を確かめるかは定めていない(AGENTS.mdの「進め方」を読んで確かめた)。エージェントの確かめは、設計との照合と検証のコマンドで、作り方の手順(Redを経たか)は含めていなかった。今回は、サブエージェントが自分で書いたため気づいた。
4. 真因: 実装を任せるときに、TDDのRedを経たことを、報告で示させる段も、取り込む前に確かめる段もない。

## 真因

- 実装を任せる手順に、Redの証拠を求める段と、それを確かめる段がない。

## 対策

行ったこと:

- 今回の成果物は、上の「確かめた事実」のとおり、判定をわざと壊した写しでテストが失敗することを確かめてから取り込んだ。Redを先に確かめた場合と同じく、テストが実装の誤りを見つけられることを示すため。

案(AGENTS.mdの変更なので、メンテナーの承認が要る。2026-11-21に、メンテナーが(1)を採った。計画0005のD-32):

1. 手順: AGENTS.mdの「進め方」のモデルの使い分けに、次を加える。実装を任せる依頼文には、Redの証拠(先に書いたテストの名前と、失敗した結果の行)を報告に含めるよう求める。取り込む前に、その証拠を確かめる。証拠がないときは、取り込む前に、判定をわざと壊した写しでテストが失敗することを確かめる(今回行った方法)。
2. 仕組み: 採らない。Redを経たかは、最後の差分からは見分けられない。失敗するテストだけのコミットを残させる方法は、「コミット前に必ずテスト」の規則と食い違う。

## 確かめ方

- このあとで実装を任せたとき、サブエージェントの報告にRedの証拠があり、エージェントがそれを確かめてから取り込むこと(取り込みの報告に、確かめたことを書く)。
