- ステータス: 対策中(2026-11-20に、メンテナーが対策の(1)〜(3)を推奨どおりと判断した。計画0005のD-23。(4)は作業10の4の結果を見て決める)
- 関連: [0028](0028-smoke-failure-merged-on-a-guess.md)(スモークテストの失敗を、値を並べて比べずに推測で扱った)、[ADR-0028](../adr/0028-wait-for-swap-chain-at-most-one-frame.md)の「背景」と「検討した選択肢と採用しなかった理由」、[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)の作業6、PR #73、PR #82、PR #88

## 起きたこと

2026-11-19に、PR #88(文書と開発の道具だけの変更)のCI(実行201、head `dbefc86`)で、Windowsのスモークテストの`F-02 /p ends with its parent`が失敗した。親の窓を閉じてから2000ms(上限。`crates/smoke/src/windows.rs`の`EXIT_AFTER_PARENT_GONE`)たっても、プレビューのプロセスが終わっていなかった。

気づいたきっかけは、この失敗の原因を調べるために、過去の実行の値を並べたことである。

確かめた事実:

- PR #88のつぎの実行202(head `db2c2d4`、文書だけのコミット)でも、F-02が同じ形で失敗した。`+397ms`に`preview exit: WindowDestroyed (exit code 0)`があり、`preview ended`の行はない。失敗したF-02のプロセス(pid 7848)の起動は、最初のフレームまで377ms、アトラスの用意が164msだった。同じ実行の最初のF-01のプロセス(pid 4060)は、1003msと232msだった。
- その次の実行203(head `ca4765b`)では、F-02は1994msで通った(上限まで6ms)。失敗したのは、壊れた設定ファイルでのF-01の、キーから画面が消えるまでの検査だった([incident 0035](0035-key-to-screen-gone-failed-after-adr-0028.md))。
- 実行201のプロセスのログ(スモークテストが失敗のときに表示する`log of process 7652`):
  - `+453ms`に`preview: first frame presented`、`+469ms`に`preview exit: WindowDestroyed (exit code 0)`がある。
  - `preview ended: ... frames`の行はない。この行は、`event_loop.run_app`が戻ったあとに書かれる(`crates/app/src/preview.rs`の`run`)。ログは1行ずつファイルに直接書かれ、バッファーを通らない(`crates/app/src/log.rs`の`write`)。
  - したがって、終了を決めたあと、`run_app`が戻るまでの後始末(`preview.rs`の`exiting`で、描画先、GPU、窓を破棄する)か、winitの終了の処理で、時間がかかっていた。どこでかかったかは、ログに出ないため分からない。
- CIの実行151〜201のWindowsのジョブのログから、F-02の`parent destroyed to exit`(F-02が通ったときに出る)と、最初のF-01の`to process exit`を集めた(サブエージェントが書き写し、実行159、160、200はエージェントがログで確かめた)。実行135〜150と、取り消された実行183は含まない。

## なぜなぜ分析

1. なぜ実行201でF-02が失敗したか。
   - 終了を決めてからプロセスが終わるまでが、2000msを超えたため。この時間は、PR #73からふだんでも1.2〜1.8秒で、上限までの余裕が小さい(上の表)。
2. なぜ、余裕が小さくなったことに8日間気づかなかったか。
   - スモークテストは、時間を上限と比べて、通るか失敗するかだけを判定する(`crates/smoke/src/windows.rs`の`wait_exit`)。上限の近くまで延びても、通るあいだは何も知らせない。
   - 値はログに出ているが、PR #73の記録では、変えたところ(アトラスの作成と最初のフレーム)の値だけを比べ、終了の値は見ていない。
3. なぜ、変えたところの値だけを比べたか。
   - 作業6の確認の項目が、「負荷と起動の速さ」と決めていたため。変更が、ほかの時間(終了)にどう効くかを確かめる決まりがない。
4. なぜ、incident 0028の調査とADR-0028の案Bの判断でも、終了の値を比べなかったか。
   - 0028の調査は、失敗した値(画面が消えるまで)だけを集めた。
   - 案Bの判断は、試しの1回の失敗を、案の違いによるものと考えた。0028で加えた規則は、「ときどきだけ失敗するCIの検査(同じコードで、通ることも失敗することもあるもの)」を対象とし、試しの案(別のコード)の失敗は対象の外だった。失敗を判断の根拠にするときに値を比べる決まりは、ほかになかった。
5. 真因: スモークテストの時間の検査は、上限を超えたかどうかしか知らせず、上限までの余裕が減ったことを知らせる仕組みがない。また、失敗を判断(案の不採用など)の根拠にするときに、その値をほかの実行と並べて比べる決まりが、「ときどき失敗する検査」に限られていた。

## 真因

- スモークテストの時間の検査に、余裕が減ったことを知らせる仕組みがない。
- 失敗を判断の根拠にするときに、値をほかの実行と並べて比べる決まりが、「ときどき失敗する検査」に限られている。

## 対策

2026-11-20に、メンテナーが(1)〜(3)を推奨どおりと判断した(計画0005のD-23)。(2)の規則は、2026-11-20の記録の変更でAGENTS.mdに加えた(対象の範囲は下の注のとおり)。(1)と(2)の仕組みはスモークテストの変更で、設計はD-24の(6)で採った。計画0005の作業10の5(作業10の4と同じPR)で行う。(3)は計画0005の作業10の4で行う。(4)は、作業10の4の結果を見て決める。

案:

1. 仕組み: スモークテストが、時間の検査の値が上限の半分を超えたときに、GitHub Actionsの警告(`::warning::`の行)を出すようにする。通る・失敗するの判定は変えない。しきい値は上限の半分とする(2026-11-20に決定。計画0005のD-23)。
2. 規則: AGENTS.mdの「ときどきだけ失敗するCIの検査」の規則の対象を、CIの検査の失敗を判断(案の不採用、原因の特定など)の根拠にするときにも広げる。その検査の値を、少なくとも直近の版からの実行で並べて比べる。注: AGENTS.mdに加えた文は、レビューの指摘を受けて、対象を「時間や回数を上限と比べるCIの検査」に絞った。ビルドや単体テストのような、値を持たず、同じコードで結果が変わらない失敗まで含めると、CIの失敗を直す通常の手順やTDDのRedの扱いと食い違うため。承認された文より狭いので、メンテナーに確かめる。
   - 規則の文だけでは守られないおそれがあるため、仕組みもあわせて置く。対策1の警告は、通った実行でも余裕の減りを示すので、比べるきっかけになる。さらに、スモークテストが最後に、すべての時間の値と上限を1行ずつの決まった形で出すようにし、実行どうしを並べやすくする。どちらも、比べることそのものを強制はしない。強制する仕組み(ADRや計画の記録の検査など)は、記録の文から判断の根拠を機械的に見分けられないため、採らない。
3. 製品: 終了の後始末のどこに時間がかかっているかを調べる作業を、計画0005に登録する。後始末の各段(描画先、GPU、窓の破棄)の前後で時刻をログに書く変更が要る見込みで、製品のコードの変更なので、設計を報告してから行う。実機でもかかるかは、`v0.3.0-alpha.4`の実機での確認のログ(プレビューは`preview exit`と`preview ended`の時刻の差。`/s`は`crates/app/src/saver.rs`の`screensaver ended`の行と、その前の終了の行)で確かめられる見込みである(どの行で測れるかは、調べる作業の中でコードを読んで確かめる)。
4. 記録の訂正: ADR-0028はマージ済みで、決定の書き換えはできない。許される編集は、非推奨化の手順(ステータスの変更と冒頭への追記)だけである(`docs/adr/README.md`の9行)。そのため、案Bの理由を確かめていないことは、この記録に書く(上の「起きたこと」)。案Bを改めて試し、決定を変えることになったら、ADR-0028を非推奨にして新しいADRを書く。案Bを改めて試すかどうかは、判断していただくこと。

## 確かめ方

- 対策1: 終了の時間が上限の半分を超える実行で、Windowsのジョブに警告が出ること。今の値(1.2〜1.8秒)なら、次の実行で出る。
- 対策2: これからのADRと計画の記録で、時間や回数を上限と比べるCIの検査の失敗を根拠にした判断に、値を並べた表か、その表への参照があること。
- 対策2の仕組み: スモークテストのログの最後に、すべての時間の値と上限の行があること。
- 対策3: 調べる作業の結果として、後始末のどこに時間がかかるかが、ログの行で示されていること。
