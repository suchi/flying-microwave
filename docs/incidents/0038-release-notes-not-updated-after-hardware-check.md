# 0038: 公開したプレリリースの実機での確認の結果を、CHANGELOGとリリースノートに反映しなかった

- 日付: 2026-11-20
- ステータス: 対策中(CHANGELOGの訂正は、このincidentを記録したPRで行う。リリースノートの差し替えはメンテナーの作業。手順と仕組みの対策は、メンテナーの判断を待っている)
- 関連: [0031](0031-requested-publishing-an-already-published-release.md)(公開済みのリリースを下書きとして扱った)、[計画0001](../plans/0001-initial-implementation-plan.md)の7.3、[計画0003](../plans/0003-v0.1.1-smoke-test.md)のD-10、[計画0004](../plans/0004-v0.2.0-settings.md)のD-16

## 起きたこと

2026-11-20に、メンテナーから、最新のリリース(プレリリースを含む)の文書が「実機での確認をしていない」となっているので直すよう指示を受けた。AGENTS.mdの「進め方」の異常の定義の、完了として渡した成果物(公開したリリース)の誤りの指摘に当たる。

確かめた事実:

- 最新のリリースは`v0.3.0-alpha.4`(プレリリース。2026-11-18 12:44(JST)に公開。GitHubのリリースの`published_at`)。リリースノートの冒頭に「実機での動作の確認はしていない。」、既知の制限の最初の箇条に「実機での動作の確認をしていない。」とあった(2026-11-20に`list_releases`で取得した本文)。`CHANGELOG.md`の`v0.3.0-alpha.4`の節も同じだった(リリースノートは、この節から`scripts/prepare_release.py`で作る。計画0001の7.3の手順3)。
- この版の実機での確認は、公開のあとの2026-11-20に行われ、結果を受け取った([手順書](../development/hardware-check-v0.3.0-alpha.4.md)の「結果」の節)。
- エージェントは、結果を記録したコミット(`0ba2475`)で、手順書、計画0005、incident 0033、0035、0036を変えたが、`CHANGELOG.md`は変えなかった(`git show --stat 0ba2475`)。リリースノートの差し替えも、メンテナーに依頼しなかった。
- 似た前例がある。`v0.2.0-alpha.4`では実機での確認を行ったが(計画0004のD-16)、CHANGELOGのその版の節は「実機での動作の確認はしていない」のままである(結果は`v0.2.0`の節に書いた)。確認が公開の前か後かは、記録からは分からない(D-16に書かれていない。リリースの`published_at`は2026-11-09 16:25(JST)、確認を記録したコミット`eb31ef1`は同じ日の22:58(JST)で、確認を行った時刻の記録はない)。一方、`v0.1.1-alpha.3`では、公開の前に、その版に限った決定(計画0003のD-10)で、CHANGELOGとリリースノートから確認をしていないとする記述を外した。

## なぜなぜ分析

1. なぜ、公開したリリースの文書が「実機での確認をしていない」のままだったか。
   - 実機での確認の結果を受け取ったとき、エージェントがCHANGELOGを直さず、リリースノートの差し替えも依頼しなかったため(上の事実の`git show --stat 0ba2475`)。
2. なぜ、直さなかったか。
   - 結果を記録する先として、手順書、計画、incidentだけを考え、利用者が読む文書(CHANGELOGとリリースノート)を確かめなかった(推測。根拠は、`git show --stat 0ba2475`の変更の対象にCHANGELOGがないことと、下の3の手順と規則に、利用者が読む文書を直す段がないこと)。
3. なぜ、利用者が読む文書を確かめなかったか。
   - リリースの手順(計画0001の7.3)には、実機での確認の結果(行ったことと確かめられなかった項目)を、CHANGELOGとリリースノートに反映する段が、公開の前後を問わずない(7.3を読んで確かめた)。CHANGELOGのプレリリースの節は、版を上げるPR(手順1)の時点で「実機での動作の確認はしていない」と書かれるが、手順4は「実機での確認を行ってから、公開する。リリースノートは、必要なら画面で直す(インストールの手順など、CHANGELOGにない内容)」で、確認の結果を書く段がない。今回のように公開のあとで確認した場合の手順もない。`v0.1.1-alpha.3`のときは、その版に限った決定(計画0003のD-10)で扱い、手順にしなかった。`v0.2.0-alpha.4`では書き改めなかった。`alpha.4`の手順書のZ-4(確認のあとで下書きを公開する)にも、記述を直す段はなかった。
   - AGENTS.mdの「進め方」は、確かめられなかった項目を「リリースノートか計画の記録に書き」と定めていて、計画に書けば足りると読める。
   - 実機での確認の手順書にも、結果を受け取ったあとでCHANGELOGを確かめる段がない(`docs/development/hardware-check-v0.3.0-alpha.4.md`の「Z」と「結果」の節)。
4. なぜ、これまで気づかなかったか。
   - 文書の食い違い(手順書には結果があり、CHANGELOGにはない)を機械的に見つける検査がない(`scripts/`のテストと`.github/workflows/`に、CHANGELOGと手順書を比べるものはない。`grep -rln "hardware-check" scripts .github`で何も当たらないことを確かめた)。

## 真因

- 実機での確認の結果をCHANGELOGとリリースノートに反映する段が、公開の前後を問わず、リリースの手順にない。
- 規則が、確かめた結果と確かめられなかった項目の記録先を「リリースノートか計画」としていて、公開済みのリリースの文書を直すことを求めていない。
- 手順書の結果とCHANGELOGの食い違いを見つける検査がない。

## 対策

目の前の現象への対応(このincidentを記録したPRで行う):

- `CHANGELOG.md`の`v0.3.0-alpha.4`の節を、実機での確認の結果に合わせて書き改めた(「行った確認」と、既知の制限の確かめられなかった項目)。
- リリースノートの本文を`scripts/prepare_release.py`でこの節から作り、メンテナーがGitHubの画面で差し替える(エージェントのセッションからはリリースを編集できないため。計画0003のD-10)。リポジトリは変更できないリリース(immutable releases)を有効にしているが、固定されるのはタグと成果物で、リリースノートは公開のあとも編集できる(計画0004のD-17)。
- zipに同梱した`README.md`には、実機での確認についての記述がない(`git show v0.3.0-alpha.4:packaging/windows/README.md`を`grep -n "実機"`で検索して確かめた)ため、リリースノートに断り書きは要らない。

案(承認が要る。メンテナーの判断を待っている):

1. 手順: 計画0001の7.3に、実機での確認の結果を受け取ったら、エージェントが、結果を記録するPRで、CHANGELOGのその版の節(冒頭の確認の説明と既知の制限)を書き改め、そこから作ったリリースノートの本文をメンテナーに渡す段を加える。メンテナーは、公開の前なら下書きを差し替えてから公開し、公開のあとなら画面で差し替える。
2. 規則: AGENTS.mdの「進め方」の、確かめられなかった項目を「リリースノートか計画の記録に書き」とする箇条に、公開済みのリリースで実機での確認を行ったときは、CHANGELOGのその版の節とリリースノートも直すことを加える。
3. 仕組み: `scripts/`に、手順書(`docs/development/hardware-check-vX.Y.Z*.md`)に「## 結果」の節がある版で、CHANGELOGのその版の節が「実機での動作の確認はしていない」「実機での動作の確認をしていない」を含むときに失敗するテストを加える。CIのスクリプトのテストで実行される。
4. 前例の`v0.2.0-alpha.4`: CHANGELOGの節とリリースノートを、計画0004のD-16の結果に合わせて直すか(手順書がないため、3のテストの対象にはならない)。

## 確かめ方

- `v0.3.0-alpha.4`のリリースノートの本文が、CHANGELOGの節から作った本文と同じであること(メンテナーの差し替えのあとで、`list_releases`で取得して比べる)。
- 3を採った場合: 次に公開のあとで実機での確認をした版で、CHANGELOGを直す前にテストが失敗すること。
