# 0012: フックの検査のテストが、Windowsのスパイクのビルドで失敗した

- 日付: 2026-11-02
- ステータス: 対策中(対策のPRがマージされていない)
- 関連: [0009](0009-guard-hooks-never-ran.md)(フックの検査を加えた異常)、[0010](0010-onboarding-missed-build-steps.md)

## 起きたこと

文書の修正のPR #37で`spikes/README.md`を変えたため、スパイクのワークフロー(`spikes.yml`)がWindowsのランナーで動いた。その中のスクリプトの単体テスト(`python -I -m unittest discover -s scripts`)で、フックの検査のテスト(`scripts/test_check_hooks.py`の`RunTest`)が2件失敗し、`Build spikes`のジョブが失敗した。PR #37の差分(文書だけ)が原因ではない。

確かめた一次情報:

- 失敗の内容: Windowsのpythonから`sh -c`でフックを起動すると、`/usr/bin/bash: -c: line 1: unexpected EOF while looking for matching`の誤りになった(ジョブのログ)。この誤りの原因は特定していない(推測: Windowsのpythonが引数をコマンドラインの文字列に変換するときと、Git Bashがそれを解釈するときとで、引用符の扱いが合わず、登録の文字列の引用符が崩れた)。さらに、実行権限のないフックが起動に失敗すること(終了コード126)を確かめるテストは、実行権限のないWindowsでは成り立たない。
- 影響: 原因が引用符の扱いだとすると、Claude CodeがWindowsで、このリポジトリの防御のフック(`"$CLAUDE_PROJECT_DIR/..."`の形の登録)を起動したときにも、同じように崩れて動かないおそれがある。メンテナーの判断で、開発はクラウドのLinuxのエージェントだけで行い、WindowsでClaude Codeを使わないため、Windowsでのフックの動作は「未確認」とし、使うことになったときに確かめる。
- 経緯: フックの検査のテストは、2026-11-01 22:34(UTC)のコミットfbfaaa3で加わった(incidents 0009の対策)。それを実行するワークフローは2つある。CIのLinuxのジョブ(PRごとに毎回)と、スパイクのワークフローのWindowsのジョブ(`spikes/`を変えたときと手動実行のときだけ)である。スパイクのワークフローは、2026-11-01 11:56の実行を最後に動いておらず、テストを加えてからWindowsで実行されたのは今回が初めてだった(実行の一覧で確かめた)。
- オンボーディングは、Windowsでのフックの検査を「Git Bashで実行する」としていた。Windowsでは実行して確かめていない手順だった。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜスパイクのビルドが失敗したか | Windowsで成り立たないテスト(`sh -c`での起動と実行権限)が、Windowsのジョブで実行されたため |
| なぜテストを加えたときに気づかなかったか | 加えたPRで動いたのは、CIのLinuxのジョブだけだった。スパイクのワークフローは`paths`の条件で`spikes/`を変えたときだけ動くため、そのPRでは動かなかった |
| なぜ条件付きで動くジョブを確かめなかったか | スクリプトやそのテストを変えたときに、それを実行するワークフローをすべて挙げて確かめる手順がなかった。PRで動いたジョブが成功すれば足りるとしていた |
| なぜWindowsで成り立たないテストを書き、手順を書いたか | フックの検査の目的(LinuxとmacOSでの起動の再現)と、それを実行する環境(Windowsのジョブとメンテナーの環境を含む)を突き合わせていなかった。エージェントはWindowsで実行できないのに、Windowsでの手順を確かめないまま書いていた |

## 真因

1. スクリプトやそのテストを変えたときに、それを実行するすべてのワークフロー(条件付きで動くものを含む)で確かめる手順がなかった。
2. エージェントが実行できない環境(Windows)の手順を、確かめないまま確定した手順として書いていた。

## 対策

1. 現象への対応(メンテナーの判断): フックの検査を、LinuxとmacOSの専用にした。`check_hooks.py`はWindowsでは対象外と表示して終了コード0で終わり、起動を確かめるテスト(`RunTest`)はWindowsでは理由を書いてスキップする。対象外であることをテストで確かめる。オンボーディングの手順を、LinuxかmacOS(WindowsではWSL)で実行する形に直した。
2. 真因1への対策: AGENTS.mdの検証コマンドの段落に、「`scripts/`のスクリプトやそのテストを変えたときは、`.github/workflows/`でそれを実行するワークフローを探し、そのPRで動かないジョブ(`paths`の条件で動かないものなど)があれば、手動実行で確かめる」を加えた。スパイクのワークフローは手動実行に対応している。
3. 真因2への対策: AGENTS.mdの同じ段落に、「エージェントが実行できない環境(Windowsなど)の手順は、メンテナーが実行して確かめるまで、文書で『未確認』と示す」を加えた。
4. 仕組みによる対策(メンテナーの承認を得た): CIのWindowsのジョブ(PRごとに毎回動く)で、スクリプトの単体テストを実行するようにした。これで、Windowsでのスクリプトの失敗は、`spikes/`を変えたときを待たずに、そのPRで分かる。2の規則は、ほかの条件付きのワークフロー(リリースのワークフローなど)のために残す。
5. 判定の誤りへの備え: `check_hooks.py`のWindowsの判定が誤ってLinuxでも成り立つと、CIのフックの検査が黙って成功してしまう(0009と同じ種類の失敗)。LinuxとmacOSでは判定が偽になることを、テストで確かめる。

## 確かめ方

- PR #37のスパイクのビルドと、CIのWindowsのジョブのスクリプトのテストが、この対策の入ったコミットで成功すること。
- 以後、`scripts/`を変えたPRで、それを実行する条件付きのワークフローの結果(手動実行を含む)が、まとめコメントか本文に記録されていること。
