# 0041: 記録の日付を、JSTに直さずにUTCの日付で書いた

- 日付: 2026-11-21
- ステータス: 対策中(記録の日付は、このincidentを記録したPRで直した。規則と手順の対策は、メンテナーの判断を待っている)
- 関連: AGENTS.mdの「言語ルール」(メンテナーに示す時刻はJSTで書く)、[0024](0024-unfounded-guess-as-premise.md)(確かめていない事実を書いた)

## 起きたこと

2026-11-21に、作業ブランチの差分の再レビューで、記録の日付がUTCのままだと指摘を受けた。AGENTS.mdの「言語ルール」は、メンテナーに示す時刻を日本標準時(JST)で書き、ツールやGitHubの表示がUTCでも変換して書くと定めている。規則が守られなかったので、異常に当たる。

確かめた事実(このセッションの会話の記録の時刻をJSTに直したもの):

- 実機での確認の結果を受け取ったのは2026-11-21 00:09(JST)、D-25の判断は00:12(JST)、CHANGELOGの訂正の指示は08:20(JST)だった。記録には、どれも「2026-11-20」と書いていた(手順書の「結果」、計画0005のD-25と作業10の3、incident 0033、0035、0037、0038、0039、一覧の日付)。
- CHANGELOGには「公開のあと(2026-11-20)」と、確認を行った日として書いていた。確認を行った日時は記録がない(製品のログは起動からの経過時間だけを書く。`crates/app/src/log.rs`の書き出しの形`+{elapsed}ms pid=...`。`fm-usage.txt`にも日付がない)。
- セッションに示される日付は、2026-11-21 10:21(JST)に届いた知らせで、はじめて2026-11-21に変わった(会話の記録)。それまでは2026-11-20と示されていた。示される日付はUTCに沿っている(JSTの0時から9時の間は、前の日になる)。

## なぜなぜ分析

1. なぜUTCの日付を書いたか。
   - 記録の日付を、セッションに示される日付から取ったため(推測。根拠は、誤った日付がすべて、JSTの0時から9時の間の出来事で、示される日付と一致すること)。
2. なぜ、示される日付をJSTに直さなかったか。
   - AGENTS.mdの規則は「ツールやGitHubの表示がUTCでも、変換して書く」とするが、セッションに示される日付がUTCに沿うことに気づいていなかった。時刻を持たない日付は、直す対象と考えなかった(推測)。
3. なぜ、確認を行った日を書いたか。
   - 結果を受け取った日を、確認を行った日と同じものとして書いた。確かめられない事実を書かない規則(AGENTS.mdの「情報源」)に反していた。
4. 真因: 記録に日付を書くときに、JSTの日付を一次情報(時計)から取る手順がなく、セッションに示される日付を、確かめずに使った。

## 真因

- 記録に書く日付を、JSTの時計で確かめる手順がない。セッションに示される日付がUTCに沿うことが、規則と手順に書かれていない。

## 対策

行ったこと(このincidentを記録したPR):

- 上の記録の日付をJSTに直した。CHANGELOGと0038からは、確認を行った日を消し、結果を受け取った日を書いた。

案(承認が要る。メンテナーの判断を待っている):

1. 規則: AGENTS.mdの「言語ルール」の時刻の箇条に、セッションに示される日付もUTCに沿うため、記録に書く日付は`TZ=Asia/Tokyo date`などで、JSTの時計から取ることを書き添える。
2. 仕組み: 日付の誤りを機械的に見つける仕組みは、作れない(書いた日付が正しいかは、出来事の時刻を知らないと決められないため)。そのため、コミットの手順(`.claude/commands/commit.md`)に、追加した行に日付があれば、JSTの時計と比べる段を加える。

- 次の再レビューと、フェーズの区切りの整合性の確認で、UTCの日付の指摘が出ないこと。
