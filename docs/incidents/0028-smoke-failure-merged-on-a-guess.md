# 0028: スモークテストの失敗を、原因を確かめないまま再実行で通してマージし、再発した

- 日付: 2026-11-13
- ステータス: 対策中(真因への対策と、製品の原因の調べ方は、2026-11-13にメンテナーが承認した。真因への対策はAGENTS.mdに加え、PR #80でマージした。製品の原因を、調べる仕組みを入れた版のCIと実機の値で確かめるまでは、マージのあとも「対策中」とする)
- 関連: [0024](0024-unfounded-guess-as-premise.md)(推測を判断の前提にした)、[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)の作業10、PR #78、PR #79、PR #80

## 起きたこと

2026-11-12に、PR #78(飛ぶ食べ物)のCI(実行171の1回目)で、Windowsのスモークテストの F-01 が失敗した。失敗したのは最初の`/s`で、キーを押してから画面が消えるまでが1090msあり、上限の200msを超えていた。

エージェントは、次の手順で進めた。
1. 1つ前の実行(169)とだけ比べ、原因を「ランナーの一時的な遅さ」と推測した。
2. 失敗したジョブを1回だけ再実行した。再実行では通った(13ms)。
3. 推測であることを示したうえで、メンテナーにマージの判断を仰いだ。
4. メンテナーの承認を得て、マージした。

2026-11-13に、PR #80(文書だけの変更)のCI(実行175)で、同じ F-01 が再び失敗した(519ms)。このときは起動の時間がふだんどおりで、「ランナーの遅さ」の推測は当てはまらなかった。

確かめた事実:

- CIの実行160〜175のWindowsのジョブのスモークテストの値を、ログから集めた(サブエージェントが書き写した表)。
  - 食べ物の追加の前(実行160〜170、11回): 最初の`/s`は、すべて通った。キーから画面が消えるまでは5〜42msだった。
  - 追加の後(実行171〜175、6回): 2回失敗した。
  - 11回中0回と6回中2回の差は、偶然でも起こりうる(2回の失敗がすべて後の6回に入る確率は C(6,2)/C(17,2) = 15/136 で、約11%)。食べ物が原因とは言えない。
- 終了のときの要約の行(`crates/app/src/diag.rs`の80行目)の数を見た。
  - 失敗した2回は、どちらも「5 draws attempted, 4 frames」だった。
  - 通った回は、実行173を除いて「3 frames」だった(実行171の2回目は「3 draws attempted, 3 frames」)。
- 描画の回数の少なさ:
  - どの実行でも、最初の`/s`は、起動からキーを押して終わるまでの約2秒で、3〜4フレームしか描いていない。設定の上限は60fps。
  - 実行173だけは58フレームを描いた。
  - この傾向は、食べ物の追加の前からある。
- ログに出ないこと:
  - 製品は、ウィンドウごとに、描画の試みを最初の3回だけログに書く(`crates/app/src/diag.rs`の`first_few`。`LOGGED`は3。`crates/app/src/saver.rs`の750行目と835行目で使う)。
  - そのため、4回目以降の描画で、どこにどれだけ時間がかかったかは、ログに出ない。
- 1フレームの描画の流れ:
  - 描く先の画像を`get_current_texture`で受け取ってから、描いて表示する(`crates/app/src/render.rs`の`Target::draw`)。
  - 表示の方式はFifo(ログの`surface configured: ... Fifo`)。
  - 描画とキーの処理は、同じスレッドのイベントループで動く(`saver.rs`)。
- 当時の判断:
  - 実行171の1回目のあと、エージェントは、過去の実行の値を集めずに、1つの実行とだけ比べて推測を立てた(このセッションの作業の記録)。
  - 再実行で通ったことを、マージの判断の材料にした。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ同じ失敗が再発したか | 製品の側の原因が直っていないため。PR #78のときに原因を確かめず、再実行で通ったことを材料にマージした(PR #78のまとめコメント) |
| なぜ原因を確かめなかったか | 失敗を、1つ前の実行とだけ比べ、ランナーの遅さと推測したため。過去の実行の値を並べていれば、どの実行でも約2秒で3〜4フレームしか描かない傾向と、失敗は4フレーム目を描いた回だけという規則性が見えた(上の表) |
| なぜ過去の実行と並べなかったか | ときどきだけ失敗するCIの検査について、過去の実行の値を並べて比べる手順がないため(AGENTS.mdと`docs/development/review-process.md`には、ときどき失敗する検査の扱いの記述がない。2026-11-13に、両方のファイルで「再実行」を検索して確かめた。見つかるのは、PRを作ったあとの修正をまとめて1回でプッシュする手順の「重いCIの再実行を減らすため」だけ(AGENTS.mdの「PR・レビュー・マージ」の手順6と、`review-process.md`の42行目))。エージェントは、このセッションのPRの見守りの指示(リポジトリの外の、実行環境の指示)にある「ジョブの再実行は1回まで」に従って再実行し、通ったことを材料にした |
| なぜ推測のまま先に進めたか | 推測であることはメンテナーに示したが、「原因不明のまま回避策で迂回しない」(AGENTS.mdの「進め方」)に対して、再実行で通すことが回避策に当たると扱わなかったため |

## 真因

1. ときどきだけ失敗するCIの検査について、原因を調べる手順がない。過去の実行の値を並べて比べることが求められていない。そのため、1つの比較からの推測で判断してしまう。
2. 再実行で通ることを、原因の解決と区別する決まりがない。再実行は、原因を調べないまま失敗を迂回する回避策にもなる。

## 対策

1. 現象への対応:
   - `v0.3.0-alpha.3`のタグ付けを止めるよう、メンテナーに依頼した(2026-11-13)。
   - PR #80に、失敗がそのPRによるものでないことをコメントした。
   - 実行160〜175の値を集め、この記録に書いた。
2. 製品の原因の調べ方と直し方(2026-11-13にメンテナーが承認した): 終了のときの要約の行(`crates/app/src/diag.rs`)に、ウィンドウごとの、描く先の画像を待った最長の時間、表示にかかった最長の時間、1回の描画全体にかかった最長の時間を加える。当初は`v0.3.0-alpha.3`に入れてからタグを付ける予定だったが、タグはこの仕組みを含まないコミットに付いたため、`v0.3.0-alpha.4`に入れる(計画0005のD-19)。CIと実機の両方で、どこで待っているかを確かめる。直し方は、その値を見てから案を出す。
3. 真因1と2への対策(2026-11-13にメンテナーが承認した): AGENTS.mdの「PR・レビュー・マージ」に、次を加えた。
   - ときどきだけ失敗するCIの検査は、再実行で通っても、原因を確かめるまで解決としない。
   - 原因を調べるときは、その検査の値(時間、回数など)を、少なくとも直近の版からの実行で並べて比べ、表にして記録する。
   - 原因を確かめられないままマージするときは、その旨と、調べる作業を計画に登録したうえで、メンテナーの判断を得る。
   - この規則の差分の軽いレビューは、文の判定の基準(何をもって原因を確かめたとするか、並べる実行の範囲、表の記録先)、手順7の「CI全ジョブグリーン」と禁止の一覧との関係、登録先の計画が決まっていないことを指摘した。2026-11-13に、メンテナーの判断で、いまの文言のまま運用し、フェーズの区切りの整合性の確認で見直すことにした(計画0005の作業14に登録した)。
4. 仕組み: スモークテストの失敗の報告に、過去の実行の値を自動で並べる仕組みは加えない。理由: 過去の実行のログを集めるには、GitHubのAPIの権限と、ワークフローの変更(セキュリティ設定)が要る。3の手順の効果を見てから、改めて判断する。

## 確かめ方

- 以後、CIの検査がときどきだけ失敗したときに、過去の実行の値の表と、原因を確かめたかどうかが、記録されていること。
- 再実行で通ったことだけを材料に、原因の分からない失敗をマージしていないこと。
