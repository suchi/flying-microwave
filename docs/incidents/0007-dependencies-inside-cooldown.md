# 0007: 公開から7日たっていない依存の版を使った

- 日付: 2026-11-01
- ステータス: 対策済み(対策は`main`にマージした。2026-11-02に確かめた)

## 起きたこと

メンテナーが、手元の`cargo`の実行でも、Dependabotと同じ7日のcooldownが守られているかを尋ねた。確かめると、守られていなかった。

- 製品の`Cargo.lock`と2つのスパイクの`Cargo.lock`に、ロックファイルを作った時点(2026-10-31)で公開から7日たっていない版が、合わせて12個あった。たとえば`log` 0.4.35は2026-10-30の公開である。
- Windows向けのビルドに入っていたのは、次の版である。
  - 製品とsaver-spike: `log` 0.4.35、`ordered-float` 5.5.1、`unicode-width` 0.2.3
  - settings-spike: 上の3つと`accesskit` 0.25.2
- 残りの8つ(wasm-bindgenの系統の7つと`rustix`)は、ロックファイルに載るだけで、WindowsとLinuxのどちらのビルドにも入らない。
- メンテナーは、これらの版を含む実行ファイルを実機で動かした(スパイクの1回目から4回目の確認と、PR #21の成果物での確認)。
- ライセンス表記を作る`cargo-about` 0.9.3も、選んだ時点(2026-10-31)で公開から5日しかたっていなかった。
- プレリリース`v0.1.0-alpha.1`は、これらの版を含むコミットにタグが付けられた。配布物を作るCIの手動実行(57番)の途中で気づき、手動実行を取り消して、公開しなかった。

確かめた一次情報:

- `.github/dependabot.yml`。`cargo`と`github-actions`の`cooldown`は7日である。Dependabotが作る更新のPRにだけ効く。
- cargo 1.99.1の実行ファイル。`min-publish-age`の設定はあるが、`-Zmin-publish-age`(不安定版の機能)を求めるメッセージがある。このリポジトリは安定版を使っている。
- crates.ioの索引の`pubtime`(各版の公開日時)と、各ロックファイルを最初にコミットした日時。
- `cargo tree --target`による、各ターゲットのビルドに入るクレート。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ7日たっていない版を使ったか | エージェントが手元の`cargo`でロックファイルを作ったとき(スパイク、製品)、各版の公開日時を確かめなかったため。`cargo-about`の版を計画で選んだときも同じだった |
| なぜ確かめなかったか | 7日のcooldownはDependabotの設定としてだけ書かれていて、手元での依存の解決にも同じ決まりが要るとは、どこにも書かれていなかったため。AGENTS.mdのセキュリティの節にあるのは、`cooldown`を消さない決まりと、追加前に名前を確かめる決まりだけだった |
| なぜ仕組みで止まらなかったか | cargoの安定版には同じ設定がなく(`min-publish-age`は不安定版の機能)、CIにも公開日時を確かめる検査がなかったため |
| なぜ規則に欠けがあったか | サプライチェーン攻撃への対策を、Dependabotという1つの経路でだけ考え、依存の版がリポジトリに入る経路(手元の`cargo update`・`cargo add`・新しいロックファイル、CIの`cargo install`)を洗い出さなかったため |

## 真因

依存の版がリポジトリやビルドに入る経路を洗い出さず、7日の決まりをDependabotの経路にだけ設けていたこと。

## 対策

1. 検査のスクリプト(`scripts/check_publish_age.py`)を加えた。ロックファイルのcrates.ioのすべての版と、指定した追加の版の公開日時を、crates.ioの索引で確かめる。7日たっていない版があるとき、索引に版が見つからないとき、索引を読めないときは、失敗にする。
2. CIで検査を行う。
   - `ci.yml`のLinuxのジョブ(必須のチェック): PR、`main`へのプッシュ、手動実行のたびに行う。対象は、3つのロックファイル、CIで入れる`cargo-about`の版、そのパッケージに含まれるロックファイルである(`cargo install --locked`は、このロックファイルを使う)。配布物を作るWindowsのジョブは、このジョブが成功してから始まる(`needs: linux`)。
   - `spikes.yml`: ビルドの前に、2つのスパイクのロックファイルを検査する。
   - 検査は、`pubtime`のない版や、crates.io以外から来る依存(gitなど)も、失敗にする。
3. AGENTS.mdのセキュリティの節に、決まりを加えた。依存(間接の依存とCIで入れるツールを含む)は、公開から7日以上たった版だけを使う。手元でロックファイルを変えたときは、コミットの前に検査を実行する。検証コマンドの表にも加えた。
4. 7日たっていなかった版を、7日以上前に公開された1つ前の版に下げた(`log` 0.4.34、`ordered-float` 5.5.0、`unicode-width` 0.2.2、wasm-bindgenの系統 0.2.129など、`rustix` 1.1.5、settings-spikeの`accesskit` 0.25.1、`cargo-about` 0.9.2)。プレリリースは`v0.1.0-alpha.2`として出し直す。`v0.1.0-alpha.1`は公開しない。
5. この検査の対象は、crates.ioのクレートだけである。次の2つは対象にしていない。
   - GitHub Actions: SHAで固定していて、更新はDependabotの`cooldown`の対象になる。いま使っている版は、2026-10-31から11-01に手で固定したもので、そのときには公開日時を確かめていなかった。2026-11-01に、次のとおり確かめた。3つとも、固定した時点で7日の決まりを満たしていた。手で版を変えるときも、7日以上前の版を選び、SHAで固定する(AGENTS.mdの決まりの「CIで入れるツール」に含まれる)。

     | Action | 版 | 公開日(メンテナーがGitHubのリリースで確かめた) | ワークフローのSHAとタグの一致(`git ls-remote`で確かめた) |
     | --- | --- | --- | --- |
     | actions/checkout | v7.0.1 | 2026-07 | 一致(`3d3c42e5`) |
     | Swatinem/rust-cache | v2.9.3 | 2026-10-20 | 一致(注釈付きのタグが指すコミット`d1527c8f`) |
     | actions/upload-artifact | v7.0.2 | 2026-10-02 | 一致(`cf430e03`) |
   - Rustのツールチェーン(`rust-toolchain.toml`の1.99.1): 2026-10-15に公開され、10-31に固定したので、7日の決まりを満たしている。更新するときは、公開日を確かめる。

## 確かめ方

- CIのLinuxのジョブの「Check dependency cooldown」が、毎回成功すること。7日たっていない版を入れると、失敗すること。
- 手元でロックファイルを変えたPRの記録に、検査の結果があること。
