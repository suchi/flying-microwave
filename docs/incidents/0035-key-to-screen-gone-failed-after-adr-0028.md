# 0035: ADR-0028の直し方のあとも、F-01のキーから画面が消えるまでが上限を超えた

- 日付: 2026-11-19
- ステータス: 対策中(原因を調べる作業と、対策の案は、メンテナーの判断を待っている)
- 関連: [0028](0028-smoke-failure-merged-on-a-guess.md)(同じF-01の失敗)、[0033](0033-exit-time-near-limit-unnoticed.md)(同じPRのCIで見つかった、終了の遅さ)、[ADR-0028](../adr/0028-wait-for-swap-chain-at-most-one-frame.md)、[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)の作業10の4、PR #88

## 起きたこと

2026-11-19に、PR #88(文書と開発の道具だけの変更)のCI(実行203、head `ca4765b`)で、Windowsのスモークテストの`F-01 /s ends on user input with a broken settings file`が失敗した。キーを押してから画面が消えるまでが396msで、上限の200msを超えていた。incident 0028で扱った失敗と同じ種類で、その直し方(ADR-0028。PR #82)を入れたあとの失敗である。

確かめた事実(実行203のWindowsのジョブのログ):

- スモークテストの行: `input to screen gone: 396 ms; to process exit: 1937 ms`。同じ実行のF-02は`parent destroyed to exit: 1994 ms`で通った(上限2000ms)。
- プロセス968のログ:
  - `+708ms`に`first frame presented`、`+841ms`〜`+920ms`に`frame skipped: NotReady`(最初の3回だけが書かれる。`crates/app/src/diag.rs`の`first_few`)。
  - `+1999ms`に`exit: KeyPressed`、`+2157ms`にウィンドウの要約の行、`+3735ms`に`screensaver ended`。
  - 要約の行: `25 draws attempted, 3 frames, 2 paced, 0 blank, 20 skipped (… NotReady 20 …); 1 drawn without signal; longest surface wait 304 ms, longest present 0 ms, longest draw 309 ms`。
- `longest surface wait`は、合図を待ち始めてから`get_current_texture`が戻るまでの時間の最長である(`crates/app/src/render.rs`の`Target::draw`の`self.timings.wait = waited.elapsed()`、`saver.rs`の`w.stats.timed`)。合図の待ちは最大1フレーム(ADR-0028の(2))なので、304msのほとんどは`get_current_texture`の中か、合図なしで描いた回(ADR-0028の(3))の取得でかかったと考えられる。ただし、ログには最長の値しか出ず、どの回で304msだったか、その回がキーの前後のどこにあったかは、ログから分からない。
- wgpuには待機オブジェクトで待たせない設定にしている(`render.rs`の`create_instance`の`DontWait`)。それでも`get_current_texture`が待ちうるかは、wgpuとDXGIのソースで確かめていない。
- ADR-0028の「結果」は、キーの処理が待たされるのを「最大で、1フレーム分(ミリ秒に切り上げ)×モニターの数に、描画そのものの時間(取得、送信、表示)を足した時間」としている(「結果」の58行)。取得に300ms近くかかる場合は、この見積もりの中の「描画そのものの時間」が大きくなる。

## なぜなぜ分析

1. なぜF-01が失敗したか。
   - キーを押してから画面が消えるまでが396msだった。同じプロセスで、1回の描画(取得を含む)に最長309msかかっている。
   - キーの処理がその描画のあとまで待たされた可能性があるが、ログからは確かめられない(上の事実)。
2. なぜ1回の描画に300ms近くかかったか。
   - 記録がなく分からない。取得(`get_current_texture`)の待ちと考えられるが、取得が待つ条件をwgpuとDXGIのソースで確かめていない。
3. なぜ、ADR-0028の直し方で、この待ちが残ることに気づかなかったか。
   - ADR-0028は、wgpuの待機オブジェクトでの待ちをなくすことを直し方とし、取得そのものの待ちは調べていない(ADR-0028の「背景」と「決定」)。PR #82のCIで通ったことを確かめたが、取得の時間の分布は記録していない。
4. 真因(暫定): 取得の時間がどれだけかかりうるかを確かめないまま、キーの処理の待ちの上限を見積もった。調べる作業を終えるまで、真因は確定しない。

## 真因

暫定。上の4。後始末の遅さ(incident 0033)と同じく、WARPでの取得と後始末の時間が、どこで、なぜかかるかを確かめていない。

## 対策

案(メンテナーの判断を待っている):

1. 調べる作業(計画0005の作業10の4に加える): 取得(`get_current_texture`)と後始末の各段の時間を、回ごとにログに書く(最初の数回と、長かった回)。あわせて、取得が待つ条件を、wgpuとDXGIのソースと文書で確かめる。製品のコードの変更なので、設計を報告してから行う。
2. 記録: incident 0028のステータス(対策済み)の文に、この記録へのリンクを書き添える。0028の真因への対策(値を並べて比べる規則)は効いていて、製品の直し方(ADR-0028)が十分でなかったことを示すため。
3. 判断していただくこと: ADR-0028の直し方を見直すか(調べる作業の結果を見てから決める)。

## 確かめ方

- 対策1: CIのログに、取得と後始末の各段の時間が出ていること。それを並べた表で、キーの処理が待たされる時間を説明できること。
- F-01とF-02が、続けて10回のCIの実行で通ること(調べたうえで直したあと)。
