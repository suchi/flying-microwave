# 0035: ADR-0028の直し方のあとも、F-01のキーから画面が消えるまでが上限を超えた

- 日付: 2026-11-19
- ステータス: 対策中(2026-11-20に、メンテナーが対策の(1)と(2)を推奨どおりと判断した。計画0005のD-23。(1)のログとスモークテストの出力は、2026-11-22にPR #94でマージした。そのうち後始末の各段の時間は、PR #94の実行(44913003558)とmainの実行(44948887108)で出て、incident 0033の「その後の再発」の表に載せた。その後、終了で描画先とGPUを破棄しないことにしたため(計画0005のD-34、[ADR-0029](../adr/0029-leave-gpu-resources-to-process-exit.md))、以後は出ない。取得が待つ条件の確かめと(3)は、作業10の4の結果を見て決める)
- 関連: [0028](0028-smoke-failure-merged-on-a-guess.md)(同じF-01の失敗)、[0033](0033-exit-time-near-limit-unnoticed.md)(同じPRのCIで見つかった、終了の遅さ)、[ADR-0028](../adr/0028-wait-for-swap-chain-at-most-one-frame.md)、[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)の作業10の4、PR #88

## 起きたこと

2026-11-19に、PR #88(文書と開発の道具だけの変更)のCI(実行203、head `ca4765b`)で、Windowsのスモークテストの`F-01 /s ends on user input with a broken settings file`が失敗した。キーを押してから画面が消えるまでが396msで、上限の200msを超えていた。incident 0028で扱った失敗と同じ種類で、その直し方(ADR-0028。PR #82)を入れたあとの失敗である。

確かめた事実(実行203のWindowsのジョブのログ):

- スモークテストの行: `input to screen gone: 396 ms; to process exit: 1937 ms`。同じ実行のF-02は`parent destroyed to exit: 1994 ms`で通った(上限2000ms)。
- プロセス968のログ:
  - `+708ms`に`first frame presented`、`+841ms`〜`+920ms`に`frame skipped: NotReady`(最初の3回だけが書かれる。`crates/app/src/diag.rs`の`first_few`)。
  - `+1999ms`に`exit: KeyPressed`、`+2157ms`にウィンドウの要約の行、`+3735ms`に`screensaver ended`。
  - 要約の行: `25 draws attempted, 3 frames, 2 paced, 0 blank, 20 skipped (… NotReady 20 …); 1 drawn without signal; longest surface wait 304 ms, longest present 0 ms, longest draw 309 ms`。
- `longest surface wait`は、合図を待ち始めてから`get_current_texture`が戻るまでの時間の最長である(`crates/app/src/render.rs`の`Target::draw`の`self.timings.wait = waited.elapsed()`、`saver.rs`の`w.stats.timed`)。最長の値は、最初の3回の描画の試みを除いて取る(`crates/app/src/diag.rs`の`FrameStats::timed`)。そのため、304msの回は4回目以降(`+758ms`の3回目より後)である。それより細かく、どの回か、キーの前後のどこにあったかは、ログから分からない。
- キーから画面が消えるまでの396msの内訳(2つの時計は、同じ機械の`Instant`。製品は`crates/app/src/log.rs`の`start`から、スモークテストはキーを送った直後(`crates/smoke/src/windows.rs`の343行の`send_key`のあと、373行の`start`)から計る):
  - プロセスが終わるのは、`screensaver ended`(`+3735ms`。`saver.rs`の`run`で、`run_app`が戻ったあとに書く)より後である。スモークテストの`to process exit: 1937 ms`も同じ起点から計るため、起点は製品の時計で`+1798ms`(3735 − 1937)以降である。
  - 製品は、`exit:`の行(`+1999ms`)を書いた直後に窓を隠す(`saver.rs`の`decide`の338行と346行の`set_visible(false)`)。したがって、キーを送ってから製品が窓を隠すまでは、多くとも約201msだった。
  - スモークテストが画面が消えたと判定したのは、起点から396ms、つまり`+2194ms`以降で、窓を隠してから少なくとも約195ms後である(判定は2msごと。`windows.rs`の`POLL`)。要約の行(`+2157ms`、`exiting`の始め)よりも後である。
  - したがって、396msのうち少なくとも約195msは、製品が窓を隠したあと、スモークテストが消えたと判定するまでにかかった。窓が見えなくなるのが遅れたのか、スモークテストの確かめが遅れたのか(アダプターはCPUで描くWARP)は、ログから分からない。304msの描画がキーの処理を遅らせたという見方だけでは、この部分を説明できない。
- wgpuには待機オブジェクトで待たせない設定にしている(`render.rs`の`create_instance`の`DontWait`)。それでも`get_current_texture`が待ちうるかは、wgpuとDXGIのソースで確かめていない。
- 推測(根拠は上の2つの箇条): 304msは、`get_current_texture`の中の待ちか、合図なしで描いた回(ADR-0028の(3))の取得か、CPUで描くWARPでスレッドが待たされたことによる。どれかは確かめていない。
- ADR-0028の「結果」は、キーの処理が待たされるのを「最大で、1フレーム分(ミリ秒に切り上げ)×モニターの数に、描画そのものの時間(取得、送信、表示)を足した時間」としている(「結果」の58行)。取得に300ms近くかかる場合は、この見積もりの中の「描画そのものの時間」が大きくなる。

- 実機(NVIDIA GeForce RTX 5060 Ti、リモートデスクトップ)の`v0.3.0-alpha.4`の確認(結果は2026-11-21に受け取った)では、全画面の14回の要約の行が、すべて`0 drawn without signal`で、合図なしで描いた回はなかった([手順書](../development/hardware-check-v0.3.0-alpha.4.md)の「結果」)。キーから画面が消えるまでの時間は、実機では測れない。
## なぜなぜ分析

1. なぜF-01が失敗したか。
   - キーを押してから画面が消えるまでが396msだった。そのうち、キーを送ってから製品が窓を隠すまでは多くとも約201ms、窓を隠してからスモークテストが消えたと判定するまでは少なくとも約195msだった(上の事実の内訳)。
2. なぜ、それぞれに時間がかかったか。
   - 記録がなく分からない。前半は、キーの前にあった描画(最長309ms)を待った可能性がある。後半は、窓が見えなくなるまでの遅れか、スモークテスト側の遅れの可能性がある。どれも、ログからは確かめられない。
3. なぜ、ADR-0028の直し方で、この待ちが残ることに気づかなかったか。
   - ADR-0028は、`get_current_texture`の中の待ちの経路をwgpuのソースで調べたが(「背景」の12〜13行)、待ちの時間は測っておらず(「結果」の58行の「実際の待ちの時間は測っていない」)、待機オブジェクト以外の待ちと、窓を隠してから見えなくなるまでの時間は調べていない(`grep -n '隠\|set_visible\|IsWindowVisible' docs/adr/0028-*.md`で0件)。
4. 真因(暫定): キーから画面が消えるまでの時間の内訳(キーの処理の待ち、窓が見えなくなるまで、スモークテストの確かめ)を測らないまま、キーの処理の待ちの上限だけを見積もった。調べる作業を終えるまで、真因は確定しない。

## 真因

暫定。上の4。後始末の遅さ(incident 0033)と同じく、WARPでの取得、窓を隠してから見えなくなるまで、後始末の時間が、どこで、なぜかかるかを確かめていない。

## 対策

2026-11-20に、メンテナーが(1)と(2)を推奨どおりと判断した(計画0005のD-23)。(1)は計画0005の作業10の4で行う。(2)は、D-23を記録した変更で行った。(3)は、作業10の4の結果を見て決める。

案:

1. 調べる作業(計画0005の作業10の4に加える): 取得(`get_current_texture`)と後始末の各段の時間を、回ごとにログに書く(最初の数回と、長かった回)。窓を隠してから見えなくなるまで(`set_visible(false)`から`IsWindowVisible`が偽になるまで)の時間も、製品とスモークテストの両方で測る。あわせて、取得が待つ条件を、wgpuとDXGIのソースと文書で確かめる。製品のコードとスモークテストの変更なので、設計を報告してから行う。
   - 2026-11-21に、メンテナーが、窓を隠す時間は、製品では`set_visible(false)`の呼び出しの時間だけを測り、見えなくなるまではスモークテストのいまの判定(入力から画面が消えるまで)で見ることにした(計画0005のD-25の(2))。製品の側で見えなくなるのを待つと、終了がそのぶん遅くなるため。
   - 実装(計画0005のD-24の(6)、D-33): 取得の時間は、100msより長くかかった回を、窓ごとに最初の5回だけ書く(最初の数回の取得の時間は書かない)。後始末は、始まりの行と、各段の時間をまとめた行を書く。スモークテストは、これらの行を、通ったケースでも失敗したケースでも出力に出す。
2. 記録: incident 0028のステータス(対策済み)の文に、この記録へのリンクを書き添える。0028の真因への対策(値を並べて比べる規則)は効いていて、製品の直し方(ADR-0028)が十分でなかったことを示すため。
3. 判断していただくこと: ADR-0028の直し方を見直すか(調べる作業の結果を見てから決める)。

## 確かめ方

- 対策1: CIのログに、取得と後始末の各段の時間と、窓を隠す呼び出しの時間(製品のログ)と、入力から画面が消えるまでの時間(スモークテスト)が出ていること(D-25の(2)で、窓を隠してから見えなくなるまでを製品では測らないことにしたため)。取得の時間は、100msより長くかかった回だけが出る(D-24の(6))。スモークテストの出力には、通ったケースでも出る(D-33の(2))。後始末の各段の時間は、ADR-0029(D-34)のあとは出ないため、PR #94とmainの2回の実行の値(incident 0033の「その後の再発」の表)で確かめたものとする。それを並べた表で、キーから画面が消えるまでの時間の内訳を説明できること。
- F-01とF-02が、続けて10回のCIの実行で通ること(調べたうえで直したあと)。
