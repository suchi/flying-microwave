# 異常の記録(なぜなぜ分析)

- ステータス: 採用(2026-11-01)
- 関連: [AGENTS.md](../../AGENTS.md)の「進め方」

開発の中で起きた異常について、真因と対策を記録する。目的は再発の防止である。

## 異常への対応の手順

トヨタ生産方式では、異常が起きたら止めて異常を明らかにし(自働化)、「なぜなぜ」を繰り返して真因を追求し、対策を講じる。本プロジェクトの手順はこれに倣う。

1. 止める: 異常に気づいたら、その作業をそのまま進めず、ユーザーに知らせる。知らせたあとは、ユーザーが止めるよう指示しない限り、記録と対策を含めて作業を続ける。ただし、対策のうち承認が要るもの(規則や仕組みの変更、セキュリティ設定など)は、案と質問を示すところまで進める(手順4)。知らせた異常(要約と記録の場所)と判断が要る点は、そのターンの最後の報告にも書き、判断を待たずに進められる作業を先に進める(2026-11-10にメンテナーが指示した)。異常とは、規則や手順が守られなかったこと、規則や手順に欠けがあったこと、同じ種類の問題の再発、ユーザーが異常として指摘したこと、ユーザーが、完了として渡した成果物(マージ済みの`main`の内容、公開したリリース)の欠けや誤りを指摘したこと(質問の形のものを含む)である。PRのレビュー(人間のレビューを含む)での通常の指摘は、異常に含めない。ただし、指摘の中身が、規則や手順が守られなかったことや、同じ種類の問題の再発に当たるときは、異常として扱う(指摘を受けたら、異常の定義と照らし合わせる。[0025](0025-implemented-against-recorded-decision.md))。レビューの通常の指摘や、予定どおりの失敗(TDDのRed)は、通常の手順で扱う。
2. 事実を確かめる: 何が起きたかを、ログ・ソース・設定・公式ドキュメントなどの一次情報で確かめる。推測は推測として分ける。記録がないことは、なかったことの根拠にしない。メンテナーが知っている事実(メンテナーの環境や過去の操作など)は、推測せずに尋ねる([0024](0024-unfounded-guess-as-premise.md))。
3. なぜなぜ分析: 「なぜ」を繰り返し、対策を打てば再発しなくなる原因(真因)までさかのぼる。各段の答えは、確かめた事実で書く。
4. 真因に対策する: 目の前の現象を直すだけで終わらせない。規則・手順・仕組みのどれを変えれば同じ種類の異常が起きなくなるかを考え、ユーザーの承認を得て変える。規則の文言を変えるだけの対策は、守られなければ効かない。機械的に確かめる仕組み(フック、CIの検査など)を検討し、採らない場合はその理由を記録する。
5. 記録する: この一覧に、番号付きで記録する。記録の前に、なぜなぜ分析の各段の答えに、確かめた方法(ファイル、コマンド、メンテナーの指摘など)が書かれているかを見直す。書けない答えは、推測として根拠を添えるか、分からないと書く([0024](0024-unfounded-guess-as-premise.md))。出典として挙げたファイルや文書は、開いて該当箇所を確かめたかも見直す(書かれた出典を、開かずに書いていないか。[0024](0024-unfounded-guess-as-premise.md)の「その後の確認」)。記録したあとで、`python3 -I -m unittest discover -s scripts`を実行し、一覧のテスト(`scripts/test_incident_lists.py`)が通ることを確かめる(文書だけの変更でも行う。[0026](0026-incident-row-placed-in-procedure.md))。

## 記録の書き方

ファイル名は`NNNN-<異常の要約>.md`(4桁の連番。要約は英語のkebab-case)。本文には次を書く。

- 起きたこと: 日付、現象、気づいたきっかけ。
- なぜなぜ分析: 各段の「なぜ」と答え(確かめた事実)。
- 真因: 対策の対象とした原因。
- 対策: 変えた規則・手順・仕組みと、その変更(PR)。
- 確かめ方: 対策が効いたことを、何で確かめるか。できるだけ客観的に確かめられる方法にする。
- ステータス: 「対策中」(対策がまだマージされていない)か「対策済み」。ただし、Claude Codeの実行時の振る舞いに頼るフックの対策は、そのPRのマージのあとで最初に始めるセッションで、Claude Codeから起動されたフックが期待どおり働くことを確かめるまで「対策中」とする([0022](0022-note-hook-reads-transcript-too-early.md))。
