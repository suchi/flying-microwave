# 0034: incidentを記録したコミットで、手順が求める一覧のテストを実行しなかった

- 日付: 2026-11-19
- ステータス: 対策中(2026-11-20に、メンテナーが対策の(1)〜(3)を推奨どおりと判断した。計画0005のD-23。(1)と(3)はPR #89、(2)はPR #90でマージした。(2)の方式は計画0005のD-26の(1)。(2)のフックは、Claude Codeがフックを動かす時点(コマンドの実行の前)に頼るため、マージのあとで新しく始めたセッションで働くことを確かめてから対策済みにする(計画0005のD-29の(2))。下の「その後の確認」。2026-11-23の再発(下の「その後の再発(2026-11-23)」)の追加の対策(計画0005のD-43)は、作業10の10のPR(PR #102)で行い、マージされるまでは対策済みにしない)
- 関連: [0026](0026-incident-row-placed-in-procedure.md)(一覧のテストを手順に加えたincident)、[0033](0033-exit-time-near-limit-unnoticed.md)(この異常が起きた記録の作業)

## 起きたこと

2026-11-19に、incident 0033を記録したコミット(`3a9db20`)で、エージェントは、スクリプトのテスト(`python3 -I -m unittest discover -s scripts`)を実行しないままコミットした。`docs/README.md`の一覧に0033の行を加え忘れていて、一覧のテスト(`scripts/test_incident_lists.py`の`test_the_docs_readme_lists_every_record`)が失敗する状態だった。プッシュの前の軽いレビューで見つかった。

確かめた事実:

- `docs/incidents/README.md`の手順5は、「記録したあとで、`python3 -I -m unittest discover -s scripts`を実行し、一覧のテスト(`scripts/test_incident_lists.py`)が通ることを確かめる(文書だけの変更でも行う。[0026])」と定めている。
- AGENTS.mdの「検証コマンド」の節は、「コミット前に必ずテスト・リントを実行する。ドキュメントだけの変更(Rustのコード・Cargoの設定・ワークフローを変えないもの)では不要とする」と書いている。incidentの記録を例外とすることは、AGENTS.mdには書かれていない(`grep -n 'test_incident_lists' AGENTS.md`で0件)。
- エージェントは、記録を書く前に`docs/incidents/README.md`を読んだが、`sed -n 1,60p ... | cut -c1-300`で、各行を300文字で切って読んだ(このセッションのコマンド)。その行(手順5)は438文字で、テストの文の始まり(「記録したあとで」)は269文字目にある。GNU coreutilsの`cut -c`はバイト単位で切るため(この環境で`printf 'あいう\n' | cut -c1-3`は「あ」だけを出す)、読めたのは先頭の300バイト、和文で約100文字だけだった。テストの文は640バイト目付近から始まり、読んだ範囲に入っていなかった。
- コミットのときは、AGENTS.mdの「文書だけの変更では不要」に従い、テストを実行しなかった。
- CIは、スクリプトのテストを実行する(`.github/workflows/ci.yml`のWindowsのジョブの`Script tests`の手順)。プッシュしていれば、CIで失敗していた。

## なぜなぜ分析

1. なぜテストを実行しなかったか。
   - 文書だけの変更と考え、AGENTS.mdの「不要とする」に従ったため。
2. なぜ手順5の例外に従わなかったか。
   - 手順を、行を300文字で切るつもりで`cut -c1-300`で読んだが、`cut -c`はバイト単位で切るため、実際には約100文字しか読んでおらず、例外の文を読んでいなかった。
3. なぜ、切って読んでも例外に気づけなかったか。
   - 例外が`docs/incidents/README.md`の手順5の長い行の終わりにだけ書かれていて、エージェントがコミットのときに従うAGENTS.mdの検証の節には書かれていないため。2か所の書き方が違い、AGENTS.mdだけを見ると「不要」と読める。
4. なぜ仕組みで止まらなかったか。
   - コミットの前にテストを強制する仕組み(gitのフックやClaude Codeのフック)がない。CIは、プッシュしたあとでしか動かない。

## 真因

- 文書だけの変更でテストを行う例外が、手順の文書の中にだけあり、コミットのときに従う規則(AGENTS.md)には書かれていない。
- incidentの記録のコミットで、テストを実行させる仕組みがない。

## 対策

2026-11-20に、メンテナーが(1)〜(3)を推奨どおりと判断した(計画0005のD-23)。(1)と(3)は、2026-11-20の記録の変更で、AGENTS.md(検証の節と表、「情報源」の節)と`.claude/commands/commit.md`に加えた。`docs/development/onboarding.md`と`.claude/commands/babysit-pr.md`の同じ説明への書き添えと、(2)のフックは、計画0005の作業10の5で行う。

行ったこと(計画0005の作業10の5):

- (2): `block-dangerous-git.sh`は、`git commit`のときに、`docs/incidents/`か`docs/README.md`に変更があれば、一覧のテストを実行し、失敗したらコミットを止める。Pythonが動かない環境では止めない。`scripts/check_hooks.py`に、一覧にない記録があるときに止まり、ないときは通ることを試す入力を加えた。変更があるかどうかは、承認された案(ステージした変更)と違い、作業ツリー全体で見ている。この違いを確かめずに実装したため、[0040](0040-hook-implemented-against-reported-design.md)に記録した。2026-11-21に、メンテナーが作業ツリー全体で見る方式に決めた(計画0005のD-26の(1))。
- `docs/development/onboarding.md`と`.claude/commands/babysit-pr.md`への書き添えは、作業10の5で行った。

案:

1. 規則: AGENTS.mdの「検証コマンド」の節の「ドキュメントだけの変更…では不要とする」に、「ただし、`docs/incidents/`と`docs/README.md`を変えるときは、スクリプトのテストを実行する(`docs/incidents/README.md`の手順5)」と書き添える。
2. 仕組み: `block-dangerous-git.sh`で、`git commit`のときに、ステージした変更に`docs/incidents/`か`docs/README.md`が含まれていれば、一覧のテスト(`python3 -I -m unittest scripts/test_incident_lists.py`の形)を実行し、失敗したらコミットを止める。フックの変更なので、承認が要る。フックが重くなりすぎないかは、試して確かめる。
3. 読み方: 規則と手順の文書は、行を切らずに読む(Readのツールで読む)。`cut -c`は和文をバイト単位で切り、読んだつもりの範囲より狭くなるため。エージェントの作業の仕方で、規則にするかどうかは判断していただくこと。

## 確かめ方

- 対策1: AGENTS.mdの検証の節に、例外の文があること。
- 対策2: `scripts/check_hooks.py`の試験の入力で、一覧のテストが失敗する状態の`git commit`が止まること。
- このあとのincidentの記録のコミットで、一覧のテストが失敗したまま入っていないこと(CIの`Script tests`の結果)。

## その後の確認

- 2026-11-21に、PR #90のマージのあとで、Claude Codeから起動されたフックを試した。一覧にない仮の記録を置いた状態の`git commit --dry-run`は、フックが拒否した。対策2の試験の入力は、PR #90の`scripts/check_hooks.py`にあり、CIで通った。
- ただし、仮の記録を作る`echo`と`git commit`を1つのコマンドでつないだときは、止まらなかった。フックはコマンドの実行の前に動くため、同じコマンドの中で作ったり変えたりした記録と一覧の変更は見えない。この制約は、`docs/development/onboarding.md`の6.3の説明に書いた。2026-11-21に、メンテナーがこの取りこぼしを受け入れた(計画0005のD-28。CIのスクリプトのテストで見つかるため)。
- 確かめたのは、PR #90のマージ(2026-11-21 11:12(JST))の前から会話が続いていたセッションである(マージのあとに作業プロセスの再起動はあった)。このフックは、Claude Codeがフックを動かす時点(コマンドの実行の前)に頼るため、AGENTS.mdの「検証コマンド」の節の規則のとおり、マージのあとで新しく始めたセッションで、一覧にない記録を置いた状態のコミットが止まることを確かめてから、対策済みにする(2026-11-21のメンテナーの判断。計画0005のD-29の(2))。

## その後の再発(2026-11-23)

2026-11-23 21:36(JST)に、作業10の10のブランチのレビューの指摘(M-1)を確かめるとき、エージェントは、`grep -n 'TZ=Asia/Tokyo date' AGENTS.md .claude/commands/commit.md ... | cut -c1-80`で、規則の文書の行を切って表示した。AGENTS.mdの「情報源」の節(規則と手順の文書は、行を切らずに読む。`cut -c`などで行を切って読まない)に反するので、異常に当たる。実行した直後に出力を見て気づいた。

確かめた事実:

- そのコマンドは、行番号を探すためのものだった。指摘の中身は、AGENTS.mdの37行目と表の176〜177行目をReadのツールで切らずに読んで確かめた(このセッションの作業の記録)。
- この規則は、PR #89のマージ(2026-11-20 23:53 JST。マージのコミット`ddfe8db`の日時)でAGENTS.mdに入った。それ以降の会話の記録で、規則の文書(AGENTS.md、`.claude/commands/`、`docs/incidents/README.md`、`docs/development/`など)の行を`cut -c`で切ったBashの呼び出しを数えると、19回あった(会話の記録のJSONLを、Pythonのスクリプトで読み、`cut -c`へのパイプと規則の文書のパスを含むコマンドを選んだ)。19回とも`grep -n`で行の場所や有無を探したもので、`sed`や`cat`で中身を切って読んだものはなかった。
- 19回のそれぞれで、切った出力を判断に使ったかどうかは、1件ずつは確かめていない。

なぜなぜ分析:

1. なぜ、規則の文書を`cut -c`で切ったか。
   - 長い行の`grep`の出力を短くして、行番号だけを見ようとした(実行したコマンド)。
2. なぜ、規則があるのに続いていたか。
   - 規則は「読む」ときの決まりとして書かれていて、エージェントは、`grep`で場所を探すことを「読む」に当たらないと扱っていた(推測。根拠は、19回とも`grep`で、中身を読む`sed`や`cat`は0回だったこと)。場所を探したあとで、同じ行を切ったまま判断に使えば、最初の発生と同じことが起きうる。
3. なぜ、5日間気づかなかったか。
   - 規則に反した形を機械的に見つける仕組みがない。最初の発生の対策の3は、エージェントの作業の仕方として規則に書いただけである。
4. 真因: 規則の文が「読む」に限られていて、場所を探すときに切ることが許されるかが曖昧である。規則に反した形を見つける仕組みがない。

対応: 以後は、場所を探すときも`cut -c`を使わず、`grep -c`、`grep -l`、`grep -o`(一致した部分だけ)を使う。追加の対策は、2026-11-23に、メンテナーが次の案1と案2を採った(計画0005のD-43。PR #102で行う)。

1. 仕組み(推奨): `.claude/hooks/block-dangerous-git.sh`に、`cut -c`へのパイプがあり、規則の文書のパスを含むBashのコマンドを止める検査を加える。止めるメッセージで、`grep -c`、`grep -l`、`grep -o`かReadのツールを使うよう示す。`scripts/check_hooks.py`にサンプル入力を加える。
2. 規則: AGENTS.mdの「情報源」の節の文を、場所を探すときも含めて行を切らないことと、代わりの書き方(上の`grep`の形)に改める。1と合わせて行う。
