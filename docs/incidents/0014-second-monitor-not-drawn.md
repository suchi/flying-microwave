# 0014: 2台目のモニタに電子レンジが描かれないまま、リリースした

- 日付: 2026-11-04
- ステータス: 対策中(原因の確定と、対策のPRがまだ)
- 関連: Issue #50、[スパイクの結果](../research/spike-results.md)のS4と3回目、[計画0001](../plans/0001-initial-implementation-plan.md)のF-01と8.2の6、[v0.1.1の手順書](../development/hardware-check-v0.1.1.md)のE、[計画0004](../plans/0004-v0.2.0-settings.md)のD-11

## 起きたこと

2026-11-04に、メンテナーが公開した試作版`v0.2.0-alpha.1`を2画面の環境で実行し、電子レンジが主画面にしか表示されないと指摘した。計画0001のF-01は「全モニタを覆う」ことを求めており、公開したリリースの欠けにあたる。

確かめた事実:

- 製品のコードは、`display.monitors`が`all`(既定値)なら、すべてのモニタのウィンドウに描画先を作り、描くたびにウィンドウごとに再描画を求める(`crates/app/src/saver.rs`)。
- Phase 0のスパイクの3回目(2026-11-01)の記録には、「2台目のモニタのウィンドウのフレームの行は、ログに出ていない」とあり、それを「ログに出るのはウィンドウごとの最初の数フレームなので、2台目で描画できたかはログからは分からない」と解釈していた。しかし、スパイクは、ウィンドウごとに最初の3フレームをログに書く作りである(`spikes/saver-spike/src/saver.rs`の`w.frames <= 3`)。2台目の行がないことは、2台目のウィンドウが1フレームも描かなかったことを示していた(元のログはリポジトリにないため、記録の文と、スパイクのコードからの推定)。
- v0.1.0は、実機での確認をしないまま出した(計画0001のD-30)。v0.1.1の実機での確認では、複数モニタの項目(手順E)は「環境がある場合」の任意の項目で、項目ごとの結果は受け取っていない(Issue #47)。
- CIとリリースのワークフローのランナーはモニタが1つで、スモークテストでは2台目を確かめられない。

原因はまだ確定していない(Issue #50)。候補は次のとおり。

- 設定の`Primary only`が残っていた。ただし、Phase 0のスパイクには設定の機能がないのに、3回目で2台目が描かなかったので、この候補だけではスパイクの症状を説明できない。
- 再描画の順番が2台目に回らない(推測)。winit 0.30.13のWindowsの実装(`platform_impl/windows`)では、`request_redraw`は`RedrawWindow(RDW_INTERNALPAINT)`で再描画の印を付け、`RedrawRequested`は`WM_PAINT`の処理の中で送る。`RedrawRequested`を1回送るたびに、メッセージの処理を打ち切る(`dispatch_peeked_messages`の`interrupt_msg_dispatch`)。製品もスパイクも、描画の直後に同じウィンドウの`request_redraw`を呼ぶ。そのため、2つのウィンドウにいつも印が付いた状態になり、どちらの`WM_PAINT`が先に取り出されるかはWindowsに任される。その順番は、Win32の文書では決まっていない(一次情報で確かめていないのは、Windowsが実際に主画面のウィンドウを選び続けるかである)。
- 2台目のウィンドウでサーフェスを作れなかった。`v0.2.0-alpha.1`のログでは、`surface setup failed`の行にウィンドウの番号がないため、どのウィンドウかは分からない(このブランチで番号を付けた)。

メンテナーのログの`settings:`の行(`monitors`の値)と、`window 1: first frame presented`・`surface setup failed`の行の有無で、これらを切り分ける。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ2台目に描かれない版を、リリースしたか | 2台目のモニタで描けることを、どの段階でも確かめていなかったため |
| なぜPhase 0のスパイクで見つけられなかったか | 3回目のログには、2台目が描かなかったことを示す事実(フレームの行がない)があったが、記録の際に、スパイクのログの書き方をコードで確かめず、「ログからは分からない」と解釈したため |
| なぜ「分からない」のまま先に進んだか | S4を「一部成立」とし、分からないことを製品の実機での確認(手動テストの6)に回したが、その項目は「環境がある場合」の任意の項目で、結果を確かめる仕組みもなかったため |
| なぜ製品の実機での確認でも見つけられなかったか | v0.1.0は実機での確認をしなかった。v0.1.1では、項目ごとの結果を受け取っていない。メンテナーの環境に2台目のモニタがあるかを、確認の前に確かめていなかった |
| なぜ自動の確認で見つけられなかったか | ランナーはモニタが1つで、2台目のウィンドウを作る経路を通らないため |

## 真因

ログの読み方を一次情報(ログを書くコード)で確かめずに「分からない」と判断し、その「分からない」を、結果を必ず確かめる項目として残さなかった。複数モニタのように自動の確認で通らない経路を、実機での確認の任意の項目に回し、環境があるかと結果を確かめる仕組みがなかった。

## 対策

1. 現象への対応: Issue #50で原因を確かめてから直す。原因を確かめるため、`v0.2.0-alpha.1`より後のビルドでは、描画先の準備のログにウィンドウの番号を付け、サーフェスを作れなかった理由も書く(`feature/v0.2.0-finish`のF-07の作業に含めた)。メンテナーからログを受け取り、`window 1`の`first frame presented`の行があるかで切り分ける。
2. 記録の訂正: スパイクの結果の3回目とS4の解釈を、上の事実に合わせて直した(訂正の日付を本文に付けた)。4回目の記録は、2台目のフレームの行の有無を書いておらず、元のログもないため、確かめられないことを追記した。
3. 真因への対策(2026-11-04にメンテナーの判断を得て決めた):
   - ログから「分からない」と判断するときは、そのログを書くコードを読み、何が書かれうるかを確かめてから判断する。AGENTS.mdの「情報源」に加えた。
   - メンテナーの判断: 実機での確認は、メンテナーの都合で行わないか、一部だけ行うことがある。実機での確認をしないことで見つかる問題は、メンテナーが承知のうえで先に進める。そのため、実機での確認の項目を必須にする案は採らない。代わりに、エージェントは、確かめられなかった項目(自動の確認で通らない経路を含む)をリリースノートか計画の記録に書き、作業を止めずに進める。AGENTS.mdの「進め方」に加えた。
   - 実機のログを受け取ったときは、見た目の報告だけでなく、ログでも判定する。複数モニタでは、モニタの数だけ`window N: first frame presented`の行があることを、エージェントがログで確かめる(スモークテストの`screensaver_ready`と同じ判定を、実機のログにも当てる)。
   - 仕組みによる対策の検討: CIのランナーで2台目のモニタを用意する方法(仮想のディスプレイなど)は、GitHubがホストするWindowsのランナーで使えるかを確かめていない。v0.2.0のあとで調べる(計画0004の「あとで決めること」に登録した)。

## 確かめ方

- Issue #50の原因が確かめられ、直した版で、メンテナーの2画面の環境のログに、`window 0`と`window 1`の両方の`first frame presented`の行があること。
- 以後のリリースノートか計画の記録に、確かめられなかった項目が書かれていること。
