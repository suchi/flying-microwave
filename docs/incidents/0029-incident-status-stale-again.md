# 0029: 0020の対策のあとも、incidentのステータスがマージのあとで古いままだった

- 日付: 2026-11-13
- ステータス: 対策済み(現象への対応は、この記録と同じ変更で行い、PR #80でマージした。真因への対策は、2026-11-13にメンテナーが承認し、AGENTS.mdとマージの手順に加えて、PR #81でマージした。確かめ方は、PR #81のマージのあとの確認で、含まれた記録を一覧にしてステータスを直した(このセッションの作業)。次の整合性の確認は、まだ行っていない)
- 関連: [0020](0020-incident-status-not-updated.md)(同じ種類の問題の再発)、[0023](0023-tag-check-command-failed-in-cmd.md)、[0024](0024-unfounded-guess-as-premise.md)、[0026](0026-incident-row-placed-in-procedure.md)

## 起きたこと

2026-11-13に、incident 0028の対策の差分のレビューを受けた。その中で、エージェントは0024の記録の形を確かめていた。そのとき、0024のステータスが「規則と手順の対策は、2026-11-10にメンテナーが承認し、まだマージしていない」のままになっていることに気づいた。

「対策済み」でない記録をすべて見直したところ、3件のステータスが、対策のマージのあとも古いままだった。

確かめた事実:

- 0023と0024: 対策のコミット(0023は`1700706`、0024は`5bc7666`と`d9aee80`)は、2026-11-10にPR #70(`89bd379`)で`main`にマージされていた(`git log --merges --ancestry-path`で確かめた)。ステータスは「まだマージしていない」のままだった。
- 0026: 手順の対策のコミット`1d60ef1`は、2026-11-12にPR #78(`f546bd9`)でマージされていた。ステータスは「手順の対策は…まだマージしていない」のままだった。
- 0020の対策は、次の2つである。
  - マージの手順(`.claude/commands/merge-pr.md`の手順4)に、マージのあとでincidentのステータスを直す手順を加えた。
  - 整合性の確認(`.claude/commands/consistency-check.md`の6)で、ステータスを確かめる。
- エージェントは、PR #70からPR #79までのマージを、`merge-pr`のコマンドを使わず、GitHubのツール(`merge_pull_request`)で直接行っていた(このセッションの作業の記録)。そのため、手順4が実行される経路を通らなかった。
- 整合性の確認(`/consistency-check`)は、フェーズの区切りで行う決まりで、2026-11-10のあとは行っていない(このセッションの作業の記録)。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜステータスが古いままだったか | マージのあとでステータスを直す手順(`merge-pr.md`の手順4)を行わなかったため |
| なぜ手順を行わなかったか | エージェントは、マージを`merge-pr`のコマンドでなく、GitHubのツールで直接行っていた。手順4は、コマンドの中にしか書かれていない(AGENTS.mdの「PR・レビュー・マージ」の手順7には、マージのあとの作業の記述がない) |
| なぜ整合性の確認で拾えなかったか | 整合性の確認はフェーズの区切りでだけ行う。0020の対策のあとで、まだ行っていない。マージから区切りまでの間、古いステータスが残る |

## 真因

1. マージのあとの手順が、マージの経路の1つ(`merge-pr`のコマンド)にだけ書かれている。エージェントが実際に使う経路(GitHubのツールで直接マージする)には、その手順が結びついていない。
2. 整合性の確認の間隔(フェーズの区切り)が長く、マージのたびの漏れを早く拾えない。

## 対策

1. 現象への対応: 0023、0024、0026のステータスを、事実に合わせて直した(この記録と同じ変更)。0026は「対策済み」にした。0023は、確かめ方を確かめた記録がないので、0024は再発があったので、それぞれ「対策中」のままにした。
2. 真因1への対策(2026-11-13にメンテナーが承認した): AGENTS.mdの「PR・レビュー・マージ」の手順7に、「マージは、どの方法で行う場合も、`.claude/commands/merge-pr.md`の手順に従う。マージのあとで、そのPRに含まれたincidentの記録を`git diff --name-only`で確かめ、ステータスを直す」を加えた。
3. 真因2への対策(2026-11-13にメンテナーが承認した): `scripts/test_incident_lists.py`に、ステータスが「まだマージしていない」と書かれた記録について、その記録のファイルの最後の変更のあとに、`main`へのマージがあれば失敗する検査を加えることを検討した。しかし、記録のファイルの変更とマージの関係は、記録の対策のコミットとは限らない。誤った検査になりうるため、採らない。代わりに、1つのPRのマージのたびに、そのPRに含まれるincidentの記録を一覧で示す手順を、2の規則と、マージの手順(`.claude/commands/merge-pr.md`の手順4)に加えた(`git diff --name-only`で`docs/incidents/`の変更を確かめる)。

## 確かめ方

- 以後のマージのあとの報告で、そのPRに含まれたincidentの記録と、ステータスを直したかどうかが示されていること。
- 次の整合性の確認で、ステータスが古いままの記録がないこと。

## その後の再発

2026-11-22に、incident 0041の再発を記録するために0041を読んだとき、そのステータスが「規則と手順の対策は…そのあとのPRで行う」のままで、対策はすでにPR #91(2026-11-21にマージ)に入っていたことに気づいた。0039と0040も同じだった。同じ種類の問題の再発なので、異常に当たる。

確かめた事実:

- 0039、0040、0041の対策の文(AGENTS.md、`.claude/commands/merge-pr.md`、`.claude/commands/commit.md`)は、コミット`967fa32`で入り、PR #91のマージ`f672b82`に含まれる(`git merge-base --is-ancestor`)。
- PR #91の差分の`docs/incidents/`の変更(`git diff --name-only f672b82^1 f672b82 -- docs/incidents/`)には、0038、0039、0041が含まれ、0040は含まれない(0040の対策は、記録のファイルではなくAGENTS.mdなどの変更だった)。
- PR #91のマージのあとで、incidentのステータスを直したのは、コミット`cac67cd`の0038だけだった(メッセージ: 「PR #91のマージのあとの記録として、incident 0038を対策済みにした(リリースノートの差し替えを確かめた)」)。

なぜなぜ分析:

1. なぜ、0039と0041のステータスを直さなかったか。
   - マージの手順4の一覧を作ったか、一覧のどの記録をどう判断したかは、記録がなく分からない。0038だけを直したのは、メンテナーに依頼していた作業(リリースノートの差し替え)の確認と結びついていたため(推測。根拠は`cac67cd`のメッセージ)。
2. なぜ、0040は一覧に出なかったか。
   - 手順4は、PRの差分に含まれる記録のファイルだけを一覧にする。対策だけを含み、記録のファイルを変えないPRでは、その記録が一覧に出ない。
3. 真因: マージのあとの確かめが、差分に含まれる記録のファイルに限られ、対策を含むPRで参照された記録を拾わない。一覧に出た記録を、どれも確かめた記録を残す段もない。

案(承認が要る。メンテナーの判断を待っている):

1. 仕組み: マージのあとに、そのPRの差分で加えた行が参照するincident(`docs/incidents/NNNN`へのリンク、または`incident NNNN`の語)と、差分に含まれる記録のファイルを、合わせて一覧にするスクリプトを`scripts/`に加え、マージの手順4で使う。今回の0040も一覧に出る。
2. 手順: マージの手順4に、一覧の記録ごとに、ステータスを直したか、直さない理由を、完了の報告に書く段を加える。
