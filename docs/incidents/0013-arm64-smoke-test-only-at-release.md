# 0013: arm64のスモークテストを、タグを付けるまで試せず、リリースが2回続けて止まった

- 日付: 2026-11-03
- ステータス: 対策済み(対策はPR #45でマージした)
- 関連: [計画0003](../plans/0003-v0.1.1-smoke-test.md)のD-4・D-7・D-9、[計画0001](../plans/0001-initial-implementation-plan.md)のD-23・D-32、[ADR-0016](../adr/0016-arm64-without-guarantee.md)、[ADR-0022](../adr/0022-ship-x64-only-for-now.md)、Issue #44

## 起きたこと

プレリリース`v0.1.1-alpha.1`(2026-11-03 07:33 JST)と`v0.1.1-alpha.2`(同 08:47 JST)のリリースのワークフローで、どちらもarm64のスモークテストのF-01が失敗し、下書きが作られなかった。

確かめた一次情報(リリースのワークフローの実行41538219628と41548092403のログ):

- alpha.1: arm64のランナー(`windows-11-arm`)で、製品の`SetForegroundWindow`が`false`を返し、テストが送ったキーが全画面のウィンドウに届かなかった。x64(`windows-2025`)では前面化もテストも成功した。
- alpha.2: alpha.1の失敗を受けて、前面に出せないときはクリックで確かめるようにした(D-7)。しかし、前面のウィンドウは別のプロセスの`Windows.UI.Core.CoreWindow`で、カーソルの下も製品の全画面のウィンドウではなかった。決めた条件のとおり、テストはクリックに切り替えずに失敗した。
- arm64のランナーでGUIを伴う処理を実行できるのは、リリースのワークフローだけである。PRのCIのWindowsのジョブはx64だけで(`ci.yml`)、リリースのワークフローはタグか既存のタグの手動実行でしか動かず、どちらもタグのコミットをビルドする。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜリリースが2回続けて止まったか | arm64のスモークテストが、2回ともランナーの環境で入力が届かずに失敗したため |
| なぜ1回目の失敗のあとの修正も、リリースで失敗したか | 修正(D-7)が正しいかを確かめる手段が、次のタグしかなかったため。また、修正は、1回目のログで分かった前面化の失敗(`SetForegroundWindow: false`)だけを前提にした推測に基づいていた。前面にどの画面があり、カーソルの下に何があるかは、確かめないままだった |
| なぜ推測のまま、次のタグで試したか | 1回目のスモークテストの出力には、前面のウィンドウとカーソルの下のウィンドウの情報がなく、原因を絞り込めなかった。前面のウィンドウの持ち主を出力する診断は、D-7の修正と同時に加えたため、その情報が得られたのは2回目の失敗のときだった。診断だけを先に試す手段も、タグしかなかった |
| なぜタグでしか確かめられなかったか | arm64のランナーを使うのはリリースのワークフローだけで、PRのCIや手動のジョブにarm64がないため |
| なぜその状態で、arm64で新しい検査を始めたか | 計画で「arm64のスモークテストは、プレリリースのタグで初めて動かす」と決めていた(D-4)。最初の1回は失敗を見込んでいたが、失敗したあとの修正を、タグなしで試す手段を用意していなかった |
| なぜ、タグでしか試せないリスクをメンテナーに示して判断を得ていたのに、2回続けて止まったか | 示したリスクは、最初の1回が失敗しうることと、失敗したら新しい版のタグが要ることだった(D-4、v0.1.0のときの計画0001のD-23も同じ構造)。1回目が失敗したあと、原因を一次情報で確かめる前に、推測に基づく修正を入れて次のタグを使った。そのとき、「次のタグも失敗しうる」ことは示していなかった。AGENTS.mdの「原因を特定してから対処する」は、前面化の失敗(`SetForegroundWindow: false`)を原因と見なしたために働かなかった。前面に何があるかという、確かめていない前提が残っていることを、未確認として扱わなかった |

## 真因

リリースのワークフローだけで動くランナー(arm64)に、環境に左右される検査(GUIを伴うスモークテスト)を加えるとき、タグを付けずに試す手段を用意せず、失敗したあとの修正もタグでしか確かめられなかった。そのうえで、1回目の失敗のあと、原因を確かめずに、推測に基づく修正を次のタグで試した。最初の1回のリスクは判断を得ていたが、失敗のあとにどう進めるかの決まりがなかった。

同じ構造(タグでしか試せないarm64のビルド)は、v0.1.0のときにも計画0001のD-23で受け入れていた。v0.1.0では最初の1回で成功したため、問題にならなかった。

## 対策

1. 現象への対応(メンテナーの判断。計画0003のD-9、計画0001のD-32、ADR-0022): arm64には当面対応せず、`v0.1.1-alpha.3`からarm64版を配布しない。リリースのワークフローはx64だけをビルドする。arm64への対応はIssue #44で扱い、v1.0.0のあとに優先度を決める。版を`v0.1.1-alpha.3`にしてやり直す。
   - 途中で、arm64ではF-01の入力から先だけをスキップする案を一度決めたが、確かめられない範囲が広がり、タグでしか試せない状態も変わらないため、配布をやめる判断に改めた。
2. 真因への対策: AGENTS.mdの検証コマンドの段落に、「リリースのワークフローでだけ動く環境(arm64のランナーなど)に、環境に左右される検査を加えたり変えたりするときは、タグを付けずにその環境で試す手段(手動実行のジョブなど)を用意するか、試せないことと、失敗したときに新しい版のタグが要ることを、メンテナーに示して判断を得る」を加えた。さらに、レビューの指摘を受けて、「その環境で失敗した検査の修正を、その環境で試せないまま次の版に入れるときは、原因を確かめたと考える場合も、修正が前提にしていることを並べ、そのそれぞれを一次情報(ログの行など)で確かめたかを示す。あわせて、次のタグも失敗しうることと、失敗したらさらに新しい版のタグが要ることを示して、メンテナーの判断を得る。版を上げるPRは、その判断のあとで作る」を加えた。原因を確かめたかどうかをエージェントが自分で判断する形にすると、今回のように、原因(前面化の失敗)は確かめたと考えて、修正の前提(カーソルの下が製品の画面であること)を確かめないまま進めてしまう。そのため、条件を付けず、いつも前提を並べて示す形にした。タグを付けるのはメンテナーのため、エージェントの操作は、版を上げるPRを作ることと、次のタグを提案することとして書いた。この規則は、arm64への対応を再開するとき(Issue #44)にも適用する。
3. 仕組みによる対策(検討して採らなかった): CIにarm64の手動実行のジョブを加える案は、メンテナーに示したが、arm64に当面対応しない判断となったため、採らなかった。arm64への対応を再開するときに、2の規則に従って改めて判断する(Issue #44に、決めることとして書いた)。

## 確かめ方

- `v0.1.1-alpha.3`のリリースのワークフローが、x64だけをビルドし、スモークテストを含むすべてのジョブが成功して、下書きが作られること。下書きにarm64のzipがなく、リリースノートにarm64版の節がないこと。
- 以後、リリースのワークフローでだけ動く環境に、環境に左右される検査を加えたり変えたりしたPRで、タグの前に試した記録か、試せないことについてのメンテナーの判断が、PRのまとめコメントに残っていること。
