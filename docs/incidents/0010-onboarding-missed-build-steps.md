# 0010: 開発参加者向けの文書に、ビルドの方法が抜けていた

- 日付: 2026-11-01
- ステータス: 対策中(対策のPRがマージされていない)
- 関連: [0006](0006-plan-delayed-first-runnable-version.md)(エージェントの作業の側から計画した点が近い)

## 起きたこと

メンテナーが「開発ドキュメントにビルドの仕方が見当たらない。どこを読めば手動でビルドしたりテストできるか」と尋ねた。確かめたところ、手でビルドしてテストする手順は、どこにもまとまっていなかった。コマンドはAGENTS.mdの検証コマンドの表に、前提のツールはスパイクの手順書に、`.scr`の作り方はワークフローの中だけにあった。

エージェントは、これを情報の問い合わせとして扱った。オンボーディングに手順を足すPR(#27)を作っただけで、なぜ抜けたのかを調べなかった。メンテナーは、現象を直すだけでなく、原因と真因を調べて真因に対策するよう、改めて指摘した。この指摘は、同じ趣旨のものとして何度目かである。さらに、テストやデバッグの方法など、同じ根から漏れているものにも気づけるはずだ、と指摘した。

確かめた一次情報:

- `git log`: オンボーディング(`docs/development/onboarding.md`)は2026-10-31に作られた(fbbd7d6)。コードがまだない計画の段階である。そのあと34回更新されたが、ほとんどは規則・手順・異常の対策の追記だった。ビルドの手順が加わったのは、このPRが初めてである。
- 製品のコードがビルドできるようになったのはPR #21である。そのときも、オンボーディングは更新されていない。
- 計画0001の文書の一覧では、オンボーディングは「後から参加する人の入口」とだけ書かれていた。何を書く文書かは決まっていなかった。
- 冒頭のステータスは「Phase 0の着手前」、1章は「製品コードはまだない」のままだった。
- AGENTS.mdのドキュメントの規則は「コードの実態と一致させる」である。レビューの手順と`/consistency-check`が確かめるのは、書いてあることの正しさ(食い違い・リンク切れ)だけだった。
- 同じ根から漏れていたもの: 動かして試す方法(`/s`・`/c`・`/p`)、ログの見方、デバッグの方法、困ったときの対処。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜビルドの方法が抜けていたか | オンボーディングに、ビルドの手順を書く節がなかったため |
| なぜ節がなかったか | コードのない段階で作り、その時点で書けることだけを書いたため。コードができたら足す、という予定もなかった |
| なぜコードができたときに足されなかったか | 文書を更新するきっかけが「実態との食い違いをなくす」ことだけだったため。足りない情報は食い違いではないので、レビューでも`/consistency-check`でも見つからない |
| なぜ足りない情報を見つける基準がなかったか | オンボーディングの読者(新しく参加する開発者)が、何をできるようになる必要があるかを決めていなかったため。エージェントは自分の作業(規則、レビュー、CI)の側から文書を書いていて、エージェントがふだん行わない作業(Windowsでの手元のビルド、実行、デバッグ)が見えていなかった |
| なぜ最初の指摘で、手順を足すだけで終えたか | 質問の形の指摘を情報の問い合わせとして扱い、成果物の欠けという異常として扱わなかったため。AGENTS.mdの異常の定義に、成果物の欠けの指摘が含まれていなかった |

## 真因

1. 開発者向けの文書の中身を、読者が行う作業から決めていなかった。何を書くべきかの基準がなく、書き漏れを見つける手順もなかった。
2. メンテナーが成果物の欠けや誤りを指摘したことを、異常として扱う決まりがなかった。

## 対策

1. オンボーディングの冒頭に「この文書でできるようになること」の一覧を置いた。開発者が行う作業ごとに、手順を書いた節と状態を示す。手順がまだない作業は、「未整備」として理由と時期を書く。
2. 一覧で欠けていた節を加えた: 5.1 手でのビルドとテスト、5.2 動かして試す、5.3 ログとデバッグ、5.4 困ったときの対処。
   - デバッガの使い方は、公式ドキュメント(`learn.microsoft.com`、`code.visualstudio.com`)にこの環境から接続できず、確かめられなかった。推測で書かず、未整備とした。
   - 古いままだった、冒頭のステータスと1章の現在の状況も直した。
3. 書くべきことの抜けを見つける手順を加えた。
   - レビューの手順の観点: 開発者が行う作業を変える差分では、一覧と各節が更新されているかを見る。
   - `/consistency-check`: 一覧の各作業の手順が書かれていて、今のコードで動くかを確かめる。
   - 計画0001の7.1のリリースの条件: 一覧が、そのリリースの実態で満たされていること。
4. AGENTS.mdとincidentsの手順の異常の定義に、「ユーザーが成果物の欠けや誤りを指摘したこと(質問の形のものを含む)」を加えた。
5. 機械的な検査は採らない。見出しの有無は機械で確かめられるが、手順が使えるかどうかは分からず、今回のような抜けの判断には役に立たないため。一覧との突き合わせを、レビュー・整合性の確認・リリースの条件の3か所で行う。

## 確かめ方

- 次のフェーズの区切りの`/consistency-check`で、一覧の項目の抜けが報告されないこと。または、抜けが見つかり、直されること。
- 開発者が行う作業を変えたPR(たとえばPhase 1の段階2の`/p`)で、一覧と5.2が同じPRの中で更新されていること。
- メンテナーが成果物の欠けを指摘したときに、エージェントが作業を止めて、incidentsの手順で扱うこと。
