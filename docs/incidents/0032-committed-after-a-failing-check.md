# 0032: 検証のコマンドの失敗を見ずに、同じ呼び出しの中でコミットした

- 日付: 2026-11-18
- ステータス: 対策済み(規則の対策は、2026-11-18にメンテナーが承認し、PR #86でマージした。2026-11-23の再発(下の「その後の再発(2026-11-23)」)の追加の対策(計画0005のD-42。`git commit`より前のパイプを止めるフックの検査と規則)は、2026-11-24にPR #102でマージした。このフックはコマンドの文字列だけを見るため、Claude Codeが入力を用意する時点に頼るフックの確認の条件(AGENTS.mdの「検証コマンド」の節)には当たらない)
- 関連: [0031](0031-requested-publishing-an-already-published-release.md)(この異常が起きた記録の作業)

## 起きたこと

2026-11-18に、incident 0031の記録をコミットするとき、エージェントは、スクリプトのテスト(`python3 -I -m unittest discover -s scripts`)とコミット(`git commit`)を、1回のシェルの呼び出しの中で、`;`でつないで実行した。テストは失敗したが、コミットはそのまま作られた(コミット`6edc1c3`)。

確かめた事実:

- 失敗したのは`scripts/test_incident_lists.py`の`test_the_docs_readme_lists_every_record`で、`docs/README.md`のincidentの一覧に0031の行がなかったため(テストの出力)。
- エージェントは、出力の`FAILED (failures=1)`を見て気づき、プッシュの前に、行を加えてテストが通ることを確かめ、コミットを直した(`54d6906`。`git commit --amend`)。失敗したコミットは、リモートに送られていない(このセッションの作業の記録)。
- AGENTS.mdの「検証コマンド」の節は「コミット前に必ずテスト・リントを実行する」と定めている。実行はしたが、結果を確かめる前にコミットした。
- このセッションのほかのコミットでは、検証とコミットを`&&`でつなぎ、失敗したらコミットしない形にしていた(このセッションの作業の記録)。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜテストが失敗したのにコミットしたか | テストとコミットを`;`でつないだため、テストの結果にかかわらずコミットが実行された(実行したコマンド) |
| なぜ`;`でつないだか | テストの出力の一部を`grep`で取り出して表示するために、テストの出力を`grep`へのパイプで渡していた。この形では、`&&`でつないでも、終了の状態は`grep`のものになり、テストの失敗では止まらない。エージェントは、1回の呼び出しで結果の表示とコミットを済ませようとして、失敗で止まる形にすることを確かめなかった(実行したコマンド) |
| なぜ確かめる決まりがなかったか | AGENTS.mdは「コミット前に必ずテスト・リントを実行する」とだけ定め、結果が通ったことを確かめてからコミットすることや、検証とコミットを1回の呼び出しでつなぐときの形を定めていない(AGENTS.mdの「検証コマンド」の節) |

## 真因

1. 検証の結果を確かめてからコミットすることが、規則に書かれていない。「実行する」だけが求められている。

## 対策

1. 現象への対応: プッシュの前に、`docs/README.md`に0031の行を加え、テストが通ることを確かめて、コミットを直した(上の事実)。
2. 真因への対策(2026-11-18にメンテナーが承認した): AGENTS.mdの「検証コマンド」の節の「コミット前に必ずテスト・リントを実行する」を、「コミット前に必ずテスト・リントを実行し、すべて通ったことを確かめてからコミットする。検証とコミットを1回の呼び出しでつなぐときは、検証の失敗でコミットが止まる形にする(`&&`でつなぎ、検証の終了の状態をパイプなどで失わない)」にする。
3. 仕組み: 機械的な検査(コミットの前のフックなど)は加えない。理由: フックの追加はセキュリティ設定の変更で、検証の種類(Rust、スクリプト、文書だけ)によって要る検証が違うため。2の決まりで防ぐ。

## 確かめ方

- 以後のコミットで、検証が失敗したままコミットされたものがないこと。

## その後の再発(2026-11-23)

2026-11-23 20:19(JST)に、作業11(バナーとアイコン)のブランチで、再レビューの指摘L-aの修正をコミットするとき(コミット`93e5ee6`)、エージェントは、スクリプトのテストの出力を`tail -1`へのパイプで渡し、そのあとに`&&`で`git commit`をつないだ。この形では、終了の状態は`tail`のものになり、テストが失敗してもコミットは止まらない。AGENTS.mdの「検証コマンド」の節(「検証の終了の状態をパイプなどで失わない」)に反するので、異常に当たる。コミットのあとで出力を見て気づいた。

確かめた事実:

- そのときのテストは通っていた。コミットのあとで、出力をファイルに書き、終了の状態が0で、116件が`OK`だったことを確かめた。コミットは、まだリモートに送っていない。
- このセッションの会話の記録で、`git commit`の前に検証のコマンド(スクリプトのテスト、`cargo`のテストとリント、フックの検査、依存の検査)の出力をパイプで渡している呼び出しを数えた(会話の記録のJSONLを、Pythonのスクリプトで読み、`git commit`より前に、検証のコマンドの直後の`|`があるものを選んだ)。PR #86のマージ(2026-11-18 21:02 JST。マージのコミット`5559159`の日時)のあとでは、`grep -qx OK`のように、成功の行がないと失敗する形が9回、`tail`や`grep -E "^(OK|FAILED)"`のように、失敗で止まらない形が71回あった。止まらない形の最初は2026-11-19 22:04(JST)だった。
- 止まらない形の71回のうち、出力に失敗の文字(`FAILED`か`error`)があったのは3回で、2回はフック(`block-dangerous-git.sh`)がコミットを止め、1回は、わざと壊した写しでのTDDのRedの確かめのあとで、もとに戻した全体のテストが`OK`だった(どれも会話の記録の出力)。失敗したままのコミットは見つからなかった。ただし、この確かめは出力の文字によるもので、出力が切り詰められた呼び出しは見落としうる。

なぜなぜ分析:

1. なぜ、終了の状態を失う形でつないだか。
   - テストの出力を短くして表示するために、パイプで`tail`や`grep`に渡した。1回の呼び出しで結果の表示とコミットを済ませようとした点は、最初の発生と同じである(実行したコマンド)。
2. なぜ、規則があるのに守られなかったか。
   - 規則は「パイプなどで失わない」と書くが、エージェントは`&&`でつなぐことだけを守り、パイプのほうは続けていた。`grep -E "^(OK|FAILED)"`は、`FAILED`の行にも一致するので確かめにならないが、確かめのつもりで使っていた(上の71回の形)。
3. なぜ、5日間気づかなかったか。
   - 検証が失敗した場面が少なく、失敗した場面ではフックかエージェントの目で止まったため、規則に反していても結果の誤りにならなかった。規則に反した形を機械的に見つける仕組みがない。最初の発生の対策では、仕組みを採らなかった(理由は、フックの追加がセキュリティ設定の変更で、検証の種類によって要る検証が違うため。上の「対策」の3)。
4. 真因: 対策が規則の文だけで、守られないと効かない。パイプのあとのコミットという形は、検証の種類によらず機械的に見つけられるが、仕組みにしていない。

対応: 今回のコミットのテストが通っていたことを確かめた(上の事実)。以後は、検証の出力をファイルに書いて終了の状態を確かめるか、`set -o pipefail`を付ける。追加の対策は、2026-11-23に、メンテナーが次の案1と案2を採った(計画0005のD-42。作業10の10で行う)。

1. 仕組み(推奨): `.claude/hooks/block-dangerous-git.sh`に、`git commit`より前に1本のパイプ(`|`。`||`は除く)があり、`pipefail`の語がない呼び出しを止める検査を加える。止めるメッセージで、検証とコミットを別の呼び出しにするか、`set -o pipefail`を付けるよう示す。検証の種類によらず働く。ヒアドキュメントの中の表の`|`でも止まるが、`set -o pipefail`を付ければ通る。`scripts/check_hooks.py`にサンプル入力を加える。
2. 規則: AGENTS.mdの「検証コマンド」の節に、終了の状態を保つ形の例(出力をファイルに書く、`set -o pipefail`)を書き添える。1と合わせて行う。
