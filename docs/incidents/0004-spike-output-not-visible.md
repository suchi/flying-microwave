# 0004: 実機の確認で、描画が目に見えなかった

- 日付: 2026-11-01
- ステータス: 対策中(対策のPRがマージされていない)

## 起きたこと

メンテナーが、saver-spikeを実機で確かめた。1回目(2026-11-01)も3回目(同じ日)も、プレビュー枠は真っ暗に見えたと報告した。

一方、3回目のログには、プレビュー枠でも全画面でも、フレームを描画した記録がある(`frame N presented`)。描画はできていたが、目では何も見えなかった。同じ報告が2回続いた。

確かめた一次情報:

- 描く色を決める関数`spikes/saver-spike/src/policy.rs`の`dark_color`。RGBの各成分は0.05〜0.10で、8ビットにすると約13〜25になる。
- 手順書`spikes/README.md`のS1の手順2。期待する見た目として「暗い色がゆっくり(約12秒周期で)変わる描画が出るか」と書いてある。
- 3回目の確認を依頼したときのエージェントの説明。確かめる項目には、ログの行だけを挙げていた。
- 技術スパイクの結果(`docs/research/spike-results.md`)の「1回目」。ほぼ黒に見える理由を、説明として記録している。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ真っ暗に見えたか | 描く色の明るさが、8ビットで約13〜25しかないため。目では、黒(0)と見分けられない |
| なぜその色のまま、3回目の確認を依頼したか | 1回目に「真っ黒」と報告を受けたとき、エージェントは理由を説明して記録しただけで、スパイクを変えなかったため |
| なぜ説明だけで済ませたか | 描画できたかの判定を、ログ(`frame N presented`)に頼れると考えたため。目で確かめることを、判定の手段に含めていなかった |
| なぜ目で確かめることが判定に含まれていなかったか | 手順書には期待する見た目が書いてあったが、その見た目を人が見分けられるかを確かめる手順がなかったため。暗い色にした理由は、閃光と眩しさを避けるガイドライン(G-3・G-5)だった。見える必要との釣り合いは、検討していなかった |
| なぜ見分けられるかを確かめる手順がなかったか | メンテナーに実機での確認を依頼するときに、何を見れば成功と判定できるかを示す、という決まりがなかったため |

## 真因

メンテナーに実機での確認を依頼するときの決まりがなかったこと。具体的には、目で見て成功を判定できる見た目を決めて示すことと、その見た目が人に見分けられるものにすることが、決まっていなかった。

## 対策

1. スパイクに、目で見える目印を加えた。暗い背景の上に、中くらいの明るさの小さな四角を描き、ゆっくり動かす。点滅はさせず、同じ位置に留まらないので、ガイドラインのG-3・G-4・G-5に沿う。手順書のS1・S4には、この四角が見えることを期待する見た目として書いた。
2. AGENTS.mdの「進め方」に、決まりを加えた。メンテナーに実機での確認を依頼するときは、何が見えれば成功かを、目で見て判定できる形で示す。目で見分けられない場合は、確かめる対象を見分けられるように作り直してから依頼する。
3. 仕組みによる確認(フックなど)は採らない。依頼の文面が目で判定できる形になっているかは、機械では判定しにくいため。

## 確かめ方

- 次の実機での確認で、メンテナーが、プレビュー枠と全画面の両方で四角が見えたかを報告できること。
- 以後の実機での確認の依頼に、期待する見た目が書かれていること。
