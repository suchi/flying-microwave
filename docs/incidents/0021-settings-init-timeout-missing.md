# 0021: 設定画面のGPUの初期化に、要件にある上限がないまま出した

- 日付: 2026-11-10
- ステータス: 対策中(対策2と3、決定の記録、v0.2.0の既知の制限への追記は、PR #65でマージした。残りの対策1の上限の実装は、計画0001のPhase 3の作業9に登録し、計画0005の作業1として実装した(マージの前)。マージのあとで「対策済み」に直す)
- 関連: [計画0004](../plans/0004-v0.2.0-settings.md)のF-03・E-4・D-10、[ADR-0024](../adr/0024-settings-file-location-and-handling.md)のE-4、[0011](0011-log-written-against-requirement.md)

## 起きたこと

2026-11-10に、Phase 2の区切りの整合性の確認(`/consistency-check`)で、設定画面のGPUの初期化に上限がないことが分かった。要件(計画0004のF-03)は上限があることを前提にしているが、上限を設けないという決定の記録もない。v0.2.0は、この状態で公開した。

確かめた事実:

- 計画0004のF-03は、「異常終了(panic、初期化の上限による終了など)の前にも、オーナーを有効に戻す」としている。
- 計画0004のE-4は、設定画面のプロセスで、GPUが使えないとき(初期化の失敗、初期化が終わらないとき)の動作と、`/s`と`/p`の15秒の上限(計画0001のD-27)に当たる決まりを、作業8の前に決めるとしていた。
- ADR-0024のE-4が決めたのは、初期化に失敗して設定画面を開けないときに、メッセージボックスで設定ファイルのパスを示し、終了コード7で終わることだけである。初期化が終わらないときの扱いは決めていない。計画0004のD-10も、終了コード7だけを記録している。
- `/s`(`crates/app/src/saver.rs`)と`/p`(`crates/app/src/preview.rs`)は、`render::Watchdog`で15秒の上限を設け、終了コード6で終わる。設定画面(`crates/app/src/settings.rs`)には、上限がない。
- 設定画面は、オーナーを無効にする処理(`attach_owner`)を、eframeがアプリを作るときに行う。初期化が終わらない場合、オーナーは無効にならず、設定画面のプロセスだけが残ると考えられる(推測。eframeの内部で、アプリを作るのが描画の準備のあとであることは、ソースで確かめていない)。
- 実機やCIで、設定画面の初期化が終わらなかった例は、記録にない。
- v0.2.0の公開の前(2026-11-09)にも、整合性の確認を行い、その指摘をPR #60で直していた。そのときは見つけられなかった。整合性の確認の項目(`.claude/commands/consistency-check.md`の5)は、要件と実装の照合の対象を、計画0001のF-xx・N-xxとしている。F-03は計画0004(フェーズの計画)の要件で、照合の対象に入っていなかった。2026-11-10の確認では、依頼の文で計画0004の要件も対象に加えたため、見つかった。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ上限がないまま出したか | E-4を決めたとき(ADR-0024)に、初期化の失敗だけを決め、初期化が終わらないときを決めなかったため。実装もそれに合わせた |
| なぜ決め漏れに気づかなかったか | E-4を「決めた」と記録したとき(計画0004の「あとで決めること」)に、E-4の項目に挙げた内容(失敗、終わらないとき、15秒の上限に当たる決まり、利用者に示すこと)と、決めた内容を突き合わせなかったため |
| なぜ突き合わせなかったか | 先送りした決定を決めたときに、項目の内容をすべて決めたかを確かめる手順がない。incident 0011の対策は、先送りした決定を計画に登録することで、決めたときの確かめ方は扱っていない |
| なぜ公開の前の整合性の確認で見つからなかったか | 整合性の確認の項目が、要件と実装の照合の対象を計画0001の要件に限っていて、フェーズの計画の要件(計画0004のF-03)を含んでいなかったため |

## 真因

先送りした決定(E-x)を決めたときに、項目に挙げた内容をすべて決めたかを確かめなかった。そのため、要件(F-03)が前提にしている上限が、決めないまま、記録のないまま実装から抜けた。あわせて、整合性の確認がフェーズの計画の要件を照合の対象にしていなかったため、公開の前に見つけられなかった。

## 対策

1. 現象への対応(2026-11-10にメンテナーが案Aを承認した。計画0004のD-17): 設定画面にも`/s`・`/p`と同じ15秒の上限を設け、上限に達したら、オーナーを有効に戻し、メッセージボックスで開けなかったことを示して、終了コード7で終わる。計画0001のPhase 3の最初の作業(作業9)として行う。v0.2.0の既知の制限(CHANGELOGと、GitHub Releaseのリリースノート)に書く。E-4に挙げた内容ごとの決定は、計画0004のD-17に並べた(対策2の規則を、この決定に最初に当てた)。採らなかった案B(上限を設けず、そう決めたことを記録する)は、要件(F-03)が上限を前提にしていることと、`/s`・`/p`との一貫性から採らなかった。
2. 手順(2026-11-10にメンテナーが承認した): 先送りした決定(E-x)を「決めた」と記録するときは、項目に挙げた内容ごとに、決めた内容と記録の場所を並べる。決めなかった内容は、改めて先送りして計画に登録する。AGENTS.mdの「進め方」の、incident 0011の規則の箇条に加えた。整合性の確認の項目5にも、決めたとした項目の内容がすべて決まっているかを加えた。
3. 確認の範囲(2026-11-10にメンテナーが承認した): 整合性の確認の項目5の照合の対象に、進行中と直近に完了したフェーズの計画(`docs/plans/`)の要件を加えた。

## 確かめ方

- 1の判断のあと、案Aなら、設定画面の初期化が15秒で終わらないときに終了することを、テストかスモークテストで確かめる。案Bなら、計画の決定と要件の記述が一致すること。2026-11-10に、[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)のD-1で、製品にテスト用の待ちを入れないと決めたため、確かめ方を次のとおりにした。上限の処理の状態の移り方と、上限に達したときの処理の順番を、単体テストで確かめる。設定画面への組み込みとWindowsの作用(オーナーを戻す、メッセージボックス、終了)は、レビューの観点として確かめる。初期化が止まる状況そのものは、テストで再現しない。上限に達したときは、メッセージボックスが閉じられてから終了するため、止まったメインのスレッドの状態によってメッセージボックスが表示されない場合に、プロセスが終わらずに残るおそれがある(推測。確かめていない。2026-11-10のレビューの指摘)。順番は計画0005のD-1の(2)のとおりとし、変えていない。
- 次に先送りした決定を決めるとき、項目ごとの対応の表が記録にあること。
