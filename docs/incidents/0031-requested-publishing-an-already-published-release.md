# 0031: 公開済みのリリースの公開を依頼し続け、確かめていない前提で判断を仰いだ

- 日付: 2026-11-18
- ステータス: 対策中(真因への対策は、2026-11-18にメンテナーが承認し、まだマージしていない)
- 関連: [0024](0024-unfounded-guess-as-premise.md)(記録がないことを、なかったことの根拠にした。同じ種類の問題の再発)、[0016](0016-tag-before-merge.md)(前提が満たされていない手順を依頼した)、[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)のD-21

## 起きたこと

2026-11-18に、エージェントが最後の報告で`v0.3.0-alpha.3`の下書きの公開を依頼したところ、メンテナーが「ずいぶん前に公開した」と指摘した。

確かめた事実:

- GitHubのリリース`v0.3.0-alpha.3`は、`draft`が`false`、`published_at`が`2026-11-14T10:12:20Z`(2026-11-14 19:12 JST)だった(GitHubのツールの`get_release_by_tag`で、2026-11-18に確かめた)。zipのダウンロードの回数は1だった。誰がダウンロードしたかは分からない。
- エージェントは、2026-11-14の夜から2026-11-18まで、ターンの最後の報告で、`alpha.3`の下書きの公開(と、2026-11-16までは実機での確認)を依頼し続けた(このセッションの作業の記録)。依頼のたびに、リリースの状態をGitHubで確かめていなかった。
- この依頼は、会話の要約の「メンテナーの作業」に残っていた項目を、そのまま持ち越したものだった(このセッションの作業の記録)。このセッションには、リリースの公開についての通知は届いていない(受け取った通知の記録。届いたのはPRの通知だけ)。
- 2026-11-16に、エージェントは`alpha.4`の進め方について、メンテナーに2つの質問をした(このセッションの作業の記録)。
  - 1つめは「`v0.3.0-alpha.3`の実機での確認は、まだ行われていません」と書いた。これは確かめておらず、報告を受け取っていないことを根拠にしていた。
  - 2つめは、`alpha.3`を「GitHub Releaseの下書き」として、公開するかどうかを尋ねた。メンテナーは「そのまま公開する」を選んだ。
- この2つの答えは、計画0005のD-21として記録され、PR #84で`main`にマージされた。D-21の(2)(下書きを公開する)は、誤った前提による決定である。`alpha.3`の手順書の「結果」の「確認は行わなかった」も、確かめていない。
- AGENTS.mdの「進め方」には、「メンテナーに依頼するのは、前提がその時点で満たされている手順だけにする」がある(0016の対策)。「情報源」には、「記録がないことを、なかったことの根拠にしない」と「メンテナーが知っている事実は、推測せずに尋ねる」がある(0024の対策)。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ公開済みのリリースの公開を依頼し続けたか | 依頼を繰り返すたびに、リリースの状態をGitHubで確かめず、前の報告と会話の要約の項目を持ち越したため(このセッションの作業の記録) |
| なぜ確かめなかったか | 「前提がその時点で満たされている手順だけを依頼する」の規則はあるが、エージェントは、初めて依頼したときに確かめた前提(下書きがある)を、その後の依頼でも満たされているものとして扱った。持ち越した依頼のたびに確かめ直すことは、規則に書かれていない(AGENTS.mdの「進め方」の該当の箇条の文言)。メンテナーの作業の完了は、エージェントに通知されない(上の事実) |
| なぜ確認が行われていないと書いて判断を仰いだか | 報告を受け取っていないことを、行われていないことの根拠にしたため。0024の規則に反する(同じ種類の問題の再発)。エージェントは、この規則を、文書や記録に書く場面のものと考え、メンテナーへの質問の前提の文に当てはめなかった(このセッションの作業の記録) |

## 真因

1. メンテナーへの依頼と、メンテナーの作業の状態についての文を、前の報告から持ち越すときに、その時点の一次情報で確かめ直す決まりがない。
2. 0024の規則(記録がないことを、なかったことの根拠にしない。メンテナーが知っている事実は尋ねる)の対象に、メンテナーへの質問や依頼の前提の文が含まれることが、明示されていない。

## 対策

1. 現象への対応:
   - 計画0005のD-21の(2)を訂正し、`alpha.3`は2026-11-14に公開済みで、(2)は誤った前提による決定であり、意味を持たないことを書いた。
   - `alpha.3`の手順書の「結果」を、「確認を行ったかは、記録がなく分からない(メンテナーに尋ねている)」に直した。
   - メンテナーに、`alpha.3`の実機での確認を一部でも行ったかを尋ねた。答えによって、D-21の(1)の前提を確かめ直す。
2. 真因への対策(2026-11-18にメンテナーが承認した): AGENTS.mdの「進め方」の「メンテナーに依頼するのは、前提がその時点で満たされている手順だけにする」の箇条に、次を加える。
   - 依頼(前の報告からの持ち越しを含む)と、メンテナーの作業の状態(行ったか、まだか)について書く文は、そのたびに一次情報(リリースの状態、タグ、PRの状態など)で確かめてから書く。
   - 一次情報で確かめられないこと(実機での確認を行ったかなど)は、「まだ行われていない」と書かず、尋ねる。質問の選択肢の前提に書くときも同じ。
3. 仕組み: 機械的な検査は加えない。理由: 文がメンテナーの作業の状態を述べているか、その前提を確かめたかは、文の意味によるため。2の決まりと、依頼の前の確認で防ぐ。

## 確かめ方

- 以後のメンテナーへの依頼で、リリースやタグなどの状態を前提にする依頼に、その時点で確かめた結果(確かめた方法)が添えられていること。
- メンテナーの作業を「まだ行われていない」と、確かめずに書いた文がないこと。
