# 0040: 承認された設計と違う方式で、フックを確認なしに実装した

- 日付: 2026-11-21
- ステータス: 対策中(方式をどちらにするかと、手順の対策は、メンテナーの判断を待っている)
- 関連: [0025](0025-implemented-against-recorded-decision.md)(記録した決定と違う方式を、確認を取らずに実装した。同じ種類の再発)、[0034](0034-incident-list-test-skipped.md)の対策(2)、[計画0005](../plans/0005-v0.3.0-visuals-and-clock.md)のD-23、D-24の(6)

## 起きたこと

2026-11-21に、作業ブランチの差分の敵対的レビューで、incident 0034の対策(2)のフックが、承認された案と違う方式で実装されていると指摘を受けた。AGENTS.mdの「進め方」の、規則が守られなかったことと、同じ種類の問題の再発(0025)に当たる。

確かめた事実:

- incident 0034の案2(D-23で採った)は、「`git commit`のときに、ステージした変更に`docs/incidents/`か`docs/README.md`が含まれていれば、一覧のテストを実行」だった(0034の「対策」の節)。
- エージェントは、2026-11-20 16:50(JST)に、メンテナーに設計を報告した。報告の「設計3」の`block-dangerous-git.sh`の行も、「ステージした変更に`docs/incidents/`か`docs/README.md`があれば」だった(このセッションの会話の記録)。D-24の(6)は、この設計を採った。
- 実装(コミット`e2dc801`)は、`git status --porcelain -- docs/incidents docs/README.md`で作業ツリー全体(ステージしていない変更と、追跡していないファイルを含む)を見ている。理由は、フックの説明の文に「`git add ... && git commit`は、このフックが動いたあとでファイルをステージする」と書いた。エージェントは、この違いをメンテナーに確かめず、計画にも記録しなかった。

## なぜなぜ分析

1. なぜ、設計と違う方式で実装したか。
   - 実装の途中で、`git add`と`git commit`を1つのコマンドでつなぐと、フックの時点ではまだステージされていないことに気づき、作業ツリーを見る方式に変えた(フックの説明の文)。
2. なぜ、変える前に確かめなかったか。
   - 理由が明らかで、承認された目的(一覧のテストを飛ばさない)に沿う変更だったため、実装の方式の細部として扱った(推測。根拠は、変えた理由をコードの説明の文にだけ書き、計画にもincidentにも書かなかったこと)。AGENTS.mdの「進め方」は、方式を変えるときも確認すると定めている(0025の対策)。
3. なぜ、コミットの前に気づかなかったか。
   - 実装を、報告した設計と項目ごとに比べる段を、コミットの前に行わなかった。AGENTS.mdは、実装を始める前に設計を報告することを定めているが、実装のあとで報告した設計と比べることは定めていない。レビュー(この指摘)で、はじめて見つかった。
4. 真因: 実装の途中で方式を変える判断が、確認の手順を通らずにできてしまい、実装を報告した設計と比べる段が、レビューのほかにない。

## 真因

- 実装の途中で見つけた理由による方式の変更を、確認の要る変更として扱わなかった。
- 実装を、報告した設計と項目ごとに比べる段が、コミットの前にない。

## 対策

案(承認が要る。メンテナーの判断を待っている):

1. 方式: 作業ツリーを見る方式(いまの実装)と、ステージした変更だけを見る方式(承認された設計)のどちらにするかを判断していただき、計画0005に決定として記録する。
2. 手順: 設計を報告した作業では、コミットの前に、実装を報告した設計と項目ごとに比べ、違う項目があればコミットせずに確認する。敵対的レビューの依頼文には、報告した設計を要件として渡す(`docs/development/review-process.md`に書き添える。今回、レビューで見つかったのは、D-24を要件として渡したため)。

## 確かめ方

- 次に設計を報告して実装する作業で、敵対的レビューから、報告した設計と違う実装の指摘が出ないこと。
