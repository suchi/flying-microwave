# 0017: spikesの削除で、.gitignoreのビルドの生成物のエントリも消した

- 日付: 2026-11-09
- ステータス: 対策済み(対策はPR #60でマージした)
- 関連: PR #58、[計画0001](../plans/0001-initial-implementation-plan.md)のD-28

## 起きたこと

PR #58で`spikes/`を削除したとき、`.gitignore`の`/spikes/*/target`(スパイクのビルドの生成物)のエントリも消した。マージのあと、メンテナーが、削除したフォルダのエントリも`.gitignore`に残すべきだと指摘した。古いコミットを取り出してビルドすると、生成物がまたでき、エントリがないとコミットの対象になってしまうため。

確かめた事実:

- エージェントは、PR #58の作業中に、エントリを消したあとで`git add -A`を実行し、手元に残っていたスパイクのビルドの生成物(約2,900ファイル)をコミットに含めた。プッシュの前に気づき、コミットを取り消して作り直した。このとき、原因はエントリを消したことだと分かっていたが、エントリを戻さなかった。
- PR #58の本格的なレビューも、同じ危険をlowとして指摘した(以前にスパイクをビルドしたクローンで、`spikes/*/target/`が無視されない未追跡のフォルダーとして残る)。エージェントは、メンテナーに手元の生成物を消してもらう手順を示すことで対応し、エントリは戻さなかった。
- 古いコミット(タグ`v0.2.0-alpha.4`まで)には`spikes/`があり、スパイクの結果の文書は、その読み方(`git show v0.2.0-alpha.4:spikes/...`)を示している。取り出してビルドする場面は、これからも起こりうる。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ生成物を誤ってコミットしうる状態にしたか | `spikes/`を削除するときに、`.gitignore`のエントリも、`spikes/`への参照の1つとして消したため |
| なぜ消したか | 削除したフォルダへの参照をすべて外すことを目標にし、`.gitignore`のエントリを「参照」と同じに扱ったため。エントリが、そのフォルダがなくなったあとも、古いコミットや手元の残りの生成物を守る役目を持つことを考えなかった |
| なぜ自分で誤ってコミットしかけたのに、エントリを戻さなかったか | 現象(含めてしまった生成物)を取り除くことで止まり、同じことがメンテナーや開発参加者のクローンでも起きうることまで考えなかったため。レビューの指摘にも、手順の案内で応じた |
| なぜ規則で防げなかったか | ファイルを削除するときに`.gitignore`のエントリをどう扱うかの決まりがなかったため |

## 真因

削除したフォルダへの参照を外すときに、`.gitignore`のエントリの役目(古いコミットや手元の残りの生成物を守ること)を考えず、ほかの参照と同じに消した。自分で起こしかけた事故を、その場の現象への対処だけで終えた。

## 対策

1. 現象への対応: `.gitignore`に`/spikes/*/target`を戻し、過去の作業のフォルダのために残していることをコメントで書き添えた。
2. 規則: フォルダやファイルを削除しても、それに対応する`.gitignore`のエントリは消さず、コメントで理由を残す。そのフォルダをまた使うようになったら、エントリを見直す。AGENTS.mdの「ドキュメント」の節に加えた(メンテナーの指示)。
3. 仕組み: エントリの削除を機械的に止める検査は加えない。理由: `.gitignore`の変更はまれで、レビューと上の規則で見つけられる。

## 確かめ方

- `git check-ignore -v spikes/saver-spike/target/x`が、`.gitignore`の`/spikes/*/target`の行で無視されると示すこと(2026-11-09に確かめた)。
- 以後、フォルダを削除する変更のレビューで、`.gitignore`のエントリが残っていること。
