# 0020: incidentのステータスが、対策のマージのあとも古いままだった

- 日付: 2026-11-10
- ステータス: 対策済み(対策はPR #64とPR #65でマージした)
- 関連: [README](README.md)の「記録の書き方」、`.claude/commands/merge-pr.md`、`.claude/commands/consistency-check.md`

## 起きたこと

2026-11-10に、Phase 2の区切りの整合性の確認(`/consistency-check`)で、incident 0012、0013、0015、0016、0017、0018のステータスが、対策のPRがマージされたあとも「対策中(対策のPRがマージされていない)」のままだと分かった。

確かめた事実:

- `docs/incidents/README.md`の「記録の書き方」は、ステータスを「対策中」(対策がまだマージされていない)か「対策済み」と定めている。マージのあとに、誰が、いつステータスを直すかは書いていない。
- マージの手順(`.claude/commands/merge-pr.md`)にも、整合性の確認の項目(`.claude/commands/consistency-check.md`)にも、incidentのステータスを確かめる手順はない。
- 0012は2026-11-02に記録した。対策はその後にマージしたが、ステータスは2026-11-10まで古いままだった。
- これまで「対策済み」に直したもの(0014など)は、エージェントが思い出したときに、別の文書の変更の中で直していた。
- 2026-11-02にも、整合性の確認のあとで、同じように古いままだった0002・0004〜0011の9件を、まとめて「対策済み」に直していた(コミット`378dd14`)。このときは、文書の直しとして扱い、異常として記録しなかった。異常として扱わなかった理由は、記録にない。同じ種類の問題の再発にあたる。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜステータスが古いままだったか | 対策のPRをマージしたあとに、incidentのステータスを直さなかったため |
| なぜ直さなかったか | マージの手順と整合性の確認の項目に、ステータスを確かめる手順がなく、エージェントが思い出したときにだけ直していたため |
| なぜ手順がなかったか | ステータスの定義(対策がマージされたかどうか)を決めたときに、その状態が変わる時点(マージ)での作業を決めなかったため |
| なぜ2026-11-02に同じことが起きたときに、手順を加えなかったか | 古いステータスの一括修正を、整合性の確認で見つかる通常の文書の直しとして扱い、手順の欠け(異常)かどうかを考えなかったため。整合性の確認の結果を、異常に当たるかで分ける手順もない |

## 真因

ステータスの定義が、マージという外の出来事で変わるのに、その時点で直す手順がなかった。1回目(2026-11-02)にも、整合性の確認の指摘を異常に当たるかで分けなかったため、手順の欠けとして扱わなかった。

## 対策

1. 現象への対応: 6件のステータスを「対策済み」に直した(このincidentを記録した変更と同じPR)。0019は、対策はマージ済みで、メンテナーのWindowsでの確認を待っていることが分かる書き方にした。
2. 手順(2026-11-10にメンテナーが承認した):
   - マージの手順(`.claude/commands/merge-pr.md`の手順4)に、マージしたPRがincidentの対策を含む場合は、そのincidentのステータスを直す変更を、次の文書の変更で行う手順を加えた(マージしたPRの中では直せないため)。
   - 整合性の確認の項目(`.claude/commands/consistency-check.md`の6)に、incidentのステータスが、対策のPRのマージの状態と合っているかを加えた。
   - 整合性の確認の報告で、指摘のそれぞれが異常(規則や手順の欠け、同じ種類の再発)に当たるかも示し、異常に当たるものは記録するよう、同じ文書に加えた。
3. 仕組み: 機械的な検査は加えない。理由: ステータスとPRの対応は文章で書かれていて、機械的に読み取るには記録の形を変える必要がある。整合性の確認(フェーズの区切りごと)で拾う。

- 次のフェーズの区切りの整合性の確認で、incidentのステータスが古いままのものがないこと。
