# 0002: レビューの指摘の修正で、不要なCIが走った

- 日付: 2026-11-01
- ステータス: 対策済み

## 起きたこと

PR #16(スパイクの修正)で、軽いレビューの指摘(low)に対応した。手順書(`spikes/README.md`)に1文を加えただけの修正を、単独でプッシュした。`spikes/`の下の変更だったため、Windowsのランナーでスパイクのビルド(数分)が、もう一度走った。前の実行は、ワークフローの`concurrency`の設定で取り消された。

メンテナーの方針は「GitHub Actionsは、必要な実行は惜しまないが、不要な実行は最小限にする」である。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ不要なCIが走ったか | 文書の1文の修正を単独でプッシュし、パスの条件(`spikes/**`)に当たったため |
| なぜ単独でプッシュしたか | PRを作ってプッシュしたあとでレビューを行い、その指摘の修正をもう一度プッシュする必要があったため |
| なぜプッシュのあとでレビューするのか | AGENTS.mdとレビュー手順が「PRを作る→レビューを依頼する」の順で、PRの差分をレビューの対象にしていたため。「修正はまとめて1回でプッシュする」規則(ADR-0017)を守っても、最初のプッシュとレビュー後のプッシュの2回は、構造的に避けられない |
| なぜその順にしたのか | レビュー用のエージェントはリモートのブランチを読むもの、という前提で手順を作ったため。実際には、同じリポジトリの別のworktreeから、プッシュの前のローカルのコミットをレビューできる |

## 真因

レビューの手順が「プッシュしてからレビューする」順になっていて、指摘が1件でもあれば、CIが必ずもう1回走る構造になっていた。

## 対策

- レビューを、プッシュの前に行う。ローカルでコミットし、別のworktreeのレビュー用エージェントにローカルのブランチを渡す。指摘を直してから、最初のプッシュとPRの作成を行う([ADR-0018](../adr/0018-review-before-push.md)、AGENTS.md、レビュー手順、`/babysit-pr`)。
- GitHub Actionsの方針(必要な実行は惜しまず、不要な実行を避ける。手動実行は成果物が必要なときだけ)を、AGENTS.mdに記した。

## 確かめ方

- レビューで指摘があったPRでも、CIの実行が原則として1回(最初のプッシュ)で済むこと。
- 例外(再レビュー、CIの失敗、人間のレビュー)のときも、修正をまとめて1回でプッシュしていること。
