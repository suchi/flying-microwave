# 0002: レビューの指摘の修正で、不要なCIが走った

- 日付: 2026-11-01
- ステータス: 対策中(対策のPRがマージされていない)

## 起きたこと

PR #16(スパイクの修正)で、軽いレビューの指摘(low)に対応した。手順書(`spikes/README.md`)に1文を加えただけの修正を、PRのブランチにプッシュした。`spikes/`の下の変更だったため、Windowsのランナーでスパイクのビルド(数分)が、もう一度走った。前の実行は、ワークフローの`concurrency`の設定(`cancel-in-progress: true`)で取り消された。

メンテナーの方針は「GitHub Actionsは、必要な実行は惜しまないが、不要な実行は最小限にする」である。

## なぜなぜ分析

| なぜ | 答え |
| --- | --- |
| なぜ不要なCIが走ったか | PRがすでにあるブランチにプッシュしたため(事実: `ci.yml`と`spikes.yml`は`pull_request`で起動し、PRのブランチへのプッシュで再び走る。`spikes.yml`はパスの条件`spikes/**`に当たった)。PRのないブランチへのプッシュでは、CIは走らない(事実: 2つのワークフローの`on:`。2026-11-01に、PRのないブランチへのプッシュでCIが走らないことも確かめた) |
| なぜPRのあるブランチに、レビューの修正をプッシュしたか | PRを作ってからレビューを行い、その指摘の修正をPRに入れる必要があったため(事実: 当時のAGENTS.mdの「PR・レビュー・マージ」は、PRを作る→レビューを依頼する、の順) |
| なぜPRを作ってからレビューするのか | レビューの対象をPRの差分としていたため。「修正はまとめて1回でプッシュする」規則(ADR-0017)を守っても、PRを作ったときとレビューの修正のあとの2回は、構造的に避けられない |
| なぜその順にしたのか | 推測: レビュー用のエージェントは、PRやリモートのブランチを読むもの、という前提で手順を作ったと考えられる。実際には、同じリポジトリの別のworktreeから、PRを作る前のブランチをレビューできる |
| なぜADR-0015・0017の分析で気づかなかったか | 当時もCIの待ち時間を分析したが、「修正をまとめて1回でプッシュする」という途中の対策で止め、CIを起動する条件(PRのイベント)と手順の順番までさかのぼらなかったため。異常への対応の手順がなかったという、[0001](0001-english-text-shown-to-maintainer.md)の真因2と同じ根である |

## 真因

レビューの手順が「PRを作ってからレビューする」順になっていて、指摘が1件でもあれば、CIが必ずもう1回走る構造になっていた。

## 対策

- 敵対的レビューを、PRを作る前に行う。ブランチへのプッシュは、作業を残すためにいつ行ってもよい(PRがなければCIは走らない)。指摘を直してから、PRを作る([ADR-0018](../adr/0018-review-before-opening-pr.md)、AGENTS.md、レビュー手順、`/babysit-pr`)。
- GitHub Actionsの方針(必要な実行は惜しまず、不要な実行を避ける。手動実行は成果物が必要なときだけ)を、AGENTS.mdに記した。

## 確かめ方

- 対策のあとのPRで、PRのワークフローの実行が、原則として1回(PRを作ったとき)で済んでいること。GitHubのActionsの実行の一覧で確かめる。
- 例外(CIの失敗、人間のレビュー)のときも、修正をまとめて1回でプッシュしていること。
