# 0011: 診断用のログが、要件に反していつも書かれていた

- 日付: 2026-11-02
- ステータス: 対策済み(対策はPR #34でマージした)
- 関連: [0010](0010-onboarding-missed-build-steps.md)(書いてあることの正しさだけを確かめ、ほかの文書との突き合わせが抜けた点が近い)

## 起きたこと

v1.0.0までの懸念事項を洗い出すため、計画の非機能要件を読み直したところ、マージ済みのコードが要件に反していることに、エージェントが気づいた。

- 計画のN-07は「`/s`・`/p`の実行中はファイルに書き込まない(ログを有効にした場合を除く)」である。
- アーキテクチャの「エラー処理とログ」は「ログは既定で出力しない。調査用に有効化する手段(環境変数または設定キー)をPhase 1で決める」である。
- 実装(`crates/app/src/log.rs`)は、有効にする手段を持たず、いつも一時フォルダの`flying-microwave.log`に書く。`v0.1.0-alpha.2`と`v0.1.0-alpha.3`は、この動作のまま公開された。

確かめた一次情報:

- `git log`: ログは、最初に動く版のコミット0a627bb(PR #21、2026-11-01)で加わった。コミットの説明は「実機で原因を調べられるよう、要点だけを一時フォルダのログに書く」で、要件との違いには触れていない。
- 計画の決定事項(D-xx)、ADR、レビュー記録に、この違いを認めた記録はない。
- レビューの手順(`docs/development/review-process.md`)の観点は、正しさ、セキュリティ、テストの不足、YAGNI、個人情報、オンボーディングの一覧である。差分を計画の要件(F-xx、N-xx)やアーキテクチャの方針と突き合わせる観点はなかった。`/consistency-check`の点検項目も、文書と文書、文書とコマンドの整合だけだった。
- 実害: ログには利用者のデータは含まれず、1MBで書き直す。利用者のディスクに、小さなファイルが1つ残るだけである。一方で、ログは実機での問題の調査(`/p`のプレビューの確認など)に使われ、役に立っている。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ要件に反したコードが公開されたか | 要件と違う動作が、レビューでもリリースの前の確認でも見つからなかったため。リリースの前の確認(7.1の条件5)は、文書が実態と合っているかを見るもので、CHANGELOGはログを書くことを正しく書いていた。要件と実装の違いは、この確認の対象ではなかった |
| なぜ作成者は要件と違う動作を入れたか | 最初に動く版を実機で確かめるために、ログが必要だった。作成者(エージェント)は、そのときの目的から判断し、N-07とアーキテクチャの方針を読み直さなかった。要件と違う実装をするときに確認や記録をする決まりは、AGENTS.mdの「曖昧な点は勝手に判断せず確認する」だけで、要件との違いを対象にした決まりがなかった |
| なぜPhase 1で、有効にする手段を決めなかったか | アーキテクチャの「有効化する手段をPhase 1で決める」が、計画のPhase 1の作業(1〜14)にも完了条件にも登録されていなかった(計画で「ログ」が出てくるのはN-07だけだった)。設計の文書やADRで先送りした決定を、計画の作業に登録する決まりがなく、そのフェーズで決める機会がなかった |
| なぜレビューで見つからなかったか | レビューの観点に、差分を計画の要件とアーキテクチャの方針と突き合わせる項目がなかった。レビュアーには計画とアーキテクチャを根拠として渡していたが、何と突き合わせるかは指定していなかった |
| なぜフェーズの区切りの点検でも見つからない仕組みだったか | `/consistency-check`は、文書どうしと、文書とコマンドの整合だけを見る。要件と実装の突き合わせは、どの点検にも割り当てられていなかった |

## 真因

1. 計画の要件や設計の方針と違う実装をするときに、実装の前に確認して記録する決まりがなかった。
2. レビューと`/consistency-check`の観点に、実装を要件(F-xx、N-xx)とアーキテクチャの方針と突き合わせる項目がなかった。
3. 設計の文書やADRで「Phase Nで決める」と先送りした決定を、計画のそのフェーズの作業や完了条件に登録する決まりがなかった。

## 対策

1. 現象への対応: メンテナーの判断で、v0.x系の間は今の動作(いつも書く)を続け、N-07とアーキテクチャの記述を改めた。v1.0.0までに、既定では書かない形にする(計画のD-25、Phase 6の作業3)。
2. 真因1への対策: AGENTS.mdの「進め方」に、「計画の要件や設計の方針と違う実装が必要になったら、実装の前にユーザーに確認し、決定として記録する。要件と違う実装を、記録なしにマージしない」を加えた。
3. 真因2への対策:
   - レビューの手順の観点に、製品のコードの差分を、計画の要件とアーキテクチャの方針と突き合わせ、反する場合は決定の記録があるかを確かめる項目を加えた。
   - `/consistency-check`に、「要件と実装」の点検項目を加えた。フェーズの区切りごとに、全体を突き合わせる。
4. 真因3への対策: AGENTS.mdの同じ箇条に、「設計の文書やADRで、決定を後のフェーズに先送りしたときは、計画のそのフェーズの作業か完了条件に登録する」を加えた。`/consistency-check`の「要件と実装」の項目で、設計の文書とADRの先送りした決定が、計画に登録されているかも確かめる。今の文書を確かめた範囲では、ほかに未登録のものは、ADR-0012(単独アプリ)の実装時の決定だけで、Phase 6の作業4(実装時期の判断)で扱う。設定ファイルの保存場所(Phase 2の着手前にADRで決める)は、Phase 2の作業1に登録されている。
5. 機械的な検査は採らない。要件の多くは自然言語で書かれた振る舞い(副作用、表現、操作)で、機械で突き合わせられないため。代わりに、レビュー(差分ごと)と`/consistency-check`(フェーズの区切り)の2段で確かめる。自動で確かめられる要件(N-02の終了の速さ、プロセスが残らないことなど)は、スモークテスト(作業14。v0.1.1)で確かめる。

## 確かめ方

- v0.1.0の前の`/consistency-check`の報告に、「要件と実装」の項目の結果が、F-xx・N-xxの番号ごとと、先送りした決定ごとに含まれていること。
- v1.0.0までに、要件と違う実装が、決定の記録(D-xx、ADR)なしにマージされていないこと。各フェーズの区切りの`/consistency-check`で確かめる。
- 以後の製品のコードのレビューの報告に、要件と方針との突き合わせの結果が含まれること。

## その後の確認

- 2026-11-02、v0.1.0の前の`/consistency-check`(対策を入れてから最初の実行)で、「要件と実装」の項目が番号ごとに点検され、同じ種類の食い違いがさらに見つかった。対策が働いたことを示す(確かめ方の1つめ)。
  - SEC-1のリンカ設定(`/DEPENDENTLOADFLAG`)が実装されていなかった: v0.1.0の前に実装した。
  - アーキテクチャのA-2・A-8(構成)、インスタンス描画、GPUの初期化のタイムアウトが、実装と違っていた: メンテナーの判断で、文書を実装に合わせ、計画のD-27に記録した。
  - アーキテクチャとスパイクのREADMEで「Phase 0の終了時に決める」とした`spikes/`の扱いが、計画に登録されていなかった: 計画のD-28に記録し、Phase 2の完了条件に登録した。
- どれも、対策の前にマージされたものである。対策のあとに、記録なしにマージされた食い違いはない。
