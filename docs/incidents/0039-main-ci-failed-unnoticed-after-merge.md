# 0039: マージのあとのmainのCIが2回続けて失敗し、気づかなかった

- 日付: 2026-11-21
- ステータス: 対策済み(試験の直しはPR #90、手順と規則の対策(計画0005のD-26の(3))はPR #91でマージした。このステータスは、PR #91のマージのあとで直し忘れ、2026-11-22に直した(incident 0029の「その後の再発」))
- 関連: [0030](0030-push-checked-check-runs-not-workflow-runs.md)(ワークフローの実行の一覧で確かめる)、[0009](0009-guard-hooks-never-ran.md)(フックの動作の検査)、AGENTS.mdの「PR・レビュー・マージ」

## 起きたこと

2026-11-21に、作業ブランチの差分の敵対的レビューで、mainのCIが失敗していると指摘を受けた。エージェントは、それまで気づいていなかった。マージ済みの`main`の欠けで、AGENTS.mdの「進め方」の異常に当たる。

確かめた事実:

- mainへのpushで動いたCIの実行206(PR #88のマージ、2026-11-20 14:41(JST))と実行208(PR #89のマージ、同じ日の23:53(JST))が、どちらも失敗した。その前の実行200(PR #87のマージ)は成功していた(GitHubのワークフローの実行の一覧。ブランチ`main`、`ci.yml`)。
- 実行208では、「Linux (workspace)」のジョブが「Check Claude Code hooks」(`python3 -I scripts/check_hooks.py`)で失敗し、そのあとの段(依存の公開からの日数、書式、Clippy、テスト、Windowsの型チェック)と、Windowsのジョブ(ビルド、スモークテストなど)が飛ばされた(実行208のジョブの一覧)。ログには「`.claude/hooks/block-dangerous-git.sh: 終了コード0、判断'ask'(期待はNone) … mainに直接コミットしようとしています …`」とあった。
- `block-dangerous-git.sh`は、今いるブランチが`main`か`master`のとき、`git commit`を含むコマンドに`ask`を返す(`git branch --show-current`。フックの「`git[[:space:]]+commit`」の段)。`check_hooks.py`は、フックをリポジトリのルートで起動していた(`subprocess.run(..., cwd=root, ...)`)。そのため、`main`を取り出したCIでは、期待が`None`の`git commit -m 'block pushing to main'`の試験の入力に`ask`が返った。
- PRのCIは、マージ用の参照を、ブランチのない状態で取り出す(実行207のログの「`git checkout --progress --force refs/remotes/pull/89/merge`」と「You are in 'detached HEAD' state.」)。ブランチ名が空になるため、PRのCIでは通った。手元の作業ブランチでも通った。
- この試験の入力は、コミット`9c6f19e`(2026-11-19、PR #88。`git log -S"block pushing to main" -- scripts/check_hooks.py`)で加わった。
- PR #88とPR #89は、メンテナーの指示で、エージェントがGitHubのツールでマージした。マージのあとで、mainのCIの結果は確かめなかった。

## なぜなぜ分析

1. なぜmainのCIが失敗したか。
   - 試験の入力の結果が、`check_hooks.py`を実行したリポジトリで取り出しているブランチに左右され、`main`の上でだけ期待と違ったため(上の事実)。
2. なぜ、それがマージの前に分からなかったか。
   - PRのCIはブランチのない状態で、手元は作業ブランチで動き、どちらも`main`の上で実行しなかったため(実行207のログ)。試験の入力を加えたとき、フックがブランチを見ることを考えなかった(推測。根拠は、`9c6f19e`で加えた試験の入力が、ブランチを指定する仕組みなしに`git commit`の結果を`None`と期待していること)。
3. なぜ、マージのあとで気づかなかったか。
   - マージの手順(`.claude/commands/merge-pr.md`)に、マージのあとでmainのCIの結果を確かめる段がない(全文を読んで確かめた。前提条件の「CIの全ジョブがグリーン」は、PRのCIのこと)。AGENTS.mdの「PR・レビュー・マージ」は、マージのあとのmainでの実行を「必要な実行に含まれる」とするが、結果を確かめることは定めていない。
   - PRの通知の購読は、マージのあとで外していて、mainのCIの結果は届かない。
4. 真因: 試験がそれを実行した場所の状態(ブランチ)に頼っていた。マージのあとのmainのCIを確かめる手順がない。

## 真因

- `check_hooks.py`の試験の結果が、実行したリポジトリのブランチに左右された。
- マージの手順に、マージのあとのmainのCIの結果を確かめる段がない。

## 対策

行ったこと(このincidentを記録したPR):

- `check_hooks.py`は、フックを、試験の入力ごとに決まったブランチ(既定は`check-hooks`。入力の`_branch`で指定する)の一時的なリポジトリで起動するようにした。相対パスの`transcript_path`は、ルートを基準にした絶対パスに直して渡す。`main`の上のコミットに`ask`が返ることも、試験の入力に加えた。`main`を取り出した複製で、直す前の`check_hooks.py`は2件失敗し、直したあとは通ることを確かめた。

案(承認が要る。メンテナーの判断を待っている):

1. 手順: `merge-pr.md`に、マージのあとで、そのマージのコミットのmainのCIの実行(ワークフローの実行の一覧をブランチ`main`で絞り、`head_sha`で見つける)が終わるのを待って結果を確かめ、完了報告に書く段を加える。失敗していたら異常として扱う。あわせて、前提条件に「mainの最新のCIの実行が成功している(失敗していれば、その原因を直すPRでない限りマージしない)」を加える。
2. 規則: AGENTS.mdの「PR・レビュー・マージ」の手順7に、1と同じことを書き添える。

2026-11-21に、メンテナーが案1と2を採った(計画0005のD-26の(3))。

仕組みの検討:

- 採った仕組み: 試験の結果が実行した場所に左右されないよう、`check_hooks.py`を変えた(上の「行ったこと」)。記録とフックの写しを使い、手元の作業ツリーの状態にも左右されないようにした(再レビューの指摘)。
- 採らなかった仕組み: mainのCIの失敗を、フック(たとえばセッションの開始のフック)で知らせること。フックからGitHubの状態を読むには、GitHubのAPIを呼ぶ手段が要るが、このリポジトリの規則では`gh`を検索にだけ使い、GitHubの操作はエージェントのツールで行うため、フックから確実に読む手段がない。ブランチ保護でmainのCIの失敗を次のマージの条件にすることも、GitHubのルールセットはPRのチェックを条件にするもので、mainへのpushの実行の結果は条件にできないため、採らない(推測。ルールセットの文書は、この判断のために読んでいない。次のPRで確かめる)。

その後の確認:

- PR #90のマージ(2026-11-21 11:12(JST)、`d154cdc`)のあとのmainのCIの実行210は、フックの検査を含め、LinuxとWindowsのジョブがすべて成功した(11:33(JST)に終了。ワークフローの実行の一覧)。マージの手順の対策(案1と2)は、そのあとのPRで`merge-pr.md`とAGENTS.mdに加えた。

## 確かめ方

- このincidentを記録したPRのマージのあとで、mainのCIの実行が成功すること。
- 1を採った場合: 次のマージから、完了報告にmainのCIの結果が書かれること。
