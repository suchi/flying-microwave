## 起きたこと

2026-11-27に、ランディングページ(計画0006)の本格的なレビューを受けた(対象のhead `e50c5d8`)。レビューは、ほかのサイトから読み込まないことの検査(`scripts/test_site.py`。N-02)に抜け道があると指摘した(指摘M-2)。エージェントは`d8baaa1`(2026-11-27 15:12 JST)で検査を改めた。再レビュー(対象のhead `f055e17`)は、同じ種類の抜け道が6つ残っていると指摘した(指摘M-A)。再レビューの担当は、その6つの書き方を入れた写しのサイトを配信し、Chromiumが実際にほかのサイトへ要求を出すことを確かめていた。同じ種類の問題の再発なので、異常として扱う(AGENTS.mdの「進め方」)。

確かめた事実:

- `d8baaa1`の`scripts/test_site.py`は、ファイルの種類、HTMLの要素と属性を許可した一覧で確かめていた。一方、値の検査は、禁止する形の正規表現のままだった(49行の`OUTSIDE`と50行の`CSS_OUTSIDE`。`git show d8baaa1:scripts/test_site.py`で確かめた)。
- そのコミットのメッセージは「許可した一覧の形に改めた」と書いていた。値の検査は、その形になっていなかった。
- `d8baaa1`で加えた抜け道のテストは、1回目のレビューが挙げた15の書き方を、1つずつ写しのサイトに入れるものだった。それ以外の書き方は試していなかった(同じコミットの`test_the_check_finds_the_ways_around_it`)。
- 再レビューが挙げた6つは、次の3つの性質を使っていた(再レビューの報告による)。
  - ブラウザーはURLの中のタブと改行を取り除く(`ht&#9;tps:`、属性の値の中の改行、`/&#9;/`)。
  - CSSは逆斜線のエスケープを読む(`url(\68ttps\3a//…)`、`url("\2f/…")`、`@\69mport`)。
  - 前回の検査は、どちらの解釈も再現していなかった。
- 直した検査(`78ded35`、2026-11-27 15:27 JST)は、hrefとsrcを、GitHubへの2つのリンクのほかは、決まった文字だけの相対のパスに限る。CSSは、url(、image-set(、@import、@font-faceと逆斜線を、どれも拒否する。6つの書き方を抜け道のテストに加え、直す前に6件とも見逃されることを確かめた。

## なぜなぜ分析

1. なぜ、同じ種類の抜け道が残ったか。
   - 値の検査が、禁止する形の正規表現のままだったため。ブラウザーとCSSが値をどう解釈するか(タブと改行の除去、逆斜線のエスケープ)を、検査が再現していなかった(上の「確かめた事実」)。
2. なぜ、値の検査を禁止する形のまま残したか。
   - 指摘M-2を直すときに、レビューが挙げた15の書き方をふさぐことを目標にし、それを1つずつ試すテストで終わりとしたため(`d8baaa1`のテストの中身で確かめた)。要素と属性は許可した一覧にしたが、値は、挙げられた書き方を見つける正規表現を広げるだけにした。値を読む側(ブラウザーのURLの解析、CSSの構文)の規則は、確かめなかった。
3. なぜ、挙げられた書き方をふさぐだけで終わりとしたか。
   - 検査の抜け道を直すときに、見つかった書き方の種類全体(読む側の解釈で同じ結果になる書き方)を閉じる段が、手順にないため。レビューの手順(`docs/development/review-process.md`)とAGENTS.mdの「PR・レビュー・マージ」は、指摘を一次情報で確かめて直すことを求めるが、検査の抜け道の直し方は定めていない(どちらも読み直して確かめた)。
4. 真因: 安全のための検査の抜け道を直すときに、既定で拒否する形(許可した一覧)にすることと、読む側の解釈を一次情報で確かめることを求める段がない。

## 真因

- 安全のための検査の抜け道の指摘を、挙げられた書き方をふさぐことで直し、種類全体を閉じる段がない。

## 対策

行ったこと:

- 検査を、値も含めて許可した一覧の形にした(`78ded35`)。hrefとsrcは相対のパスとGitHubへの2つのリンクだけ、CSSは読み込みに使える書き方をどれも拒否する。再レビューが挙げた6つを、抜け道のテストに加えた。

案(手順の文書の変更なので、メンテナーの承認が要る。2026-11-27に、メンテナーが(1)を採った。`docs/development/review-process.md`の「対応」の行に、案のとおりに加えた):

1. 手順: `docs/development/review-process.md`の指摘への対応の段に、次を加える。安全のための検査(読み込み、権限、入力の検査など)の抜け道の指摘を直すときは、挙げられた書き方だけをふさがない。既定で拒否する形(許可した一覧)にし、値を読む側(ブラウザー、シェルなど)の解釈を一次情報で確かめる。直したあとで、挙げられていない書き方も1つ以上試す。
2. 仕組み: 採らない案として記録する。CIで実際のブラウザー(Playwright)にページを開かせ、ほかのサイトへの要求が0件であることを確かめる案がある。読む側の解釈をそのまま確かめられるが、CIに新しい依存(Playwrightとブラウザー)が要る。いまの検査は、値を決まった文字だけの相対のパスに限ったため、読む側の解釈に左右される余地は小さい。依存を増やすかは、計画0006の範囲を超える判断になる。

## 確かめ方

- このあとで、安全のための検査の抜け道を直すときに、許可した一覧の形にしたことと、挙げられていない書き方を試したことを、コミットのメッセージかPRのまとめコメントに書くこと。
- 計画0006のPRのあとで、ページの検査の抜け道がレビューで見つからないこと。

## その後の再発

2026-11-27に、`v0.3.0`の公開のあとでページに食べ物を加える変更(計画0006のD-8)で、同じ種類の問題が起きた。上の「確かめ方」の2つ目が満たされなかった。

## その後の再発(3回目)
