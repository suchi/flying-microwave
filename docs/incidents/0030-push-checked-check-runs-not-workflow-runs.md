# 0030: プッシュの前にPRのチェックだけを見て、待ち行列のCIの実行に気づかずにプッシュした

- 日付: 2026-11-14
- ステータス: 対策中(真因への対策は、2026-11-14にメンテナーが承認し、まだマージしていない)
- 関連: [0008](0008-push-cancelled-running-pr-ci.md)(PRのCIの実行中にプッシュした。同じ種類の問題の再発)、[0028](0028-smoke-failure-merged-on-a-guess.md)(この作業の目的)、PR #82

## 起きたこと

2026-11-14に、incident 0028の調べのための試しのPR #82で、次の順に作業した。

1. 試しの案Bを打ち消すコミット`155dc6d`をプッシュした。
2. 次の試し(案E)のコミットを作ってから、プッシュしてよいかを確かめた。
3. 確かめた先は、PRのチェックの一覧(GitHubのツールの`pull_request_read`の`get_check_runs`)だった。結果は0件だった。
4. エージェントは、実行中のCIはないと判断し、案Eのコミット`0ac489d`をプッシュした。

実際には、`155dc6d`のCIの実行183(id 43584922377)が、その時点で待ち行列にあった。

確かめた事実:

- 実行の一覧(GitHubのツールの`actions_list`の`list_workflow_runs`。ブランチで絞った)で確かめた。
  - 実行183は、2026-11-14 19:21:50(JST)に作られ、状態は`queued`だった。
  - 案Eの実行184は、19:23:16(JST)に作られた。
- 実行183のジョブ(Linux)は、19:23:25(JST)に作られ、`queued`だった。プッシュの時点では、まだジョブがなかった。
- PRのCIは、新しいプッシュで前の実行を取り消す設定である(`.github/workflows/ci.yml`の24〜27行目の`concurrency`と`cancel-in-progress`)。そのため、実行183は取り消される。
- AGENTS.mdの「PR・レビュー・マージ」の手順6は、次のことを求めている。0008の対策として入った規則である。
  - プッシュの前に、そのPRのワークフローの実行の一覧で、実行中のものがないことを確かめる。
  - 新しい実行が起動するかどうかを予測して、この決まりを外さない。
- エージェントは、チェックが0件だった理由を「差分が文書だけでCIが起動しなかった」と、確かめずに書いた。CIの設定には`paths`の条件はない(`ci.yml`を`paths`で検索して、該当なし)。その直後に訂正した。
- 失われたのは、`main`と同じコードでのスモークテストの値1回分である。製品やリリースへの影響はない。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜCIの実行中にプッシュしたか | プッシュの前に、ワークフローの実行の一覧ではなく、PRのチェックの一覧を見て、0件だったため(このセッションの作業の記録) |
| なぜチェックの一覧では見つからなかったか | チェックは、実行のジョブが作られてから現れる。実行183は待ち行列にあり、プッシュの時点ではジョブがまだなかった(実行183のジョブの作成は19:23:25(JST)で、プッシュの直後) |
| なぜチェックの一覧で足りると判断したか | 手順6は「ワークフローの実行の一覧」と書いているが、チェックの一覧ではいけないこと(待ち行列の実行を含まないこと)は書かれていない。エージェントは、両者を同じものとして扱った |

## 真因

1. 手順6が、確かめる先を「ワークフローの実行の一覧」とだけ書き、待ち行列の実行(`queued`、`pending`など)も含めて確かめることを書いていない。PRのチェックの一覧では足りないことも書いていない。そのため、似た一覧で代えられてしまう。

## 対策

1. 現象への対応: この記録を書いた。実行183の取り消しを、PR #82のまとめコメントに記録する。
2. 真因への対策(2026-11-14にメンテナーが承認した): AGENTS.mdの「PR・レビュー・マージ」の手順6の「プッシュの前に、そのPRのワークフローの実行の一覧で実行中のものがないことを確かめ」を、次のように具体的にする。
   - ブランチで絞ったワークフローの実行の一覧で、状態が`queued`、`pending`、`waiting`、`requested`、`in_progress`の実行がないことを確かめる。
   - PRのチェック(check runs)の一覧は、ジョブが作られる前の実行を含まないため、この確かめには使わない。
   - 同じことを、`docs/development/review-process.md`の表の「対応」の行(42行目)に書く。
   - 同じ確かめ方を書いた`.claude/commands/babysit-pr.md`(手順2のc)と`.claude/commands/ship.md`(手順4)も、同じ文言に合わせる(検索した方法: リポジトリ全体で「実行中のものがないこと」を`grep`した)。
3. 仕組み: 機械的な検査は加えない。理由: 0008の対策4と同じく、フックからGitHubのAPIを使う認証が、実行環境によってそろっていないため。

## 確かめ方

- 以後のPRを作ったあとのプッシュで、プッシュの前に、ワークフローの実行の一覧で、待ち行列を含めて確かめたことが、報告に示されていること。
