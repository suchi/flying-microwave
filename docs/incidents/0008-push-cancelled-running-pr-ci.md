# 0008: PRのCIの実行中にプッシュし、終わりかけのビルドを取り消した

- 日付: 2026-11-01
- ステータス: 対策中(対策のPRがマージされていない)

## 起きたこと

PR #23(依存の7日の対策)で、PRのCIの実行中に、文書だけのコミット(incidents 0007にGitHub Actionsの公開日を記録したもの)をプッシュした。その結果、次のことが起きた。

- 実行中だったスパイクのビルド(`spikes.yml`の20番、head 1d00e43)が取り消された。20番は11:44:33に始まり、11:56:41に取り消された。成功した実行では12分ほどかかるため、終わる直前だった。
- 新しい実行(21番、head 22935b8)が始まり、ビルドをやり直した。21番は11:56:32に始まり、12:09:05に成功した。
- 結果として、Windowsのランナーで約12分のビルドが無駄になり、マージできるまでの時間も約12分延びた。

プッシュの前に、エージェントは20番が実行中であることを確かめていた。そのうえで、メンテナーに「文書だけのコミットなので、スパイクのビルドは走らず、取り消されない」と説明してから、プッシュした。この説明は誤りだった。

メンテナーの方針は「GitHub Actionsは、必要な実行は惜しまないが、不要な実行は最小限にする」である。不要なCIの実行は、[0002](0002-extra-ci-run-after-review.md)・[0003](0003-cancelled-maintainer-spike-run.md)に続いて3回目で、同じ種類の問題の再発にあたる。

確かめた一次情報:

- `spikes.yml`の`on.pull_request.paths`(`spikes/**`、`.github/workflows/spikes.yml`、`rust-toolchain.toml`、`.cargo/config.toml`)と、`concurrency`(PRでは`cancel-in-progress: true`)。
- GitHubの公式ドキュメント(Workflow syntaxの「Git diff comparisons」): 変更されたファイルの一覧は、pull_requestではthree-dot diff、つまり分岐した時点からPRの最新までの差分で作られる。プッシュ1回ごとの差分ではない。
- PR #23全体の差分には、`spikes/`の下のロックファイルと`spikes.yml`が含まれていた。そのため、文書だけのコミットでも条件に当たった。
- Actionsの実行の一覧(20番と21番の開始・終了の時刻と結果)。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜビルドが取り消されたか | PRのブランチにプッシュして新しい実行が始まり、`cancel-in-progress`で前の実行が取り消されたため |
| なぜ文書だけのコミットで、スパイクのビルドが始まったか | pull_requestの`paths`の条件は、PR全体の差分(three-dot diff)で判定されるため。PR #23は`spikes/`の下と`spikes.yml`を変えていた |
| なぜ「走らない」と判断したか | `paths`の条件はプッシュ1回ごとの差分で判定される、と思い込んでいたため。公式ドキュメントで確かめなかった |
| なぜ確かめずにプッシュできたか | AGENTS.mdの決まりは「外部に作用する操作の前に、その時点の状態(進行中のワークフローの実行など)を確かめる」だけで、実行中のときにどうするかを定めていなかったため。状態を確かめたあと、影響の判断を推測で行う余地が残っていた |
| なぜ実行の終了を待たなかったか | そのコミットは文書の記録で、急ぐ理由はなかった。それでも、待つという手順がなかったため、プッシュを優先した |

## 真因

1. PRのCIの実行中にプッシュしない、という決まりがなかった。そのため、プッシュしてよいかを、新しい実行が起動するかどうかの予測で決めていた。
2. その予測の前提(`paths`の条件の判定方法)を、一次情報で確かめていなかった。開発参加者向けの文書にも、書かれていなかった。

## 対策

1. AGENTS.mdの「PR・レビュー・マージ」の手順6に、次の決まりを加えた。
   - PRを作ったあとは、そのPRのCIの実行中にプッシュしない。プッシュの前に、そのPRのワークフローの実行の一覧で、実行中のものがないことを確かめる。実行中なら、終わるのを待ってから、まとめて1回でプッシュする。
   - 新しい実行が起動するかどうかを予測して、この決まりを外さない。
   - 例外は1つだけとする。実行中の実行のジョブがすでに失敗していて、そのプッシュがその失敗を直すものなら、待たなくてよい。その実行の結果はもう使えず、待っても無駄な時間が増えるだけのため。このとき取り消される実行は、まとめコメントに記録する。
2. 同じ決まりを、レビュー手順([review-process.md](../development/review-process.md)の「対応」)、`/babysit-pr`、`/ship`にも加えた。
3. オンボーディングの「4. レビューとマージ」に、pull_requestの`paths`の条件はPR全体の差分で判定されることを書いた。公式ドキュメントへのリンクも付けた。
4. 機械的な確認は採らない。
   - 採らなかった案: `git push`の前にフックで実行中のワークフローを調べる案。フックからGitHubのAPIを使うには認証が要るが、エージェントの実行環境によって、認証の手段がそろっていない。認証がそろっていない環境でフックを止めると、作業を残すためのプッシュ(PRのないブランチへのプッシュ)まで止まってしまう。
   - 採らなかった案: `spikes.yml`に、プッシュ1回ごとの差分で判定するジョブの条件を加える案。ワークフロー(セキュリティ設定)が複雑になるため。
   - 代わりに、上の決まりを、実際にプッシュする手順(手順6、レビュー手順、`/babysit-pr`、`/ship`)に書いた。

## 確かめ方

- 以後のPRで、`cancel-in-progress`によって取り消されたPRの実行がないこと。GitHubのActionsの実行の一覧で、結果が`cancelled`の実行を確かめる。
