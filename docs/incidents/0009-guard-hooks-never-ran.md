# 0009: 防御のフックが、最初から一度も働いていなかった

- 日付: 2026-11-01
- ステータス: 対策済み(対策は`main`にマージした。2026-11-02に確かめた)
- 関連: [0001](0001-english-text-shown-to-maintainer.md)、[0005](0005-english-notes-between-tool-calls.md)(フックによる対策)

## 起きたこと

表示の検査のフックを外す変更の本格的なレビューで、範囲外の所見として、次のことが指摘された。2つの防御のフックに実行権限がなく、起動に失敗しているおそれがある。エージェントが一次情報で確かめたところ、事実だった。

- `block-dangerous-git.sh`: 危険なgit操作(`main`への直接のプッシュ、force push、`--no-verify`など)を拒否するか、確認を求める。
- `protect-config.sh`: セキュリティ設定のファイルの編集の前に、確認を求める。

確かめた一次情報:

- `git ls-files -s .claude/hooks/`: 2つのフックのモードは100644(実行権限なし)だった。最初のコミット(f467cb7、2026-10-31)から、ずっとこの状態だった。日本語を確かめるフック(0001と0005で加えたもの)は100755だった。
- `.claude/settings.json`: 2つのフックは、パスで直接起動するように登録されていた(`"$CLAUDE_PROJECT_DIR/.claude/hooks/block-dangerous-git.sh"`)。
- 登録したとおりの起動の再現: `sh -c`で同じ文字列を起動すると、`Permission denied`で、終了コードは126だった。
- Claude Codeの公式ドキュメント(Hooks reference): 終了コード0と2以外は、止めないエラーとして扱われ、操作はそのまま続く。

影響:

- 2つのフックは、何も止めていなかった。
- `main`への直接のプッシュとforce pushは、GitHubのルールセットでも禁止されていたため、そちらで防がれていた(オンボーディングの9.1)。
- セキュリティ設定の変更は、これまでメンテナーの承認を得てから行っていた。ただし、それはエージェントが規則を守っていたためで、仕組みが止めていたためではない。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ止めなかったか | 起動が終了コード126で失敗し、止めないエラーとして扱われたため |
| なぜ起動に失敗したか | 実行権限のないファイルを、パスで直接起動するように登録していたため |
| なぜ実行権限がなかったか | テンプレートから作った最初のコミットで、権限が付いていなかったため。gitでは、実行権限もファイルの内容と同じように記録されるが、そのことを確かめる手順がなかった |
| なぜ気づかなかったか | フックの確かめ方(AGENTS.mdの「`sh -n`とサンプル入力での動作確認」)は、`sh ファイル名`で実行しても満たせ、その場合は実行権限がなくても動く。設定に登録したとおりの起動で確かめる手順も、仕組みもなかった。推測: 止めないエラーは、ふだんの画面には目立って出ない(公式ドキュメントでは確かめていない) |

## 真因

フックを確かめる手順が、フックが実際に起動される形(設定に登録したとおりの起動)を確かめていなかったこと。

## 対策

1. 2つのフックに実行権限を付けた(gitのモードを100755にした)。
2. 機械的な検査を加えた。`scripts/check_hooks.py`は、`.claude/settings.json`に登録されたすべてのフックについて、次のことを確かめる。CIのLinuxのジョブ(必須のチェック)で、毎回実行する。
   - gitのモードが100755であること。
   - 登録したとおりの起動(`sh -c`に登録の文字列を渡し、`CLAUDE_PROJECT_DIR`を設定する)で、止めるべきサンプル入力を、実際に止めること。
   - 止めるべき入力のほかに、通すべき入力も通すこと(すべてを止めてしまう壊れ方や、jqがない状態を見つけるため)。
   - 両方のサンプル入力のないフックが登録されていないこと(新しいフックを、確かめずに加えられないようにするため)。
   - 確かめる範囲は、LinuxとmacOSでの起動(`sh -c`)である。WindowsのGit BashとPowerShellでの起動は再現しない。`shell`と`args`のフィールドを使った登録は、再現できないため失敗にする。
3. AGENTS.mdの検証コマンドの表に「フックの動作」を加えた。シェルスクリプトの確かめ方に、フックは登録したとおりの起動で確かめることを加えた。

## 確かめ方

- 対策のPRのCIで、`check_hooks.py`が成功すること。
- 実行権限を外したり、フックの起動の形を変えたりすると、`check_hooks.py`が失敗すること(このPRで、実行権限を付ける前に失敗することを確かめた)。
- 以後のセッションで、Bashで`main`へのプッシュを試みると、フックが拒否すること。対策のブランチの作業中に、実際に拒否された(下の「働き始めてからの影響」)。

## 働き始めてからの影響

2つのフックに実行権限を付けると、このセッションでもすぐに働き始めた。エージェントの編集のコマンドが、ヒアドキュメントの中にサンプル入力(mainへのプッシュの文字列)を含んでいたために、block-dangerous-git.shに拒否された。これは、コマンドの文字列全体を見るという、このフックの既知の誤検知である。編集の内容を作業用のファイルにWriteのツールで書き、そのファイルを実行して回避した。誤検知と回避の手段は、オンボーディングの6.3に書いた。
