# 0006: 計画の順番が、最初に動く版を遅らせた

- 日付: 2026-11-01
- ステータス: 対策中(対策のPRがマージされていない)

## 起きたこと

作業を始めてから2日目(2026-11-01)の時点で、PRは19番まで進んだ。しかし製品のコードは雛形だけで、スクリーンセーバーとして動くものも、v0.1.0のリリースもなかった。メンテナーは、次の2点を指摘した。

- AGENTS.mdの「プロジェクト概要」には、最初から「基本機能から段階的に実装していく」「実行できるタイミングごとにGitHub Releaseでバージョンを付けリリースする」と書いてある。
- 同じ指示の別のプロジェクトでは、数時間で最初に動く版ができた。

確かめた一次情報:

- 計画0001の7章。Phase 0を「基盤整備(リリースなし)」とし、完了条件を「スパイクS1〜S6の結果が記録され」としていた。製品の機能は、すべてPhase 1以降に置いていた。
- スパイクの実機での確認は4回に及んだ。そのうち2回は、エージェントのスパイクの作り方の誤りが原因だった([スパイクの結果](../research/spike-results.md)、[incidents 0004](0004-spike-output-not-visible.md))。1回の往復には、CIでのビルド(約13分)と実機での確認がかかった。
- 計画のレビューの記録([0001](../reviews/0001-plan-adversarial-review.md))と、レビューの手順の観点([review-process.md](../development/review-process.md))。AGENTS.mdのプロセスの要件と作業の順番を突き合わせた記録も、そうする観点もなかった。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ最初に動く版ができていないか | 製品の機能をPhase 1以降に置き、Phase 0でスパイクの往復と手続きに時間を使ったため |
| なぜPhase 0で製品を作らなかったか | 計画で、Phase 0を「リリースなし」とし、スパイクS1〜S6の完了を条件にしたため |
| なぜそう計画したか | Windowsの実機でしか確かめられない不確実性を、先にすべて潰すことを優先したため。AGENTS.mdの「基本機能から段階的に」「実行できるタイミングごとにリリース」を、作業の順番に反映しなかった |
| なぜ計画のレビューで見つからなかったか | レビューの観点に、AGENTS.mdのプロセスの要件と作業の順番を突き合わせる項目がなかったため |

## 真因

計画を作るときにもレビューするときにも、AGENTS.mdのプロセスの要件(段階的な実装と、実行できるたびのリリース)に、作業の順番が沿っているかを確かめる手順がなかったこと。

## 対策

1. 計画0001を改めた(D-20)。Phase 0はスパイクS1〜S4の確認で終え、S5・S6はPhase 1の製品で確かめる。Phase 1は、最初に動く版(`/s`で電子レンジが飛ぶ)を最優先で作り、実機で動かしてから残りを足す。
2. レビューの手順の観点に、計画のレビューではAGENTS.mdのプロセスの要件と作業の順番を突き合わせることを加えた([review-process.md](../development/review-process.md))。
3. 仕組みによる確認(フックなど)は採らない。計画の順番が要件に沿っているかは、機械では判定しにくいため。

## 確かめ方

- Phase 1の最初のPRで、`/s`で電子レンジが飛ぶ版を作り、メンテナーが実機で動かせること。
- 以後の計画のレビューの記録に、プロセスの要件との突き合わせが含まれること。
