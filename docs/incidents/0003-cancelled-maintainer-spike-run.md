# 0003: メンテナーのスパイクの手動実行を取り消した

- 日付: 2026-11-01
- ステータス: 対策中(対策のPRがマージされていない)

## 起きたこと

エージェントは、スパイクの成果物を作るSpikesの手動実行について、「メンテナーが実行する」と「エージェントが実行することもできる」の両方を示した。メンテナーは06:26(UTC)に手動実行を起動した(15番)。その後、メンテナーの「おすすめで進めて」という返答を受けて、エージェントは06:38:43に同じ`main`で手動実行を起動した(16番)。15番は、ビルドを終えた直後(06:38:42に`Finished release profile ... in 7m 55s`)、成果物のアップロードの前に取り消された(06:38:46に`The operation was canceled`)。約12分のWindowsのランナーの実行が無駄になった。

確かめた一次情報: 2つの実行の情報とジョブのログ(GitHubのActions)、`spikes.yml`の`concurrency`の原文。

## なぜなぜ分析

| なぜ | 答え |
| --- | --- |
| なぜ15番が失敗したか | 成果物のアップロードの前に取り消されたため(事実: ジョブのログ)。ビルド自体は成功していた |
| なぜ取り消されたか | 同じ`main`で16番が始まり、`spikes.yml`の`concurrency`(`group: spikes-${{ github.ref }}`、`cancel-in-progress: true`)が、進行中の15番を取り消したため(事実: ワークフローの原文と、2つの実行の時刻) |
| なぜ進行中の実行があるのに16番を起動したか | エージェントが、起動の前に進行中の実行を確かめなかったため。また、誰が起動するかを1つに決めないまま提案し、「おすすめで」をエージェントが起動する意味に解釈したため |
| なぜ確かめなかったか | 外部に作用する操作の前に、その時点の状態を確かめる、という手順がなかったため |
| なぜ手動実行まで取り消される設定だったか | `spikes.yml`を作ったとき(コミット5a507fe。ADRでは検討していない)、PRの古い実行を取り消すことだけを考え、手動実行で取り消されると成果物が失われることを考えなかったため(事実: `ci.yml`のほうは、PRのときだけ取り消す設定になっている) |

## 真因

1. `spikes.yml`の設定が、手動実行まで取り消すものだった。
2. 外部に作用する操作の前に状態を確かめる手順がなく、作業の担い手を1つに決めずに提案していた。

## 対策

1. `spikes.yml`の`cancel-in-progress`を、`ci.yml`と同じくPRのときだけにした。取り消さない場合、新しい実行は進行中の実行を待ち、待機中の古い実行だけが新しい実行に置き換わる(GitHubの公式ドキュメント「Control the concurrency of workflows and jobs」で確かめた)。
2. AGENTS.mdの「進め方」に、外部に作用する操作の前にその時点の状態を確かめること、作業の担い手を1つに決めて示すことを加えた。

## 確かめ方

- 手動実行の最中に、同じブランチで別の手動実行を起動しても、進行中の実行が取り消されないこと(Actionsの実行の一覧で、`cancelled`にならないこと)。
- エージェントの提案に、作業の担い手が1つに決めて書かれていること。
