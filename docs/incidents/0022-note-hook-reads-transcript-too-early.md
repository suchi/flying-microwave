# 0022: 合間の文を確かめるフックが、記録の書き込みより先に動き、何も止めていなかった

- 日付: 2026-11-10
- ステータス: 対策中(仕組みの対策(案B)と手順の対策は、PR #67とPR #68でマージした。手順の対策の条件(マージのあとで最初に始めるセッションでの確認)は、まだ満たしていない。2026-11-10の確認は、再開したセッションでのもので、新しく始めたセッションではなかった(確かめ方を参照))
- 関連: [0018](0018-english-progress-note-again.md)(対策の不具合)、[0005](0005-english-notes-between-tool-calls.md)、[0009](0009-guard-hooks-never-ran.md)(フックを登録したとおりに確かめなかった)

## 起きたこと

2026-11-10に、0018の対策(PR #62)のマージのあとで始めた最初のセッションで、メンテナーの依頼により、合間の文を確かめるフック(`.claude/hooks/require-japanese-note.sh`)が読み込まれているかを確かめた。確認のため、日本語を含まない文(「Hook check test.」)を書いてから、何もしないコマンド(`true`)を呼んだ。呼び出しは拒否されず、そのまま実行された。0018の「確かめ方」の2つ目(対策のマージのあとのセッションで、合間に英語の文を書いたときに、次のツールの呼び出しが拒否されること)を満たさなかった。

確かめた事実(時刻はJST。記録はこのセッションの会話の記録(`transcript_path`)と、inotifyによるファイルの監視の記録):

- 14:54:43: 上の確認で、呼び出しは拒否されなかった。そのあとで、同じ`tool_use_id`と同じ記録をフックに渡して、登録したとおりの起動(`sh -c`)で手動で動かすと、拒否の出力を返した。判定の処理には誤りがない。
- 14:55ごろ: 同じセッションで、説明文(description)を英語だけにしてBashを呼ぶと、説明文を確かめるフック(`require-japanese-description.sh`)が拒否した。プロジェクトのPreToolUseのフックは、このセッションで読み込まれ、起動されている。
- 14:55:38: コマンドの中で記録を検索すると、そのコマンドを呼んだメッセージの文とtool_useの行は、すでに書かれていた。ただし、コマンドはフックより後に実行される。
- 14:56:21〜22: 記録のファイルへのアクセスを監視したまま、もう一度、日本語を含まない文を書いてから呼び出した。結果は次のとおりで、呼び出しは拒否されなかった。
  - 14:56:21.537〜21.547: 記録のファイルが開かれ、読まれた(フックの`tail`と考えられる。ほかのフックは記録を読まない)。このときのファイルの大きさ(655685バイト)は、確認用の文の行が始まる位置と同じだった。
  - 14:56:22.005: 確認用の文の行と、tool_useの行が、まとめて追記された(フックが読み終えてから約0.46秒後)。
  - 14:56:22.021: コマンドが実行された。
- 公式ドキュメント(Hooks reference、Common input fields の`transcript_path`)は、「記録のファイルは非同期に書かれ、会話より遅れることがあり、フックの起動の時点で、そのターンの最新のメッセージを含まないことがある」としている。ターンの最後の文が必要なフックには、Stop・SubagentStopの`last_assistant_message`を使うよう書いている。
- フックは、記録の中にそのツール呼び出しのメッセージが見つからなければ、何も止めない作りである(0018の対策2。記録が遅れることへの対応として選んだ)。そのため、上の遅れがあると、異常を示さないまま、すべての呼び出しを通す。
- 0018の対策のときの確認(2026-11-10 00:17)は、「ツールの実行の時点で直前の文が書かれていること」を確かめたもので、フックの起動の時点ではなかった。そのセッションは、フックを登録する前に始まっていて、Claude Codeから起動されたフックでは確かめていない。`scripts/check_hooks.py`の確認は、あらかじめ用意した記録をフックに渡すもので、記録の書き込みの時刻は再現しない。
- 0018のステータスは、新しいセッションでの確認(0018の「確かめ方」の2つ目)の前に、マージをもとに「対策済み」とした(incident 0020で定めたステータスの定義のとおり)。
- 以前の環境で書き込みの遅れがなかったかどうかは、確かめられない(以前のセッションの記録には、フックの起動の時刻がない)。
- 上の確認で日本語を含まない文を2回書いたのは、確認のための予定どおりの操作で、前のメッセージで日本語で予告した。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ英語の文で呼び出しが拒否されなかったか | フックの起動の時点で、そのメッセージがまだ記録に書かれておらず、フックが「見つからなければ止めない」の分岐に入ったため |
| なぜ記録に書かれていなかったか | Claude Codeは記録を非同期に書き、このセッションでは、フックの起動より約0.5秒遅れて書いていたため。公式ドキュメントにも、遅れうると書かれている |
| なぜ遅れで働かない設計のまま採用したか | 0018の対策のときに、記録に文が書かれていることを、フックの起動の時点ではなく、コマンドの実行の時点で確かめ、遅れは小さいと判断したため |
| なぜ誤った時点で確かめたか | 対策を作ったセッションでは、フックがClaude Codeから起動されず、本当の起動の時点を観測できなかったため。フックを手動で起動する確かめ方(0009の対策)は、起動のしかたは再現するが、Claude Codeが入力や記録をいつ用意するかは再現しない |
| なぜマージの前後に気づかなかったか | Claude Codeから起動されたときに働くことの確認を、「新しいセッションで」と先送りしたまま、ステータスを「対策済み」とし、その確認を行う時点を決めていなかったため。今回は、メンテナーが依頼して確かめた |

## 真因

1. 合間の文を確かめるフックが、公式ドキュメントで遅れうるとされている記録の書き込みに頼り、遅れたときに何も示さずに通す作りだった。
2. Claude Codeの実行時の振る舞い(入力や記録が用意される時点)に頼るフックを、Claude Codeから起動された状態で確かめないまま採用し、その確認を行う時点も決めていなかった。

## 対策

1. 現象への対応: メンテナーに報告した。対策が決まるまでは、0018の対策3の規則(合間の文も日本語で書く)だけに頼る状態である。0018のステータスを「対策中」に戻した。
2. 仕組み(2026-11-10にメンテナーが案Bを承認した。フックの変更はセキュリティ設定の変更にあたる): 次の案から、案Bを採った。
   - 案A(待つ): PreToolUseのフックで、そのメッセージが記録に書かれるまで、短い上限(例: 2秒)まで待つ。利点: 直前の文で、その呼び出しを拒否できる。欠点: すべてのツール呼び出しが、書き込みの遅れの分(観測では約0.5秒)遅くなる。記録の書き込みがフックの終了を待つ作りなら、毎回上限まで待ったうえで漏れる(未確認。案Aを採るなら、先に実験で確かめる)。遅れの大きさは、公式ドキュメントでは保証されていない。
   - 案B(1回遅れで確かめる): PreToolUseのフックで、記録にすでに書かれていて、まだ確かめていないassistantの文をすべて確かめる。確かめた位置(メッセージのid)は、セッションごとの状態ファイルに残す(Stopのフックと同じ置き場所)。日本語を含まない文があれば、その文の冒頭を引用して拒否する。利点: 待ち時間がなく、遅れの大きさに頼らない(漏れた文も、その次の呼び出しで拾える)。欠点: 拒否は、英語の文の次の呼び出しになる。状態ファイルが要る。ターンの最後のツール呼び出しの文は、次のターンの最初の呼び出しまで確かめられない(ターンの最後の返答は、これまでどおりStopのフックが確かめる)。
   - 案C(表示の時点で拾う): MessageDisplayのフック(表示されるassistantの文を受け取る)で文を状態ファイルに書き、PreToolUseのフックがそれを読む。MessageDisplayは表示を差し替えるだけで、拒否はできない(Hooks reference)。対話型でない実行では、メッセージが終わってから1回だけ起動されるとあり、このクラウドの環境で、PreToolUseより先に起動されるかは未確認。採るなら、先に実験で確かめる。
   - 推奨: 案B。公式ドキュメントで保証されていない時刻に頼らずに済むため。
   - 実装: `require-japanese-note.sh`を、記録の末尾の200行にある、ツール呼び出しを含むメッセージの文をすべて確かめる形に変えた。日本語を含まない文があれば、古いものから1つ選び、その文の冒頭を引用して拒否する。報告したメッセージのidは、セッションごとの状態ファイル(`require-japanese-reply.sh`と同じフォルダー)に残し、同じ文は2回報告しない。状態ファイルを使えないときは、何も止めない。状態ファイルが消えると(コンテナの再起動、一時フォルダーの掃除など)、記録の末尾の200行にある日本語を含まない文を、書き直し済みのものも含めて、もう一度1つずつ報告する(既知の制約。報告は文の数だけで、止め続けることはない)。入力に`agent_id`があるサブエージェントの呼び出しは確かめない(主のエージェントの文で、サブエージェントの呼び出しを止めないため。`agent_id`は、公式ドキュメントのCommon input fieldsにある)。`scripts/check_hooks.py`のサンプルを、この振る舞い(同じセッションで、英語の文を1つずつ報告し、すべて報告したあとは通すこと、サブエージェント、日本語だけの記録、記録がない場合)に合わせた。
3. 手順(2026-11-10にメンテナーが承認し、AGENTS.mdの検証の段落と、READMEのステータスの定義に加えた): Claude Codeの実行時の振る舞いに頼るフックを加えたり変えたりしたときは、そのPRのマージのあとで最初に始めるセッションで、Claude Codeから起動されたフックが期待どおり働くこと(拒否するべき入力で拒否すること)を確かめ、それまでincidentのステータスを「対策済み」にしない。AGENTS.mdの検証の段落(フックの動作の確認)と、`docs/incidents/README.md`のステータスの定義に加えた。

## 確かめ方

- 2026-11-10 17:39(JST)に、PR #67のマージのあとに再開したセッション(設定を読み直したもの)で、Claude Codeから起動されたフックを確かめた。英語だけの文(「Fourth hook check test.」)を書いて呼んだツールは通り、その次の呼び出しが、その文を引用して拒否された。再開したセッションは、新しく始めたセッションと同じとは確かめていない(15:55の確認と同じく、フックのファイルは変わっていない)。そのため、手順の対策の条件には数えず、新しく始めるセッションで確かめ直す。
- 2026-11-10 15:55ごろ(JST)に、このincidentを記録したセッションで、変えたフックをClaude Codeから起動して確かめた(設定(`.claude/settings.json`)は変えていないため、セッションの途中でも、フックのファイルの変更は次の呼び出しから使われる)。英語だけの文(「Third hook check test.」)を書いて呼んだツールは通り(記録の書き込みの遅れのため)、その次の呼び出しが、その文を引用して拒否された。さらに次の呼び出しは通り、状態ファイルには、そのメッセージのidだけが記録されていた。

- 2の対策のマージのあとで最初に始めるセッションで、合間に日本語を含まない文を書いたときに、案Bなら次の呼び出しが、案Aなら同じ呼び出しが拒否されること。拒否されなかった場合は、記録のファイルの監視で、フックが読んだ時点の記録の内容を確かめる。
- `scripts/check_hooks.py`のサンプル入力で、まだ記録に書かれていないメッセージと、すでに確かめたメッセージの扱いを確かめる(CIで毎回確かめる)。
