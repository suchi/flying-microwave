# 0026: incidentの一覧の行を、手順の箇条の間に入れてマージした

- 日付: 2026-11-12
- ステータス: 対策中(現象への対応はした。仕組みの対策は案で、メンテナーの判断を待っている)
- 関連: [0025](0025-implemented-against-recorded-decision.md)(この誤りの行の記録)

## 起きたこと

2026-11-12に、incident 0025を記録したコミット`85fa789`で、[README](README.md)の一覧に加えるはずの0025の行が、手順の箇条(手順2と手順3)の間に入った。一覧の表には0025の行がなかった。このコミットはPR #76で`main`にマージされた。次のブランチのPRを作る前のレビュー(M-2)が見つけた。

確かめた事実:

- 行を加えたのは、エージェントが書いたスクリプトである。目印として、0024へのリンクの文字列`0024-unfounded-guess-as-premise.md)`を探し、その最初の出現の行の後ろに加えた。この文字列は、一覧の表のほかに、手順2の本文([0024]を参照している)にもあり、最初の出現は手順2だった(`git blame`と、スクリプトの内容。このセッションの記録)。
- `docs/README.md`の一覧には、同じスクリプトで正しい位置に入った(目印の文字列が一覧の表にだけあった)。
- エージェントは、ほかの編集では目印が1つだけあることを確かめていた(`assert s.count(o)==1`)が、このスクリプトでは確かめていなかった。
- PR #76の再レビューは、0025の記録の中身を見たが、READMEの一覧の位置は見ていなかった(レビューの報告に、一覧の位置についての記述はない)。
- CIの「Script tests」は、`scripts/`の単体テスト(`python -I -m unittest discover -s scripts`)を実行する。incidentの一覧が記録のファイルと合っているかを確かめるテストはない(`.github/workflows/ci.yml`と`scripts/`で確かめた)。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜ行が手順の間に入ったか | スクリプトが、目印の文字列の最初の出現の後ろに加え、その文字列が手順2の本文にもあったため(スクリプトの内容と`git blame`) |
| なぜ目印が1つだけかを確かめなかったか | このスクリプトでは、確かめる行を書かなかった。確かめるかどうかは、エージェントがスクリプトを書くたびに任されている(このセッションのほかの編集と比べた) |
| なぜマージまで見つからなかったか | 一覧が記録のファイルと合っているかを確かめる仕組みがなく、レビューも一覧の位置を見なかったため(CIの設定とレビューの報告) |

## 真因

incidentの一覧(`docs/incidents/README.md`と`docs/README.md`)が、記録のファイルと合っているかを機械的に確かめる仕組みがない。

## 対策

1. 現象への対応: 0025の行を一覧の表の末尾に移した。
2. 仕組み(案。メンテナーの承認が要る): `scripts/`に単体テストを加え、`docs/incidents/`の記録のファイル(`NNNN-*.md`)のそれぞれが、`docs/incidents/README.md`の一覧の表と`docs/README.md`の一覧の表に、番号の順で1行ずつあり、表の外にないことを確かめる。CIの「Script tests」が実行するので、ワークフローは変えない。
3. 規則: 変えない。理由: 2の仕組みで、同じ種類の誤りがマージの前に見つかるため。編集のスクリプトで目印が1つだけかを確かめることは、作業の習慣とし、規則にはしない(2で結果を確かめる)。

## 確かめ方

- 2の承認のあとで、一覧の行を表の外に置くと、テストが失敗すること。
