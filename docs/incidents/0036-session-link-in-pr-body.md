# 0036: PRの本文に、セッションのリンクが入ったまま、マージの直前まで気づかなかった

- 日付: 2026-11-20
- ステータス: 対策中(2026-11-20に、メンテナーが対策の(1)と(3)を推奨どおりと判断した。計画0005のD-24。(2)は(3)の結果を見て決める。行うのは計画0005の作業10の5)
- 関連: [docs/reviews/0005](../reviews/0005-pre-publication-threat-review.md)のJ-7、AGENTS.mdの「コミットメッセージ」の節、PR #88

## 起きたこと

2026-11-19に、エージェントはPR #88をGitHubのMCPのツール(`create_pull_request`)で作った。本文の最後には、セッションのリンクを含まない締めの行(`Generated with [Claude Code](https://claude.com/claude-code)`)を書いた。2026-11-20に、マージの前提を確かめるためにPRの情報を読んだところ、本文の最後が`_Generated by [Claude Code](https://claude.ai/code/session_…)_`(セッションのリンク)になっていた。

AGENTS.mdの「コミットメッセージ」の節は、2026-11-19のメンテナーの判断(J-7)で、PRの本文にセッションのURLを書かないと定めている。この規則は、PR #88そのもので加えたものである。

エージェントは、本文を`update_pull_request`で直し、読み直してリンクがないことを確かめてから、マージした(マージのコミット`11c521c`)。

確かめた事実:

- PR #88の本文(マージの前に`pull_request_read`で読んだもの)の最後は`---\n\n---\n_Generated by [Claude Code](https://claude.ai/code/session_…)_`で、エージェントが書いた締めの行はなかった。
- 同じPRに、エージェントが`add_issue_comment`と`update_issue_comment`で書いた3件のコメントの締めの行(`_Generated by [Claude Code](https://claude.ai/code)_`)は、書いたとおりで、セッションのリンクはなかった。
- `update_pull_request`で本文を直したあとは、本文は書いたとおりで、リンクは付け足されなかった。
- 締めの行が置き換えられた仕組み(MCPのサーバーか、実行環境か)は、文書がなく分からない。`.claude/settings.json`の`attribution.sessionUrl: false`は、PR #88の作業ブランチにはあったが、このセッションが始まったときの`main`にはなかった。この設定がMCPのツールに効くかも、分からない。
- PRを作ったあとの確かめ(AGENTS.mdの手順5、`docs/development/review-process.md`)には、本文を読み直してセッションのリンクがないことを確かめる段階がない(`grep -n 'session_' AGENTS.md .claude/commands/*.md docs/development/review-process.md`で、AGENTS.mdの規則の文の1件だけ)。

- 対策(3)の調査(2026-11-20、PR #89): 本文に締めの行を書かずに`create_pull_request`でPRを作ったところ、作ったあとの本文の最後に、セッションのリンク付きの締めの行(`---`と`_Generated by [Claude Code](https://claude.ai/code/session_…)_`)が付け足されていた。PR #88(締めの行を書いて作った)では、書いた行が置き換えられていた。2回の結果から、PRを作るツールは、いつもセッションのリンクを付けると考える。`update_pull_request`で本文を直したときと、`add_issue_comment`で書いたコメントには、付け足されなかった(どちらも、直したあと、書いたあとに読んで確かめた)。
## なぜなぜ分析

1. なぜPRの本文にセッションのリンクが入ったか。
   - PRを作るツールが、締めの行をセッションのリンク付きのものに置き換えたため。仕組みは分からない(上の事実)。
2. なぜ、PRを作ったときに気づかなかったか。
   - PRを作ったあとで、本文を読み直していなかった。ツールの結果は、PRのIDとURLだけで、本文を返さない。
3. なぜ読み直さなかったか。
   - 書いた本文がそのまま使われると考えていた。PRを作ったあとに本文を確かめる手順がない。
4. 真因: 投稿したあとの本文が、書いたものと違いうることを前提にした確かめ(手順か仕組み)がない。

## 真因

GitHubに投稿したあとの本文を確かめる手順も仕組みもなく、ツールが本文を変えても気づけない。

## 対策

2026-11-20に、メンテナーが(1)と(3)を採った(計画0005のD-24)。(2)は、(3)の結果を見て決める。どれも計画0005の作業10の5で行う。

案:

1. 手順: AGENTS.mdの「PR・レビュー・マージ」の手順5と、`.claude/commands/merge-pr.md`の前提条件に、「PRを作ったあとと、マージの前に、PRの本文を読み直し、`claude.ai/code/session_`のリンクがないことを確かめる」を加える。
2. 仕組み: CIに、PRの本文に`claude.ai/code/session_`を含むときに失敗するジョブを加える(`.github/workflows/`の変更で、承認が要る)。ブランチのルールセットの必須のチェックに加えれば、リンクのあるPRはマージできなくなる。
3. 調査: 締めの行が置き換えられた仕組みを、次にPRを作るときに確かめる(本文の締めの行を書かない場合と、決まった形で書く場合の結果を比べる)。

## 確かめ方

- 対策1と2のあとの、すべてのPRの本文に、セッションのリンクがないこと(`pull_request_read`で読む)。
- 対策2: 試しに本文にリンクを入れたPRで、そのジョブが失敗すること。
