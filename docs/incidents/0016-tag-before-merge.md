# 0016: 試作版のタグが、マージの前のコミットに付いた

- 日付: 2026-11-09
- ステータス: 対策中(規則を加えるPRが、まだマージされていない。付け直したタグ`v0.2.0-alpha.4`は`f0fcc6e`を指し、リリースのワークフロー(実行42574528508)が成功したことは、2026-11-09に確かめた)
- 関連: PR #56、[0013](0013-arm64-smoke-test-only-at-release.md)、[計画0004](../plans/0004-v0.2.0-settings.md)のD-14

## 起きたこと

試作版`v0.2.0-alpha.4`のタグが、PR #56(版を`0.2.0-alpha.4`に上げる変更)をマージする前の`main`のコミット(`d68c9e5`。PR #55のマージ)に付いた。リリースのワークフロー(実行42564453744)は、最初の検査で失敗した(「Cargo.tomlのバージョン(0.2.0-alpha.3)がタグ(v0.2.0-alpha.4)と一致しない」)。下書きのリリースは作られず、何も公開されていない。

確かめた事実:

- エージェントは、1つの報告で、メンテナーに次の3つを依頼した。(1) PR #56のマージの承認と、CHANGELOGの日付の扱いの返信。(2) マージのあとのタグ付け。(3) 残ったブランチの削除。
- (2)には「マージしたら、マージのコミットの番号をお知らせします。そのあとで」と書いたが、タグを付けるコマンドは`git tag -a v0.2.0-alpha.4 -m "v0.2.0-alpha.4"`で、コミットを指定していなかった。これまでの試作版(alpha.2とalpha.3)では、マージのあとに依頼し、コマンドでマージのコミットを指定していた。
- マージはエージェントが行う手順だったが、承認の返信の前に、メンテナーが(2)を実行した。そのため、タグは、そのときの`main`の先頭に付いた。
- リリースのワークフローの版の検査が働き、誤ったビルドは作られなかった。

## なぜなぜ分析

| なぜ | 答え(確かめた事実) |
| --- | --- |
| なぜタグがマージの前のコミットに付いたか | タグを付けるコマンドがコミットを指定せず、実行したときの`main`の先頭に付く作りだったため |
| なぜコミットを指定しなかったか | 依頼を書いた時点では、マージのコミットがまだなかったため |
| なぜまだできない手順を依頼したか | 依頼をターンの最後の報告にすべて書く規則(2026-11-05)に合わせて、前提(エージェントのマージ)がまだ満たされていない手順まで、1つの報告に、実行できるコマンドの形で書いたため。往復を減らす意図だったと考えられる(推測) |
| なぜ前提が満たされているかを、手順の中で確かめなかったか | 手順の順番を文章(「マージのあとで」)だけで示し、コマンドで前提を確かめる形にしなかったため |

## 真因

前提がまだ満たされていない手順を、そのまま実行できるコマンドの形で依頼した。順番を文章で書くだけでは、読む人が前提を満たしているかを確かめられない。

## 対策

1. 現象への対応: PR #56をマージした(マージのコミット`f0fcc6e`)。メンテナーが、誤ったタグを消し、マージのコミットを指定してタグを付け直した。誤ったタグにはリリースがなかったため、利用者への影響はない。付け直したタグで、リリースのワークフローが成功した。
2. 規則: メンテナーに依頼するのは、前提がその時点で満たされている手順だけにする。前提がまだの手順(エージェントのマージのあとのタグ付けなど)は、何を待っているかだけを書き、コマンドは前提が満たされてから示す。タグを付けるコマンドには、必ず対象のコミットを指定し、その前にコミットの件名を確かめるコマンドを置く。AGENTS.mdの「進め方」に加えた。
3. 仕組み: リリースのワークフローの版の検査(`scripts/prepare_release.py`)が、誤ったコミットのビルドを止めた。今回の対策では、仕組みは変えない。理由: タグ付けはメンテナーの手作業(リポジトリのルールでメンテナーだけが付けられる)で、エージェントの側で機械的に止める手段がない。前提の確認は、依頼のコマンドで示す件名の確認と、リリースのワークフローの版の検査に任せる。

## 確かめ方

- 付け直したタグ`v0.2.0-alpha.4`がマージのコミット`f0fcc6e`を指し、リリースのワークフローが成功すること。
- 以後のタグ付けの依頼に、対象のコミットの指定と、件名の確認があること。
