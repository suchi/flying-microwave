## 実機での観察

### 1回目(2026-11-01)

メンテナーがWindows 11の実機で確かめた結果。環境の情報とログは、まだ記録していない。どのスパイクをスクリーンセーバーとして選んでいたか、各ボタンで渡された引数も、まだ確かめていない。

メンテナーの報告:

- 設定画面は表示された。見た目は簡素だった。
- プレビュー画面(設定画面の小さなプレビュー枠)は一瞬見えたが、真っ黒だった。
- 「プレビュー」ボタンを押すと、一瞬ウィンドウが現れ、すぐに消えた。
- S3〜S6は確かめていない。

考えられる説明(推測。ログで確かめる):

- settings-spikeを選んでいた場合: settings-spikeは、`/s`と`/p`で起動されると、ウィンドウを作らずにすぐ終了する(`spikes/settings-spike/src/main.rs`。ログに`not a settings mode (/s or /p): exiting quietly without a window`と出る)。この場合は、プレビュー枠が黒いことと、「プレビュー」ボタンのあとすぐに終わることは、どちらも想定どおりの動作で、S1の確認にはならない。設定画面が表示されたのは、「設定」ボタンでsettings-spikeが起動したためと考えられる。
- saver-spikeを選んでいた場合:
  - プレビュー枠: saver-spikeが描く色は、RGBの各成分が0.05〜0.10(8ビットで約13〜25)の暗い色で、12秒の周期でゆっくり変わる(`spikes/saver-spike/src/policy.rs`の`dark_color`。[ガイドライン](../design/visual-design.md#表現上のガイドライン)のG-3の閃光を避けるため)。そのため、正しく描画できていても、ほぼ黒に見える。描画できたかは、ログの`frame N presented`の行で確かめる。
  - 「プレビュー」ボタン: このボタンで渡される引数は、全画面の`/s`が想定されている(S3で確かめる項目)。入力やカーソルの移動で終了した場合は、ログに`decision: ... ends the screensaver`と`EXIT requested: <理由>`の行が出る。終了の条件は、カーソルの移動(初期化から500ミリ秒の猶予のあと、16ピクセル以上)、キーやマウスボタンの押下、ホイール、タッチ、ウィンドウを閉じる要求である。GPUの初期化が失敗として返った場合は終了せず、黒い全画面のまま入力を待つ。GPUの初期化が15秒たっても終わらない場合だけは、`EXIT requested`の行を出さずに、`GPU init watchdog fired after 15 s; exiting`と書いて終了する(終了コード5)。「一瞬」で消えたのであれば、この場合には当たらない。

次に確かめること:

1. どのスパイクを選んでいたか。S1はsaver-spike、S2はsettings-spikeを選んで行う(`spikes/README.md`)。
2. ログ(`%TEMP%\flying-microwave-spike.log`)の内容。各行にプログラム名が出るため、どちらのスパイクが、どの引数で起動したかも分かる。パスに含まれるユーザー名は伏せる。
3. 環境(上の「環境」の表の項目)。
4. saver-spikeを選んでいた場合は、「プレビュー」ボタンを押したあと、マウスに触れずに待った場合にも、すぐに消えるか。

### 2回目(2026-11-01)

メンテナーが、Spikesの手動実行の成果物(x64)を、上の「環境」の実機で実行した。ログ(`%TEMP%\flying-microwave-spike.log`)を受け取って読んだ。ログにはユーザー名を含むパスが出るため、ここには貼らない。結果の判定は、上の表に書いた。

問題1: `/s`が起動の直後に終了する。

- 起きたこと: ログにある`/s`の9回すべてで、起動の365〜516ミリ秒後に、右のAltキーの押下(`KeyboardInput state=Pressed is_synthetic=false ... physical_key=Code(AltRight)`)が届いた。キーの押下は猶予時間の内外を問わず終了の理由になるため、毎回すぐに終了した(`EXIT requested: key press Named(Alt)`)。メンテナーが見た「プレビューボタンを押すと一瞬ウィンドウが現れて、すぐ消える」は、これで説明できる。
- 押下の直前の様子: 9回すべてで、ウィンドウにフォーカスが移ったときに、合成されたキーイベント(`is_synthetic=true`)が届いていた。`Hankaku`(物理キーは`Backquote`)と、PowerShellから起動したときは`Enter`である。そのあと、2台目のモニタのウィンドウにフォーカスが移った直後に、右のAltの押下が届いた。
- 原因(winit 0.30.13のソースで確かめた): メンテナーは右のAltを押していない。押下を送ったのはwinitである。winitのWindowsの実装(`src/platform_impl/windows/window.rs`)は、`with_fullscreen`を付けて作ったウィンドウに対して、作った直後に必ず`force_window_active`を呼ぶ(1399〜1401行)。この関数は、ウィンドウを前面に出す許可を得るための回避策として、`SendInput`で拡張キーの印(`KEYEVENTF_EXTENDEDKEY`)を付けたAltの押下と解放を合成する(1537〜1574行)。拡張キーのAltは右のAltにあたる。スパイクは2台のモニタのウィンドウを`with_fullscreen`で作っていたため、自分が送ったAltの押下で終了していた。`SendInput`で送った入力は、winitの`is_synthetic`(フォーカスの移動に伴ってwinitが作るイベントの印)では区別できない。winitの`focus_window`も、ウィンドウが前面にないときは同じ関数を呼ぶ(1016〜1026行)。リモートデスクトップやIMEは原因ではなかった。環境によらず起こりうる。
- 参考: 同じ規則(キーの押下ですぐ終了)のスクリーンセーバーでも、Win32で`WS_POPUP`・`WS_EX_TOPMOST`のウィンドウを最初からモニタの大きさで作り、最初のウィンドウに`SetForegroundWindow`を1回呼ぶだけのものは、同じ環境で問題なく動いている(メンテナーが別に作ったスクリーンセーバー)。
- 対応: スパイクで`with_fullscreen`をやめた。枠のない最前面のウィンドウを、モニタの位置と大きさで作る。最初のウィンドウを、winitの`focus_window`ではなくWin32の`SetForegroundWindow`で前面に出す。
- 設計への影響: アーキテクチャの終了の規則(合成でないキーの押下はすぐに終了の理由になる)は、変えなくてよい見込みである。製品でも、winitの`with_fullscreen`と`focus_window`を、`/s`のウィンドウに使わない。Standaloneの全画面の切り替え(作成後の`set_fullscreen`)は、この関数を呼ばない(同じファイルで確かめた)。

問題2: 全画面のウィンドウで、サーフェスの設定がwgpuの検証エラーになる。

- 起きたこと: `/s`の全画面のウィンドウで`Surface::configure`を呼ぶたびに、`wgpu uncaptured error: Validation Error ... In Surface::configure: Invalid surface`がログに出た。サイズが変わって設定し直したときも同じだった。ログにあるプレビュー枠の実行では、どの回も出なかった。
- 一次情報で確かめたこと: wgpu-core 30.0.1(`src/device/resource.rs`)は、DX12の層(wgpu-hal)のサーフェスの設定が`Lost`・`Outdated`・`Occluded`・`Timeout`・`Other`のいずれかで失敗すると、`InvalidSurface`を返す。wgpu-hal 30.0.1の`src/dx12/mod.rs`の`configure`は、スワップチェーンの作成や`ResizeBuffers`が失敗したとき、本当の理由(HRESULT)を`log::error!`で出してから`Other`を返す。スパイクは`log`クレートの出力をログファイルに書いていないため、本当の理由が分からない。
- 描画への影響: 問題1のため、どの回もフレームを描く前に終了した(`/s`の回に`frame N presented`の行はない)。そのため、全画面で描画できるかは分からない。なお、スパイクはエラーのあとも`surface configured`と`2 of 2 windows can render`をログに出す。wgpuの検証エラーは`on_uncaptured_error`で記録するだけで(`spikes/saver-spike/src/gpu.rs`)、この判定には反映されないため、この2つの行は描画できる根拠にならない。
- 対応: スパイクで、`log`クレートの警告とエラーもログファイルに書くようにした(`[ERROR ...]`の行)。全画面の切り替えの途中の大きさの変化(下の「ウィンドウの大きさの変化」)がなくなることで、このエラーも消える可能性がある。直したスパイクで確かめる。

ウィンドウの大きさの変化:

- `/s`の全画面のウィンドウは、フォーカスが移ったときに、1184x804、1200x843、800x600と大きさが変わってから、モニタの大きさに戻った(`Resized`のイベント)。原因は分からない。winitの全画面の切り替えの途中の状態と推測する。スパイクで`with_fullscreen`をやめたため、直したスパイクで起きなくなるかを確かめる。

### 3回目(2026-11-01)

メンテナーが、Spikesの手動実行の16番(コミット`cd37f44`)の成果物(x64)を、上の「環境」の実機で実行した。2回目の問題1・問題2への対応(`with_fullscreen`をやめる、`log`クレートの警告とエラーをログに書く)を含むビルドである。ログを受け取って読んだ。ユーザー名を含むパスが出るため、ログはここには貼らない。

問題1(`/s`が起動の直後に終了する)は、起きなかった。

- `/s`は3回起動された。3回とも、最初のウィンドウへの`SetForegroundWindow`が成功した(`SetForegroundWindow(window[0]) = true`)。
- 右のAltの押下も、2回目に見られた合成されたキーイベント(`is_synthetic=true`)も、ログに出なかった。
- 3回とも、終了の理由はEscapeの押下だった(`is_synthetic=false`。`EXIT requested: key press Named(Escape)`)。起動からの時間は、約7.3秒、約2.4秒、約2.7秒だった。
- winitの`with_fullscreen`が合成したAltの押下が原因、という2回目の分析と合う。

問題2(全画面のウィンドウのサーフェスの設定が、wgpuの検証エラーになる)も、起きなかった。

- `Invalid surface`の行も、`log`クレートのエラーの行(`[ERROR ...]`)も、ログに出なかった。
- 2台のウィンドウのサーフェスを、1600x1200と1280x1024で設定できた(`Bgra8Unorm`、`Fifo`)。大きさが変わったあとの設定し直しも、エラーにならなかった。
- 主モニタのウィンドウで、フレームを描画した(`window[0]: frame N presented`)。2台目のモニタのウィンドウのフレームの行は、ログに出ていない。ログに出るのは、ウィンドウごとの最初の数フレームなので、2台目のウィンドウでも描画できたかは、ログからは分からない。
- 2回目の検証エラーの本当の理由は分からないままである。`with_fullscreen`による全画面の切り替えの途中の状態が関係していた、と推測する。

ウィンドウの大きさの変化は、まだ起きている。

- 2台のウィンドウとも、フォーカスが移ったときに、1184x804、1200x843の順に大きさが変わってから、モニタの大きさに戻った(`Resized`のイベント)。2回目にあった800x600は出なかった。
- `with_fullscreen`をやめても起きるため、2回目の「全画面の切り替えの途中の状態」という推測は、少なくともこの変化には当たらない。原因は分からない。
- サーフェスは毎回設定し直せたので、描画への影響はログからは見えない。製品の実装のときに、原因を調べる。

S1(プレビュー枠)は、2回目と同じ結果だった。

- `/p <HWND>`の子ウィンドウ(152x112)で描画できた。
- 終了は、どの回も`WindowEvent::CloseRequested`だった。
- 最も長い回は、約14秒のあいだに446フレームを描いた。カーソルの移動は無視した(`input ignored in preview mode`)。

S2(設定ウィンドウのモーダル相当)も、2回目と同じ結果だった。

- オーナーを無効にし、閉じたときに有効に戻せた。
- `SetForegroundWindow(owner)`は、また失敗した(`false`)。

メンテナーの報告: プレビューには何も表示されず、真っ暗だった。

- ログでは、プレビュー枠でも全画面でも、フレームを描画している。描く色は、RGBの各成分が0.05〜0.10の暗い色で(上の「1回目」)、目では黒と見分けられない。描画できたかを目で確かめられない作りだったため、1回目と同じ報告になった。対応は下に書いた。

メンテナーへの確認で分かったこと:

- 全画面のとき、カーソルは見えなくなった。
- Escapeは、メンテナーが押した。

ログからも見た目からも分からないこと: 2台目のモニタのウィンドウで描画できたか。

対応([incidents 0004](../incidents/0004-spike-output-not-visible.md)): スパイクに、ゆっくり動く小さな四角を目印として描くようにした。次の実機での確認では、プレビュー枠と2台のモニタのそれぞれで、四角が見えるかを確かめる。

GitHubのWindowsランナー(`windows-2025`)で、スパイクのビルド用ワークフローの自己テストのログから得た結果。実機での確認の代わりにはならないが、実機で確かめる項目の見当を付けるために記録する。

- 対象: PR #4のコミット`d472a09`のワークフローの実行(2026-10-31)
- 環境: Windows Server 2025(ドライバのバージョン`10.0.26100.33648`からビルド26100と推測)。表示言語は英語。GPUの有無は確かめていない
- `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_SYSTEM32)`は成功した。
- 自己テストはソフトウェアのアダプタ(WARP)を明示して要求する(`force_fallback: true`)。得られたアダプタは「Microsoft Basic Render Driver」(種類Cpu、DX12)。サーフェスの形式は`Bgra8Unorm`、表示モードは`Fifo`で設定できた。WARPを明示して要求したため、GPUが使えない環境で自動的にWARPへ切り替わるか(S6)の確認にはならない。
- `HKEY_CLASSES_ROOT\scrfile\shell`の値(ランナーの表示言語は英語。日本語の表示名は観測していないため、実機で確かめる):
