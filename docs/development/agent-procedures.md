# エージェントの作業の手順

- ステータス: 採用(計画0008で、AGENTS.mdの細かい手順を移した)
- 対象: AIエージェントと、同じ規則で作業する開発参加者
- 関連: [AGENTS.md](../../AGENTS.md)、[オンボーディング](onboarding.md)、[PRのレビュー手順](review-process.md)、[リリースの手順](release.md)、[異常の記録](../incidents/README.md)

AGENTS.mdの原則を実行するときの、細かい手順をまとめる。本文の「判断していただくこと」は、メンテナーが判断することを指す。

## 1. 計画と決定

AGENTS.mdの「進め方」の、計画と決定についての手順である。

- 大きめの機能は計画(SOW)を`docs/plans/`に保存し、合意してから実装する。
- 計画の要件(F-xx、N-xx)や設計の方針と違う実装が必要になったら、実装の前にメンテナーに確認し、決定として記録する(計画のD-xx、ADR)。要件と違う実装を、記録なしにマージしない。
- 決定(計画のD-xx、E-xx、ADR)がある作業の実装を始める前に、設計を報告し、関係する決定の項目ごとに、合っているか違うかを示す。違う項目があれば、実装の前に確認する。
- 選択肢を示すときと決定を記録するときは、判断していただくこと(見た目、動き、範囲など)と、実装の方式(エージェントの案)を分けて書く。方式を変えるときも、この手順で確認する。
- 設計を報告した作業では、コミットの前に、実装を報告した設計と項目ごとに比べ、違う項目があればコミットせずに確認する。敵対的レビューの依頼文には、報告した設計と関係する決定を要件として渡す([incidents 0040](../incidents/0040-hook-implemented-against-reported-design.md))。
- 見た目、メモリ、負荷に関わる選択(解像度、数、上限など)は、判断していただくこととして扱い、実装の途中で変えるときは、変える前に確認する([incidents 0025](../incidents/0025-implemented-against-recorded-decision.md))。
- 設計の文書やADRで、決定を後のフェーズに先送りしたときは、計画のそのフェーズの作業か完了条件に登録する([incidents 0011](../incidents/0011-log-written-against-requirement.md))。先送りした決定(計画の「あとで決めること」のE-xxなど)を決めたと記録するときは、その項目に挙げた内容ごとに、決めた内容と記録の場所を並べる。決めなかった内容は、改めて先送りして計画に登録する([incidents 0021](../incidents/0021-settings-init-timeout-missing.md))。
- 確認はまとめて行う: 作業を始める前に、その作業と続く作業を見越して、判断していただくこと(決定、範囲、方式の違い)と承認の要る操作(セキュリティ設定のファイルの編集、マージなど)を洗い出し、1回の質問にまとめる。セキュリティ設定のファイルは、編集の承認を求める回数が少なくなるよう、1つのファイルへの変更をまとめて1回で編集してよい。そのときは「1コミット=1論理変更」の例外として1つのコミットにし、コミットメッセージに論理変更ごとに分けて書く。細かな確認を何度も続けない(2026-11-23にメンテナーが指示した)。

## 2. 想定外の挙動と異常

- 原因不明のままワークアラウンドで迂回しない(AGENTS.mdの「進め方」)のは、脆弱性や誤ったコード・アーキテクチャの温床になるためである。
- 異常の定義、通常の指摘との区別、記録の手順は、[異常の記録](../incidents/README.md)に従う。

## 3. メンテナーへの依頼と報告

AGENTS.mdの「進め方」の、外部に作用する操作と、メンテナーへの依頼の詳細である。

- 外部に作用する操作(ワークフローの起動、プッシュ、PRのマージ、GitHubへの投稿など)の前に、その時点の状態(進行中のワークフローの実行、PRのhead、ほかの人の操作)を一次情報で確かめる。作業を提案するときは、誰が行うか(メンテナーかエージェントか)を1つに決めて示す。「どちらでもよい」と示すと、同じ操作が重なる([incidents 0003](../incidents/0003-cancelled-maintainer-spike-run.md))。
- メンテナーに作業(タグ付け、公開、実機での確認、承認など)を依頼するときは、手順とコマンドも含めて、そのターンの最後の報告にすべて書く。ターンの途中の文だけに書いたり、最後の報告で「前のメッセージの手順で」と参照したりしない。途中の文は、メンテナーの画面では目に入りにくく、時間を空けて読み返すと見つからないため(2026-11-05にメンテナーが指摘した)。
- メンテナーに依頼するのは、前提がその時点で満たされている手順だけにする。依頼(前の報告からの持ち越しを含む)と、メンテナーの作業が済んだかどうかについて書く文は、そのたびに一次情報(リリースの状態、タグ、PRの状態など)で確かめてから書く。一次情報で確かめられないこと(実機での確認を行ったかなど)は、「まだ行われていない」と書かずに尋ねる。質問の選択肢の前提に書くときも同じ([incidents 0031](../incidents/0031-requested-publishing-an-already-published-release.md))。
- 前提がまだの手順(エージェントのマージのあとのタグ付けなど)は、上の規則の例外として、何を待っているかだけを書き、手順とコマンドは、前提が満たされたターンの最後の報告に改めてすべて書く。
- タグを付けるコマンドには、必ず対象のコミットを指定し、その前にコミットの件名を確かめるコマンドと、期待する件名(例: `Merge pull request #56 ...`)を置き、一致しないときはタグを付けずに知らせてもらうよう書く。コマンドの形は`.claude/commands/merge-pr.md`の手順3にある([incidents 0016](../incidents/0016-tag-before-merge.md))。
- 依頼するコマンドは、coreutilsの入ったWindowsのコマンドプロンプト(cmd)でそのまま動く形にする(cmdは単引用符を引用符として扱わない)。coreutilsのコマンドは使ってよい。cmdではできないときや手間が多いときは、PowerShellかGit Bashでの実行を、どのシェルかを示して勧める(2026-11-10にメンテナーが指示した。[incidents 0023](../incidents/0023-tag-check-command-failed-in-cmd.md))。
- 設定の画面に値を入れてもらうときは、公式の文書で書式(区切り、書き方)を確かめ、そのまま貼れる値を示す。設定が効いたことを確かめる手順(手動の実行など)も、あわせて示す(2026-11-27にメンテナーが承認した。[incidents 0045](../incidents/0045-actions-allow-list-entered-without-separators.md))。
- 実機での確認の依頼の書き方と、確認を行わないときや結果とログを受け取ったときの扱いは、[リリースの手順](release.md)の「実機での確認」に従う。

## 4. モデルの使い分けと並行作業

AGENTS.mdの「進め方」の、モデルの使い分けの詳細である。

- 計画・設計・敵対的レビュー・プロジェクト全体の整合性の確認など深い検討が必要な作業は、最も高性能なモデルで行う。設計やロジックが決まった実装、簡単なコード、定型的な文書の作成は、より安価なモデル(安価なモデルを指定したサブエージェントなど)に任せてよい。安価なモデルの成果物は、高性能なモデルで整合性を確認してから取り込む。
- 実装を任せる依頼文では、TDDのRedの証拠(先に書いたテストの名前と、失敗した結果の行)を報告に求め、取り込む前にその証拠を確かめる。証拠がないときは、取り込む前に、判定をわざと壊した写しでテストが失敗することを確かめる([incidents 0043](../incidents/0043-delegated-implementation-skipped-tdd-red.md))。
- 並行作業: 互いに依存しない作業は、サブエージェントや別のセッションで並行して進めてよい。同じファイルを同時に編集しないよう、担当するファイルを分けて依頼する。

## 5. 接続できないWebサイト

必要なWebサイトに接続できない場合は、推測や架空の結果で補わない。接続できないホスト名を挙げて、実行環境のネットワーク設定(Claude Code on the Webでは環境設定のNetwork accessのAllowed domains。手順は[オンボーディング](onboarding.md)の6.5)への追加をメンテナーに依頼し、それに依存しない作業を先に進める。

## 6. 情報源と根拠

AGENTS.mdの「情報源」の詳細である。

- 一次情報で確認できない場合は、その旨を明記し、確認済みの事実と推測を区別する。コミュニティ情報(Stack Overflowなど)は、調査の手掛かりとしてのみ使い、一次情報で確認してから採用する。対象バージョンと情報の公開日を確認する。
- 推測は、根拠(確かめた事実)を示せるときだけ書き、その根拠を添える。選択肢の説明で数値の見込み(メモリ、時間など)を示すときは、計算の根拠を添える。計算していない見込みは示さない([incidents 0025](../incidents/0025-implemented-against-recorded-decision.md))。
- 記録がなく確かめられないことは「記録がなく分からない」と書き、推測で埋めない。記録がないことを、なかったことの根拠にしない。分からないことや推測を、原因の分析・判断・記録の前提にしない。メンテナーの環境や過去の操作など、メンテナーが知っている事実は、推測せずに尋ねる。尋ねる間も進められる作業は進め、その事実は分からないまま扱う([incidents 0024](../incidents/0024-unfounded-guess-as-premise.md))。
- ログに何が書かれるか・書かれないか、ログから何が分かるか・分からないかを、判断に使うときや、文書・記録・報告に書くときは、そのログを書くコードを読んで確かめ、その箇所(ファイルと関数名か行)を添える。行がないことも、事実として読む([incidents 0014](../incidents/0014-second-monitor-not-drawn.md)、[0027](../incidents/0027-log-contents-stated-without-reading-code.md))。
- 規則と手順の文書(`AGENTS.md`、`CLAUDE.md`、`.agents/skills/`、`.claude/commands/`、`docs/`の手順と運用ルール(`docs/incidents/README.md`、`docs/adr/README.md`、`docs/development/`など))は、行を切らずに読む。行の場所や有無を探すときも、`cut -c`などで行を切らない(`cut -c`は和文をバイト単位で切るため、読んだつもりの範囲よりずっと狭くなる。[incidents 0034](../incidents/0034-incident-list-test-skipped.md))。場所や有無は`grep -c`、`grep -l`、`grep -o`(一致した部分だけ)で探し、中身はReadのツールで読む。規則の文書のパスを含むコマンドで`cut -c`へパイプすると、フック(`block-dangerous-git.sh`)が止める(0034の「その後の再発」、計画0005のD-43)。
- 文書・記録・報告に、ファイルや文書を出典として書くときは、そのファイルを開いて該当箇所を確かめ、その箇所(節か行)を添える。ファイルに書かれていないことを書くときは、検索したコマンドと範囲(ファイル)を添える([incidents 0024](../incidents/0024-unfounded-guess-as-premise.md))。

## 7. 言語と文書の規則の詳細

AGENTS.mdの「言語ルール」と「ドキュメント」の詳細である。オンボーディングの7(ドキュメントのルール)の要約と合わせて読む。

- 図: 図のラベルも日本語で書く(英語のラベルの既存の図は、その図を変えるときに日本語にする)。
- 文体と用語: 一般的なオープンソースの文書くらいのくだけ方にする。堅苦しい言い回しは要らないが、口語的な言い方(「手でビルド」「動かして試す」「困ったとき」など)は使わず、技術文書で一般的な用語(「ローカルでのビルド」「実行と動作確認」「トラブルシューティング」など)を使う。
- 表示される文章の言語: AGENTS.mdの言語ルールは、表示の経路を一覧で決めると、一覧にない経路(考える過程やツールの説明文)が漏れるため、原則で定めている。考える過程の英語を許容するのは、メンテナーの判断である(英語になる理由が分かっているため。[incidents 0005](../incidents/0005-english-notes-between-tool-calls.md))。ツール呼び出しの合間の文は、2026-11-09に、メンテナーの判断で0005の許容をやめ、日本語で書くことにした([incidents 0018](../incidents/0018-english-progress-note-again.md))。フック(`require-japanese-note.sh`)が書き直しを求めた文は、書き直して作業を続ける。
- 時刻と日付: メンテナーに示す時刻は、日本標準時(JST)で書く。ツールやGitHubの表示がUTCでも、変換して書く。セッションに示される日付もUTCに沿う(JSTの0時から9時の間は前の日になる)ため、記録や報告に書く日付は、`TZ=Asia/Tokyo date`などでJSTの時計から取る([incidents 0041](../incidents/0041-dates-written-in-utc.md))。過去の出来事の日付の確かめ方と、コミットメッセージへの書き方は、`/commit`の手順4に従う。
- 個人情報: ドキュメント・Issue・PR本文に、個人を特定できる情報(氏名・アカウント名・メールアドレスなど)や会話のやり取りを残さない。プロジェクトの配布元としてのリポジトリのURL(利用者向けREADMEの連絡先など)は例外とする(メンテナーの判断)。会話で得たフィードバックは、決定事項・要件・ルールとして非人称の形で記録する。決定の理由(技術、知的財産、運用、利用者、確認の環境の制約など)は、プロダクトがなぜそうなっているかの記録として残す。選んだのが作成者であることや、作成者個人の事情に由来する理由を、ことさら書かない。決定を誰がしたか(メンテナーの判断、エージェントの案)は、役割として書いてよい(2026-11-21のメンテナーの指示。計画0005のD-30)。
- READMEの役割: ルートの`README.md`はリポジトリを見る人向け、`packaging/windows/README.md`は配布物の利用者向けとする。開発に参加する人向けの入口は`docs/development/onboarding.md`。
- 隠し要素: 隠し要素(イースターエッグなど)の存在・内容・発動条件は、開発者向けの文書(`docs/`・`AGENTS.md`)だけに書き、利用者が読む文書には書かない。利用者が読む文書とは、ルートの`README.md`、`SECURITY.md`、`packaging/windows/README.md`、`CHANGELOG.md`と、そこから作るGitHub Releaseのリリースノート、GitHub Pagesで公開するランディングページ(`site/`。ページのソースを含む。計画0006)を指す。設定画面の、隠し要素をまとめてオフにするスイッチ([設定項目仕様](../design/settings.md)の`extras.surprises`)は残すが、利用者が読む文書では、このスイッチも説明しない。
- `.gitignore`のエントリ: フォルダやファイルを削除しても、それに対応する`.gitignore`のエントリ(ビルドの生成物など)は消さない。古いコミットを取り出してビルドすると生成物がまたでき、エントリがないと誤ってコミットしうるため。過去の作業のフォルダのために残していることを、コメントで書き添える。そのフォルダをまた使うようになったら、エントリを見直す([incidents 0017](../incidents/0017-gitignore-entry-removed-with-spikes.md))。
- 規則の写し: AGENTS.mdの「規則の写し」の表の規則は、読む人に合わせて、複数の文書に同じ内容を書いている。規則の決まった語に当たる部分(条件のパスなど)を加えたり変えたりしたときは、表の決まった語も同じ変更で直す。`scripts/test_rule_copies.py`は、この表を読み、写しを置く文書のそれぞれに、決まった語がすべてそろった行があるかを確かめる(この節は除いて探す。同じ文書を2回書いたときは、そろった行が2つ要る)。決まった語にない部分の違い(ある文書にだけ足したパスなど)は見つけない([incidents 0042](../incidents/0042-rule-change-not-reflected-in-other-docs.md)、計画0005のD-29の(3)、D-30の(6)、D-31)。
