# リリースの手順

- ステータス: 採用(計画0008で、[計画0001](../plans/0001-initial-implementation-plan.md)の7.1〜7.3と、AGENTS.mdのリリースと実機での確認の手順を移した)
- 対象: 正式なリリースとプレリリース(試作版)、実機での確認
- 関連: [計画0001](../plans/0001-initial-implementation-plan.md)(フェーズ、8.2の手動テストのチェックリスト、9章のCI/CD)、[オンボーディング](onboarding.md)の8、`.claude/commands/merge-pr.md`

本文の「D-xx」「作業NN」は、計画0001の決定と作業を指す。

## リリースの条件

各フェーズのリリースは、次をすべて満たしてから行う。

1. 自動テストとCIの全ジョブがグリーン。
2. 敵対的レビューが完了している(各指摘に対応したか、対応しない理由を記録した)。
3. Windows 11実機で[手動テストのチェックリスト](../plans/0001-initial-implementation-plan.md#82-手動テストwindows実機)に合格している。確認できなかった項目はリリースノートに明記する。
4. 非機能要件の計測値を記録している。目標に届かない場合は、対応方針をメンテナーが決めている。
5. ルートのREADME・利用者向けREADME・CHANGELOG・設定項目仕様などのドキュメントが実態と一致している。開発参加者向けのオンボーディングの「この文書で扱う作業」の一覧が、そのリリースの実態で満たされている(未整備の項目は、理由と時期が書かれている。[incidents 0010](../incidents/0010-onboarding-missed-build-steps.md))。
6. メンテナーが承認している。

## 正式なリリースの手順

1. バージョンを上げるPRを作る(`Cargo.toml`のバージョンとCHANGELOGの`## vX.Y.Z (日付)`の節。実行ファイルのバージョン情報は`build.rs`で`Cargo.toml`から生成し、二重管理しない)。利用者向けREADMEを確定し、冒頭の下書きの印と注記を消す(作業13)。前の版のタグからの変更(`git log <前のタグ>..main`と、`Cargo.lock`の差分)を一覧にしてCHANGELOGの節と照らし、メンテナーに判断を仰ぐときは、その一覧を示す(2026-11-27にメンテナーが承認した。[incidents 0046](../incidents/0046-release-premise-without-diffing-the-last-tag.md))。
2. 共通のリリース条件を満たし、メンテナーの承認を得てからマージする。
3. メンテナーが、`main`のそのコミットに`vX.Y.Z`のタグを付ける(タグはルールセットで保護されている)。エージェントが依頼するときのコマンドの形は、`.claude/commands/merge-pr.md`の手順3と、[エージェントの作業の手順](agent-procedures.md)の3に従う。
4. タグのプッシュで、リリースのワークフロー(`release.yml`)が動く。検査のジョブは、タグと`Cargo.toml`のバージョン、CHANGELOGの節、利用者向けREADMEに下書きの印がないことを確かめる。ビルドのジョブがx64の実行ファイルを作り(v0.1.0ではarm64も作った。D-32)、それと並行してライセンスのジョブが`THIRD-PARTY-LICENSES.txt`を作る。zipのジョブが、x64のzip(実行ファイル、`README.md`、`LICENSE.txt`、`THIRD-PARTY-LICENSES.txt`、SBOMの`.spdx.json`)を作り(D-31)、下書きを作るジョブが`SHA256SUMS.txt`とGitHub Releaseの下書きを作る。失敗したときは、「プレリリースの手順」の手順3と同じく、エージェントが`main`から手動実行する(D-23)。
5. メンテナーが下書きの内容を確かめて公開する。

## プレリリースの手順

2026-11-01に加えた(D-20)。正式なリリースの前に、動く版ができるたびに、プレリリース`vX.Y.Z-alpha.N`として公開する。動作を保証しない試作版である。段階1・2のプレリリースは、x64だけを配布した。段階3でリリースのワークフローがarm64もビルドするようにしたため、それ以降のプレリリースにも、arm64版が含まれる([ADR-0016](../adr/0016-arm64-without-guarantee.md)、D-23)。2026-11-03に、arm64版の配布をやめたため、`v0.1.1-alpha.3`からは、x64版だけになる([ADR-0022](../adr/0022-ship-x64-only-for-now.md)、D-32)。arm64版のzipを作ったのは、v0.1.0のリリースのワークフローだけである(`v0.1.1-alpha.1`と`v0.1.1-alpha.2`は、arm64のスモークテストの失敗で、下書きを作らずに止まった)。

1. バージョンを`X.Y.Z-alpha.N`に上げるPRを作る(`Cargo.toml`のバージョンと、CHANGELOGのプレリリースの項目)。「リリースの条件」のうち、1(CIの全ジョブがグリーン)・2(レビューの完了)・6(メンテナーの承認)と、その段階で作った機能の手動テストを満たしてからマージする。あわせて、開発参加者向けのオンボーディングの「この文書で扱う作業」の一覧が、その段階の実態で満たされていることを確かめる([incidents 0010](../incidents/0010-onboarding-missed-build-steps.md))。非機能要件の計測と、利用者向けのドキュメントの確定は、正式なリリースのときに行う。前の版のタグからの変更(`git log <前のタグ>..main`と、`Cargo.lock`の差分)を一覧にしてCHANGELOGの項目と照らし、メンテナーに判断を仰ぐときは、その一覧を示す(「正式なリリースの手順」の手順1と同じ。2026-11-27にメンテナーが承認した。[incidents 0046](../incidents/0046-release-premise-without-diffing-the-last-tag.md))。
2. メンテナーが、`main`のそのコミットに`vX.Y.Z-alpha.N`のタグを付ける(タグはルールセットで保護されている)。依頼のコマンドの形は、「正式なリリースの手順」の手順3と同じ。
3. タグのプッシュで、リリースのワークフロー(`release.yml`。作業12)が動き、GitHub Releaseの下書き(プレリリース)を作る。ワークフローは、キャッシュを使わずにビルドし(計画0001の9章)、`FlyingMicrowave-<version>-windows-x64.zip`(実行ファイル、`README.md`(下書き)、`LICENSE.txt`、`THIRD-PARTY-LICENSES.txt`、SBOM)と`SHA256SUMS.txt`を添付する(v0.1.0では、arm64のzipも作った。D-32)。リリースノートは、CHANGELOGのその版の節から作る。ワークフローが動かなかったときや失敗したときは、エージェントが、ワークフローの実行の一覧で、待ち行列(`queued`、`pending`、`waiting`、`requested`)と実行中(`in_progress`)の実行がないことを確かめてから([incident 0030](../incidents/0030-push-checked-check-runs-not-workflow-runs.md))、`main`から、タグを指定して手動実行する。失敗して不完全な下書きが残ったときは、手動実行の前に、メンテナーがその下書きを削除する(削除は破壊的な操作のため。同じタグの下書きがあると、ワークフローは止まる)。
4. メンテナーが、下書きの中身を確かめ、x64のzipで実機での確認を行ってから、公開する。リリースノートは、必要なら画面で直す(インストールの手順など、CHANGELOGにない内容)。エージェントは、下書きができたことと、確かめる点を伝える。
5. 実機での確認の結果を受け取ったら、公開の前か後かにかかわらず、エージェントが、結果を記録するPRで、CHANGELOGのその版の節(冒頭の確認の説明と、既知の制限の確かめられなかった項目)を書き改める。そのPRのマージのあとで、エージェントが、その節から`scripts/prepare_release.py`で作ったリリースノートの本文と、差し替えの手順をメンテナーに渡す(このスクリプトは、タグと`Cargo.toml`の版が一致しないと止まるため、版を上げたあとの過去の版では、スクリプトの`release_notes`関数で節を取り出す)。メンテナーは、公開の前なら下書きを差し替えてから公開し、公開のあとなら画面で差し替える。結果は、その版の手順書(`docs/development/hardware-check-v<版>.md`。ファイル名の版は、確認した版と同じにする)の「## 結果」の節に書く。手順書に「## 結果」の節がある版で、CHANGELOGのその版の節に、確認をしていないとする決まった2つの文(「実機での動作の確認はしていない」「実機での動作の確認をしていない」)が残っていると、スクリプトのテスト(`scripts/test_changelog_hardware_check.py`)が失敗する。テストが見るのはこの見出しと2つの文だけで、ほかの書き方は見ない。確認を行わなかった版の手順書では、この見出しを使わない(見出しがあると、テストは確認を行ったものとして扱う)(2026-11-21に加えた。計画0005のD-26の(2)、[incident 0038](../incidents/0038-release-notes-not-updated-after-hardware-check.md))。

2026-11-01の変更(D-21): 当初は、エージェントがCIの手動実行で成果物を作り、メンテナーがGitHub Releaseの画面でプレリリースを作る手順だった(`v0.1.0-alpha.2`の成果物は、この手順で作り、メンテナーが実機で確かめた)。メンテナーの依頼で、作業12を段階3から前倒しし、下書きまでをワークフローで作るようにした。`v0.1.0-alpha.2`は、ワークフローの手動実行で下書きを作り直し、添付のzipで実機の確認をし直してから公開する(前の手順の成果物とは別のビルドになるため)。

## 実機での確認

- 依頼の書き方: メンテナーに実機での確認を依頼するときは、何が見えれば成功かを、目で見て判定できる形で示す。目で見分けられない場合(暗すぎる描画など)は、確かめる対象を見分けられるように作り直してから依頼する([incidents 0004](../incidents/0004-spike-output-not-visible.md))。
- 行わないとき: 実機での確認は、行わないか、一部だけ行うことがある(メンテナーの判断)。それで見つかる問題は、メンテナーが承知のうえで先に進める。エージェントは、確かめられなかった項目(自動の確認で通らない経路を含む)をリリースノートか計画の記録に書き、作業を止めずに進める。
- 結果を受け取ったとき: 実機での確認の結果を受け取ったら、公開の前か後かにかかわらず、「プレリリースの手順」の手順5のとおり、CHANGELOGのその版の節(確認の説明と、確かめられなかった項目)を書き改め、リリースノートの差し替えをメンテナーに依頼する([incident 0038](../incidents/0038-release-notes-not-updated-after-hardware-check.md))。実機のログを受け取ったときは、見た目の報告だけでなく、ログでも判定する([incidents 0014](../incidents/0014-second-monitor-not-drawn.md))。

## リリースのワークフローでだけ動く検査

リリースのワークフローでだけ動く環境(arm64のランナーなど)に、環境に左右される検査を加えたり変えたりするときは、タグを付けずにその環境で試す手段(手動実行のジョブなど)を用意するか、試せないことと、失敗したときに新しい版のタグが要ることを、メンテナーに示して判断を得る。その環境で失敗した検査の修正を、その環境で試せないまま次の版に入れるときは、原因を確かめたと考える場合も、修正が前提にしていることを並べ、そのそれぞれを一次情報(ログの行など)で確かめたかを示す。あわせて、次のタグも失敗しうることと、失敗したらさらに新しい版のタグが要ることを示して、メンテナーの判断を得る。版を上げるPRは、その判断のあとで作る([incidents 0013](../incidents/0013-arm64-smoke-test-only-at-release.md))。
