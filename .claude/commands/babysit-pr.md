PR #$ARGUMENTS のレビュー指摘とCIの状態を確認し、対応する。

手順の正本は`docs/development/review-process.md`(共通ループ)。最初の敵対的レビューは、PRを作る前(プッシュの前)に済ませておく(ADR-0018)。このコマンドは、PRを作ったあとの指摘とCIに対応する。本リポジトリのレビュアーは敵対的レビューのエージェントで、GitHub Copilotのレビューは使わない(ADR-0014)。

## 手順

1. PRの状態を確認する: マージの可否、CIの結果、未解決のレビュースレッド、前回のレビュー以降の差分。
2. 敵対的レビューを依頼する(`docs/development/review-process.md`の「敵対的レビューの手順」)。
   - 作成者とは別の新しいコンテキストで、読み取り専用を指示したレビュー用エージェント(サブエージェントまたは`/code-review`)を起動する。どちらの場合も作成者と作業ツリーを共有しない。サブエージェントは別のworktreeで起動し、作業ツリーやHEADを変えるコマンドを使わせない(`docs/development/review-process.md`の「敵対的レビューの手順」)。
   - 渡すのは差分の範囲と、関係する計画・設計・ADR・AGENTS.mdのルールだけ。作成者の結論や仮説は渡さない。
   - 再レビューでは、前回の指摘とその対応の一覧も渡す。
3. 各指摘について:
   a. 一次情報で検証し、「確認済み」「未確認・妥当」「不採用」に分ける。
   b. 採用した指摘はコードやドキュメントを修正し、AGENTS.mdの検証コマンドを実行する(ドキュメントだけの変更では不要)。
   c. 1つの論理変更ごとにコミット(形式はAGENTS.mdに従う)し、すべての修正の検証を終えてからまとめて1回でプッシュする(重いCIの再実行を減らすため。ADR-0017)。
   d. 指摘と対応の一覧をPRに1件のコメントとしてまとめて投稿する。冒頭に「レビュー対象: `<base>..<head SHA>`、指摘: N件」を書く。人間が付けたレビュースレッドには、対応内容を日本語で返信してから解決する。
4. 再レビューは、medium以上の指摘を修正したときだけ1回行う(`docs/development/review-process.md`の「レビューの深さ」)。それ以外は修正して記録したうえで、「レビュー完了の判定」を満たしたら完了と報告する。マージはしない(マージには明示的なユーザー承認が必要。/merge-pr)。

## 環境への適応

- ローカルのClaude Code(ghあり): ghとサブエージェントで上記を実行する。
- claude.ai/code(Web、ghなし): 同じ手順をGitHub MCPツールで実行し、`subscribe_pr_activity`ツールでPRを購読してレビューコメント・CIイベントを自動で受け取る。PRのマージ/クローズ時またはユーザーの停止指示で購読を解除する。

## Copilotを使う場合

本リポジトリでは使わない。将来使う場合の依頼方法・完了の判定・禁止事項は`docs/development/review-process.md`の「GitHub Copilotを使う場合の手順」に従い、上記と同じループで進める。

## 重要ルール

- スレッドを解決する前に返信を投稿する(同じ指摘の繰り返しを防ぐ)。
- 再レビュー目的でPRをクローズ/リオープン・再作成しない(履歴が壊れる)。
- セキュリティに関わる指摘は、ユーザーが判断するまで未解決のままにする。
