---

このリポジトリのドキュメントの整合性をチェックする。報告のみで、ファイルは変更しない。

1. README / AGENTS.mdと実態: 記載のコマンドが存在し動くか、ディレクトリ構成が実際のツリーと一致するか、依存の名前・バージョンがマニフェストと一致するか。
2. ADR(`docs/adr/`がある場合): `docs/adr/README.md`のインデックスとファイルの一致、番号の連番(欠番を報告)、非推奨ADRの明示。
3. 相互参照: ドキュメント間のリンクが解決できるか、削除・リネームされたファイルへの言及が残っていないか。
4. 書くべきことの抜け: `docs/development/onboarding.md`の「この文書で扱う作業」の一覧で、各作業の手順が実際に書かれていて、今のコード(引数、パス、ログの文言など)と照らして合っているか。実行での確認は、リリースの前の実機の手動テストで行う。「未整備」の項目は、理由と整える時期が書かれているか。一覧にない開発者の作業(新しく加わったコマンドやモードなど)がないか(docs/incidents/0010)。
5. 要件と実装: 計画の機能要件・非機能要件(`docs/plans/0001-initial-implementation-plan.md`のF-xx、N-xxと、進行中と直近に完了したフェーズの計画(`docs/plans/`)の要件。docs/incidents/0021)とアーキテクチャの方針(`docs/design/architecture.md`のエラー処理とログ、セキュリティなど)に、今のコードが反していないか。反している場合、その決定の記録(計画のD-xx、ADR)があるか。結果はF-xx・N-xxの番号ごとに報告する。設計の文書とADRで後のフェーズに先送りした決定(「Phase Nで決める」など)が、計画のそのフェーズの作業か完了条件に登録されているか(docs/incidents/0011)。計画の「あとで決めること」で決めたとした項目は、項目に挙げた内容がすべて決まっているか(docs/incidents/0021)。
6. 異常の記録: `docs/incidents/`の各記録のステータスが、対策のPRのマージの状態と合っているか(対策がマージされていれば「対策済み」。docs/incidents/0020)。

指摘を重要度別の箇条書きで日本語で報告する。指摘のそれぞれについて、異常(規則や手順が守られなかった、規則や手順に欠けがあった、同じ種類の問題の再発。AGENTS.mdの「進め方」)に当たるかも示す。異常に当たるものは、直すだけでなく`docs/incidents/`に記録する(docs/incidents/0020)。問題がなければ「整合性チェック OK」と報告する。
